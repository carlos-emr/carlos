# CDS import final review and refactor decisions

Target: `release/2026.08`. Scope: the complete import system, its existing clinical integrations and its coordinated CLI/container entry points. Export remains outside this delivery. See the [documentation index](cds-import.md), [architecture](cds-import-architecture.md) and [release verification contract](cds-import-release-verification.md).

## Review basis

Independent reviews compared the full implementation with the Ontario billing architecture, project layer naming, actual CARLOS DAO/model behavior, the pinned OntarioMD contracts and the import's transaction/recovery requirements. Review traces covered HTTP actions, assemblers, view records, JSP/JavaScript, application services, category preparation/writers, underlying clinical readers, physical JDBC controls and the installed command boundary.

Failure traces followed a large attachment, partial-date prevention, historical prescription and interrupted unit through preparation, publication, native commit, receipt/checkpoint reconciliation, reporting and recovery. Separate DAO reviews examined actual callbacks, generated identifiers, caches, transaction propagation and external side effects before choosing composition or a narrow participating extension.

The conclusion is that a wholesale importer or DAO rewrite is not justified. The shared engine, bounded preparation, fenced unit ownership and existing-model composition should remain. Source review identifies residual changes; executed final-candidate gates remain the release acceptance authority.

These corrections are narrow application, presentation, reporting and SQL admission changes. They do not justify generic resetting of uncertain uploads, replaying clinical units, weakening strict SQL or removing ownership checks.

R1–R3 are implemented and independently reviewed against their exact source hashes. R1/R3 passed 70 focused tests across five existing/new submission, upload, action, contract and job-service families; all ten owned Java files passed Checkstyle. R2 passed 89 focused tests across four receipt/control families, including deterministic Resume interleaving, fourteen outcome combinations and fresh preview-state coverage; both owned Java files passed Checkstyle. These are focused verification results, not final-candidate database, installed or resource acceptance.

R4 changes the verification-container contract and its fixtures; clinical Java, database migrations and import semantics are unchanged. Its 20 focused protocol tests and all 124 CI Python tooling tests passed without failures, errors or skips. Independent source review checked the read-only parent, exact bounded content-root list, dedicated writable leaves and unchanged resource/recovery cases. The complete mount policy is documented in the [container recovery driver](cds-container-recovery-driver.md); actual constrained-container cases remain separate release gates.

R2 is a point-in-time receipt correction. Controls accepted after the completion snapshot belong to later live status; prior immutable receipts are not rewritten. The existing operator facade's additional pending-review overlay remains authoritative for current review action.

R5 passed 86 focused cases and all 13 focused physical MariaDB coordinator cases. The real Spring/JPA path performed one scalar SELECT per binding without an actual transaction or entity load, applied the existing 120-second query bound, and released its connection and owned persistence context before file access. Twelve binding reads used 25 raw database statements versus 61 for the original transaction-based path, saving 36; both measurements include their final observation query. This fixed-cost diagnostic does not replace the unchanged final-candidate resource gate.

An unannotated DAO method would inherit `AbstractDaoImpl`'s transaction requirement, so removing only the service wrapper would not establish this behavior. The preliminary value object is an invocation-local snapshot, not an authorization token or a cache of mutable run state. The later protected read transaction and its current authorization/binding checks remain unchanged. No poll cadence, ownership check, interruption probe or resource limit is relaxed.

## Design decisions retained

- Prototype actions with native HTTP/version/security gates; internal JSPs render encoded immutable models.
- Service-owned acceptance and clinical transactions, with a durable database work authority and a bounded in-process worker queue.
- Bounded source parsing/spooling/preparation outside clinical write transactions.
- Native data, precision metadata, references, receipt, strict event and checkpoint in the same fenced unit.
- Recovery from exact sealed expected work and current physical receipts; unknown acknowledgment is not treated as rollback.
- Existing participating CARLOS DAOs and narrowly extended APIs where ordinary managers would change historical meaning or emit unsuitable side effects.
- Fresh bounded identity/program projections where generic APIs introduce cached authorization, eager graphs or incomplete identity predicates.
- Narrow physical JDBC ownership, metadata pinning and bounded native-row hashing.
- Retention of accepted source, uncertain publications, correction history, prior reports and resumable state.

## Native chart dates and verification boundaries

R6 was identified by an actual imported chart failure in `EChartNoteEntry` sorting. The imported notes had valid unknown or date-only source precision and nullable native observation timestamps. Reader ordering follows `CaseManagementNote.observationDateComparator`: known dates sort chronologically, unknown dates remain last in either direction, and equal keys retain their existing order. Entry identifiers span several types, so the view comparator does not introduce an identifier comparison. This is a presentation correction; it does not manufacture event times, change clinical records or assign an unknown source author to the importing operator.

R7 corrects verification sequencing. The normal workflow's initial ZIP and replay each finish their existing metadata qualification and strict browser checks before the next handle opens. The corpus installs those checks during menu setup, before its import step. Original failed test results, immutable sources, completed jobs and report generations remain evidence. The normal harness deliberately removes its own two synthetic charts after native assertions; later report audits verify authenticated HTTP delivery and physical hashes, with that cleanup stated explicitly. They do not claim those removed targets remain live.

Focused source corrections and their unit tests do not replace the current candidate's native chart, full corpus, recovery, installed-command and resource gates. Their executed results and any remaining failures belong in the linked verification record.

## SQL metadata classification complexity

R8 confirms Sonar finding S8786 with actual Java 25.0.4.1 and JSQLParser 5.3. Synthetic `DESC` statements with a long whitespace prefix and a trailing line comment containing an internal newline parse as exactly one `DescribeStatement`. The existing non-DOTALL metadata regex then refuses them. The original quantifier took about 74 ms, 267 ms and 1,108 ms at 8,192, 16,384 and 32,768 spaces; the possessive form returned the same refusal in about 0.4–1.9 ms. A bounded five-second diagnostic stopped during the 60,000-space legacy match. That is a whole-probe limit, not a measurement that the individual match exceeded five seconds.

The correction consumes the whitespace prefix once with `\s++`. It retains the full-statement parser and its one-statement requirement, the existing accepted ASCII metadata forms, conservative refusal of internal multiline comments, original SQL execution and maintenance/ownership fencing. It does not broaden the regex to accept multiline suffixes. The existing guard unit suite adds accepted-whitespace cases, both parser-valid comment refusals, metadata followed by another statement, and a bounded 128 KiB prefix case through the actual classifier. The timeout checks bounded work without asserting fragile timing ratios.

`CdsJdbcAdmissionGuard` participates in the native ruleset fingerprint. This correction therefore requires a newly measured fingerprint and fresh source/class, candidate and installed verification bindings. Prior candidate results remain evidence for their original bytes; they do not certify the later SQL correction.

## Report startup database work

R9 follows a retained ZIP64 candidate failure of 2,002 raw statements against the unchanged 2,000-statement limit. Report startup previously computed three unused patient, unit and diagnostic aggregates and separately fetched the accepted snapshot path. The report-entry projection contains only delivery, discovery, preview, sealing and immutable snapshot-location facts. Its protected string representation excludes the path.

Both entry and job-binding reads use the existing run DAO's explicit read-only `SUPPORTS` pattern. The service rejects an ambient transaction, and file access begins after the scalar read has released its resources. The current job read remains after the same ownership probe; its generation and manifest fields are not reused from the earlier entry read. Ownership checks, interruption checks, deadlines and poll intervals retain their existing positions.

The final completion summary still reads and validates the actual aggregates after report generation. Its fresh pending-Resume and terminal-state predicates remain authoritative, followed by the existing locked generation and manifest selection. Removing unused startup aggregates does not authorize cached progress, a stale completion receipt or a changed query budget. Physical query savings and a complete unchanged resource-gate pass must be recorded for the successor artifact; a fixed-cost diagnostic alone does not qualify that artifact.

## Coherent browser job observations

R10 follows a retained-recovery browser failure: the database recorded cancellation and selected the next delivered report generation in under eight seconds, but the browser's 180-second wait for that generation failed. The original response body and DOM were not retained, so the precise interleaving of that execution is unproven. Source review identified two concrete hazards: separately read job and summary values, and obsolete responses for the same run that could overwrite a newer view. Deterministic browser controls reproduce the latter hazard against the preceding code. Backend completion does not turn the failed UI gate into a pass.

The HTTP job read now obtains `CdsImportStatusDto` through `CdsImportService.observe` and `CdsImportObservationService.status`. Current authorization precedes every aggregate within one bounded read-only repeatable-read snapshot. The snapshot ends before HTTP serialization; it contains no file I/O and takes no write locks. The existing summary read scope, clinical transactions, DAO contracts and CLI methods retain their previous isolation and behavior. The adapter still applies `CdsWeb`'s safe job and summary projections, retaining API version 2 and excluding private storage locations.

The browser associates status work with both the selected view and the request. Reopening the same run starts a new view. Obsolete responses, failures and queued polls cannot replace newer values, disable their controls or change their polling decision. Patient and diagnostic pages retain their finite page bounds and reject obsolete updates. A current request failure still marks status unknown and preserves the accepted job bookmark and last confirmed values.

Cancel, Resume and review responses also retain the original run and view. A late mutation failure cannot overwrite an independent job's notice. Unconfirmed acknowledgements remain bounded client reminders for their original runs, without retaining review text or raw exception messages. Another control is refused locally while its run's earlier acknowledgement is pending or unconfirmed. An operator can check that run's fresh durable status and dismiss a settled reminder; this is an acknowledgement of the status check, not a declaration that the mutation succeeded or failed. In-flight reminders cannot be dismissed, existing reminders are not silently evicted, and no automatic mutation retry occurs.

The native regression checks a fresh JDBC read across a committed writer, rather than relying only on Hibernate's entity cache, and verifies connection isolation is restored after the read. The browser regressions drive the real controller with deferred responses, including failure and callback ordering. Fresh source, packaged artifact, runtime and full acceptance bindings remain required after this correction; earlier candidate results remain evidence for their original bytes.

## Standalone run reads

R11 follows a later first-attempt ZIP64 failure of 2,003 raw statements against the unchanged 2,000-statement limit. That execution independently verified its native document and completed the import, but failed the resource gate. Its compiled classes matched the preceding candidate; the captured counter comparison included additional progress observations and read/session work. The failure remains evidence and does not justify a retry, query subtraction, a cadence change or an assumed host explanation.

`CdsImportLedgerService.status` and `snapshotLocation` now use the existing `jobBinding` read boundary. Each invocation performs a fresh bounded scalar read through the existing run DAO, using its explicit read-only `SUPPORTS` declaration. It returns all job fields or the protected path after the connection and owned persistence context are released. It does not cache mutable run state, reuse an authorization decision or retain a transaction across file I/O. Invalid run IDs, missing rows and ambient transactions retain their existing refusals. The accepted model and migration require a non-null snapshot location.

The protected observation read methods remain separate: their current binding and authorization still occur inside the required read scope. Actor observations keep their deliberate pre-file and post-file binding checks. Ownership, interruption, attempt budgets, progress intervals and all caller read positions remain unchanged.

The native comparison exercises both public APIs independently, records the full raw statement windows without subtracting observer work, and compares the former transaction/entity reads explicitly. The earlier R5 window remains unchanged. R9's historical snapshot baseline explicitly executes its former transaction path, so changing the public getter cannot silently redefine that baseline. Focused parity tests and compiled native coverage do not establish a new ZIP64 pass; the successor's actual native measurements and all five unchanged resource profiles remain required.
