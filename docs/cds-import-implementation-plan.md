# Import invariants

1. **Source preservation:** retain an immutable authorized source package and its complete attachment inventory until the migration's retention/reconciliation policy permits deletion. Import never moves, rewrites or deletes the operator's originals.
2. **No fabricated meaning:** normalized storage cannot invent exact dates, medication status, doses, units, code equivalence, identity, authorship, reviewed status or consent. Imported historical content does not become newly prescribed, administered, reviewed or consented merely through migration.
3. **No silent loss:** every discovered patient, source section, repeated record and meaningful source field has an explicit disposition. Preserve unmapped or invalid content in protected staging/quarantine with a visible unresolved result; do not insert malformed clinical objects or count quarantine as successful structured import.
4. **Truthful completion:** completion requires clinical sections, files, routing, contacts, provenance, required audit and reconciliation. A demographic insert, a non-null return, an HTTP 200 or a generated log is insufficient.
5. **Safe identity:** merge is opt-in, uses one proven eligible target, and refuses ambiguous/conflicting identity. New-chart creation cannot be a fallback from an ambiguous merge.
6. **Safe repeats:** exactly completed record units do not duplicate on retry. Changed payloads and uncertain prior writes cannot be silently skipped or blindly appended.
7. **Bounded work:** parser, validation, Base64 decoding, persistence context, queues, result collection, lookup caches, attachments and directory discovery have measured memory/disk/concurrency bounds.
8. **Recoverable boundaries:** clinical writes and their source-to-target checkpoint are atomic within each supported transaction unit. Files and external side effects have explicit crash-safe lifecycle handling. No whole-patient atomicity claim is made unless separately proven.
9. **Fenced ownership:** a stale worker cannot commit after takeover. Heartbeats are observations, not authorization to reclaim a running import.
10. **Operational separation:** imported data must not unexpectedly trigger outbound fax, integrations, reminders, messages or unrelated scheduled work. Each side effect is suppressed or intentionally queued with its own idempotency and reviewed policy.

# Required refactoring structure and design

Refactor the CARLOS import path and every adopted reference implementation to these responsibilities. Extracting the large action unchanged into one large service is insufficient. Names below describe responsibilities rather than mandating new frameworks, one class per row, or a general migration platform. Use the target release's existing injection, persistence, transaction, security, path-validation and testing conventions. Prefer small import-specific components and existing infrastructure where it can prove the contract.

| Boundary | Responsibility and dependency direction | Problems it must prevent |
| --- | --- | --- |
| Web/CLI adapters | Authenticate, bind/validate typed arguments, resolve approved delegation and submit/status/cancel through the application API; format the common result contract | Servlet-dependent core, option defaults silently overriding user input, forged provider attribution, divergent web/CLI behavior |
| Application coordinator | Own the explicit job state machine, immutable options, admission, permissions, stage transitions and cancellation; compose injected collaborators | A new giant service, hidden mutable action state, stages continuing after a failed prerequisite, request lifetime controlling execution |
| Source and upload storage | Secure bounded ingress, immutable snapshot publication, digests, archive/reference discovery and owned spool lifecycle | Pre-action body buffering, path escape, mutable input, loss of accepted source during replacement, cleanup deleting committed bytes |
| Schema/profile reader | Hardened streaming events, local pinned validation, lexical checks and bounded typed/on-disk records; no clinical writes | DOM/XMLBeans/Base64 reconstruction, repeated full parses, validator retention, global lists/caches and parser exceptions converted to success |
| Category normalization and target constraints | Pure deterministic source-to-target mappings selected by approved profile; retain original meaning/precision and emit structured diagnostics | Fabricated dates/status/authority, truncation, invalid native values, DIN enrichment replacing source and normalization drift on retry |
| Identity and execution planner | Read-only candidate resolution, reviewed target map, full occurrence/dependency workset and durable seal | Ambiguous create fallback, option-based idempotency bypass, duplicate fan-out, recovery overlooking never-started work |
| Clinical unit executors | Small category-specific writers using reviewed participating CARLOS domain APIs; one explicit owner for isolation, fencing, clinical writes, strict audit and source checkpoint | Nested independent commits, mixed persistence contexts, stale worker commits, partial source records counted complete |
| File publication and allowed side effects | Ownership-aware staged/durable publication, reference checks and idempotent outbox delivery only for approved effects | Database/filesystem pseudo-atomicity, deleting reused destinations, duplicate sends or premature clinical visibility |
| Recovery and finalizer | Reconcile sealed expected work against durable outcomes, resume only proven safe units, atomically complete/release holds | Whole-patient blind retry, uncertainty treated as rollback, count-only completion, hold release after a process simply exits |
| Diagnostics and result projection | Project the same durable state into protected event/error files, UI, API and CLI results; bounded streams and explicit delivery state | Contradictory totals, PHI in ordinary logs, unbounded warning arrays, reporting failure hiding committed data |

Dependency flow is adapters → application orchestration → pure readers/planners and explicit domain/storage interfaces. Clinical write adapters call CARLOS domain APIs; core normalization never calls an action, servlet, filesystem publication API or DAO. Transaction boundaries belong to the unit executor rather than controllers, parser callbacks or result formatting. Repositories expose narrow operations for source lineage, ownership, checkpoints and finalization. Use constructor/injected dependencies and immutable per-run context; avoid static service locators, shared mutable valid-file lists and per-run fields on reusable singleton services. Persist state explicitly instead of depending on in-memory object identity between stages.

Keep each category's interpretation and writer separate enough to review and test independently, with shared temporal/code/unit helpers only where semantics truly match. A registry keyed by approved profile/category can select reviewed mappings; do not build a permissive reflection-based copier or dynamically execute vendor-supplied transformation code. Unrecognized profiles/choices/fields have explicit contract handling. Pure normalization returns a candidate value plus original-value/provenance and diagnostic decisions; it never silently repairs data by catching persistence exceptions.

Before writes, validate normalized candidates against a versioned CARLOS constraint catalogue: actual fresh/upgrade column lengths, nullability, precision/scale, code/enum limits, Unicode/collation behavior, date representation, required related rows and downstream reader assumptions. Validate the runtime schema/capabilities against the supported catalogue, and refuse a mismatched deployment before execution. Review Unicode character/byte distinctions, decimal rounding and overflows explicitly. A final database constraint failure still rolls back its whole unit and produces a contextual protected diagnostic; prevalidation does not make database enforcement optional. Legitimate overlength/unknown values require lossless native expansion or the approved category-local representation, never silent truncation or malformed active rows.

Every stage has an assigned heap/buffer/cache/queue bound, disk/inode reservation, timeout/cancellation boundary and durable restart point. Backpressure prevents the parser/attachment producer from outrunning persistence; spill occurrence grouping, diagnostics and execution manifests rather than making batch-sized collections. Use overflow-safe counters and measured resource admission for the whole process group. Transaction size is independent of upload size and parser lifetime. A worker process may have an explicit heap limit, but more heap, parallel threads, a new parser name or generic retries are not substitutes for these guarantees.

Typed failures distinguish rejected input, review-required clinical meaning, retryable known-uncommitted infrastructure failure, uncertain commit and operational delivery failure. Exceptions that require rollback propagate through the transaction owner. Catch at stage/entry boundaries to record the proven outcome; do not return a nominal success object after an internal failure, use catch-and-continue around required writes, or wrap an entire patient/job in an automatic retry decorator. Fatal VM/resource failures terminate the worker and are reconciled by supervision. Generate human messages from stable structured codes with protected context; domain mappers do not log raw source values to ordinary logs.

Refactor incrementally with explicit before/after boundaries: capture meaningful current behavior with fixtures; introduce the pure model and read-only comparison; replace one reviewed category/transaction path at a time behind disabled admission; prove its state and failure behavior; then switch web and CLI together to the single safe mutation path. Preserve ordinary non-import callers through separate reviewed participating APIs rather than global propagation/cleanup changes. Remove obsolete import-only parsing, counters and fallback paths once the replacement has evidence. Never run old and new mutation paths against the same clinical input for comparison.

For every Magenta/Open-O candidate, record whether its behavior is adopted, rewritten or rejected and why. Adapt algorithms to CARLOS domain/injection/security conventions, namespace and current transaction ownership instead of copying static helpers, request-coupled actions or unsafe error recovery. Preserve required attribution and source tests, then add CARLOS-specific field/constraint, failure-injection and installed workflow evidence. The final architecture review must trace one large attachment, one partial-date prevention, one historical prescription and one crash/resume across every boundary and demonstrate the absence of hidden independent writes or unbounded materialization.

# Clinical normalization contract

These are proposed CARLOS normalization rules, not invented OntarioMD mandates. Reconcile them with the official dictionary in G0 and approve the clinical decisions before implementation. ## Dates and precision

| Source input | Safe CARLOS representation | Required behavior and tests |
| --- | --- | --- |
| Valid full date | Preserve the clinical calendar date and source precision | Strict leap/calendar validation; no timezone day shift; display/edit/print agree |
| Year and month only | Preserve the original month precision and interval covering that month | A first-of-month storage anchor, if legacy storage requires it, is explicitly synthetic; rules cannot treat its day as known |
| Year only | Preserve year precision and the full-year interval | A January 1 anchor is storage only, never a claimed administration/birth/event day |
| Optional date absent | Represent unknown date explicitly while retaining the valid historical record | Do not use import time, epoch or today's date as a clinical event date; audit timestamps remain separate |
| Invalid/impossible/ambiguous date | Preserve source in quarantine and a review item; do not construct an invalid active clinical record | No lenient rollover, silent truncation or date invented from locale |
| DateTime with explicit offset | Preserve the original lexical value/offset and correct instant where the target supports it | Verify DST/day-boundary behavior; keep clinical date-only semantics distinct |
| Local DateTime without offset | Preserve local time with unknown/source-configured zone explicitly identified | Do not assume UTC; ambiguous DST resolution requires the approved source policy or review |

CARLOS already has a `partial_date` mechanism: prevention precision is stored with table identifier 4 and field identifier 7, using `YYYY` or `YYYY-MM`, with a full-date storage anchor. The list view can display original precision, but inspected prevention readers such as `PreventionItem` and date/age interval calculations can still consume only the raw date. The prior edit-fix issue being closed is not proof that the exact release has the fix or that all readers preserve precision.

The implementation must carry precision through creation, partial metadata, display, edit/save, print, reminder/due calculations, age-at-dose and migration reconciliation. For an interval, a clinical rule may make a definite decision only if every possible date supports that decision under an approved rule. Otherwise return an explicit unknown/review state, not a fabricated overdue/valid dose. Overlapping intervals, such as a year-only 2019 dose and a May 2019 dose, cannot be ordered by their synthetic anchors as proof of which happened last. Test last-dose selection, dose counts and spacing under uncertainty. Clinical reviewers must approve the exact domain semantics; do not invent vaccine scheduling thresholds in migration code.

Track [#4814](https://github.com/carlos-emr/carlos/issues/4814) and the actual fix [#4815](https://github.com/carlos-emr/carlos/pull/4815) as a named dependency. The inspected release JSP still contains the problematic required full-date input. Verify target/ancestry and include any missing equivalent correction in this same `release/2026.08` feature PR. Do not assume an issue closed elsewhere establishes release behavior or routinely cherry-pick across protected lines contrary to the repository's merge process.

A valid undated immunization must not be dropped just because a legacy column/widget requires a full date. Add explicit unknown-date storage and precision-aware readers where necessary. If that cannot be made safe in the release, preserve the record as a visible unresolved historical item and block a claim of complete structured migration for that patient. It must never appear as an administered dose on a guessed day.

Resolve the existing Date-only REST, SOAP, summary and lightweight DTO contracts explicitly. Add precision/original-value/interval information or a versioned representation and update bundled consumers; a legacy client must negotiate a safe representation or receive a clear refusal requiring an upgrade for an affected operation. Silent omission of partial/undated records is not a compatible solution. Exact-date records retain their existing public type and behavior. Inventory actual integration clients before activation. The shared `PartialDate` helper is also used by allergy, prescription, diagnosis and document workflows: preserve existing YEAR/YEAR-MONTH tags and do not introduce an `UNKNOWN`/interval tag that old helpers silently interpret as a full date. Never infer precision from January 1 or the first of a month, or backfill existing exact dates by that heuristic. Test genuine exact January 1, existing partial records without new provenance, and ordinary non-import edit/save flows.

DOB is stricter for identity: under the inspected runtime schema it is a required full date. Malformed or incomplete DOB cannot participate in automatic HIN+DOB merge, and zero-filled components cannot become a valid invented DOB. Any supported older/vendor variant allowing uncertain DOB needs its own reviewed representation and must remain ineligible for exact-date automatic matching.

Time-shift behavior is explicitly limited to synthetic/anonymized testing unless an authorized migration contract requires it. Default is zero. Reject nonzero shift with automatic merge unless a separately reviewed identity policy proves safety; a shifted DOB must not match a real existing chart.

## Specification discrepancies requiring recorded interpretation

The source documents are not perfectly uniform. Preserve and resolve the actual discrepancy rather than silently choosing whichever definition is easier:

1. Guide section 1.10 describes k as 1000, while the XSD explicitly uses limits such as 32768/65536 and the migration dictionary references those XSD lengths. 3. Logical support M/O, per-field storage/display flags, code-set conformance and XML occurrence are distinct matrix columns. A mandatory-to-support logical element need not be populated in every source patient. Optional supplied supported values still require faithful import.
4. Field-specific blank/unknown choices differ. For example, the medication narrative permits undocumented compliance, while different fields use `ynIndicator` versus `ynIndicatorAndBlank`. Test each field's actual choice and document narrative/schema disagreement; do not globally turn missing/empty into false or globally permit invalid empty elements.
5. The earlier mapped-history columns in the migration workbook can conflict with its current definitions or the XSD, including allergy recorded-date precision. Use explicit versioned evidence and a reviewed resolution; do not silently reject current valid partial forms using an old mapping column.
6. The implementation guide calls the past-medication indicator `PastMedication`, but the actual supplied wire XSD declares `PastMedications` (main XSD line 388). Map the narrative concept to the actual plural XML element; do not rename it in the strict parser or generated bindings, and do not silently accept a schema-invalid singular alias without a separately identified vendor adapter.

The actual property table is CT-017 (`DR/ND/UK`), corroborated by the field-bound datatype XSD and CDS-S definition. 8. `Migration!G361` points ResidualInfo DataType to CT-024, whose actual table is Medication Frequency; XML primitive datatypes are CT-028. Cross-check field meaning, actual headings/values, guide and schema instead of mechanically following the stale number. ResidualInfo Name, DataType and Content are transported as `xs:token`; the XSD neither enumerates primitive types nor validates Content according to DataType. Preserve original type/content/category and apply reviewed profile-specific semantic checks. Until an affected discrepancy is resolved, keep the source and expose the precise review item. The final supported-profile claim must identify the interpretation and its passing assertions; a generic disclaimer cannot replace the decision.

## Malformed data and review workflow

Separate schema-invalid input, schema-valid but semantically conflicting data, valid but unsupported target representation, and safe lossless normalization. Do not repair malformed XML by dropping tags, replace unknown required fields with arbitrary defaults, truncate clinical text silently or disable schema validation to let a batch through.

Re-run validation and fingerprint the correction/ruleset. The original remains intact; no hidden edited copy becomes the apparent source.

An optional record's problem need not prevent importing independent valid patients. Within a patient, strict preflight holds unresolved required/clinical-risk data before mutation. No default option silently imports the good parts and discards the rest.

# Phase 4 Make durable writes and recovery correct

**Owner roles:** import implementer, database reviewer and independent recovery reviewer. **Outputs:** transaction inventory, source-to-target ledger, ownership fencing, journal, file lifecycle and reconciliation tools.

## Transaction ownership

1. Inventory every clinical write, direct JDBC call, JPA/Hibernate context, nested transaction, checksum, routing row, contact association, file operation and external side effect. Classify which transaction owns it. Include rollback behavior for exceptions that legacy code catches internally.
2. Define bounded durable units, preferably one source record and its dependent rows, or an explicitly bounded clinically cohesive group. A prescription and its precision/provenance cannot be split into unrelated successful units. Set unit size by measured memory/transaction-time behavior; do not turn the whole batch into one transaction.
3. Each clinical unit commits its source-record key, target row references, normalization/ruleset hash, audit event/outbox and checkpoint in **the same database transaction**. A checkpoint written after a separate commit leaves an unrecoverable crash gap. Row counts or matching clinical text are not adequate source-to-target provenance.
4. Refactor import-specific calls that independently commit into participating unit APIs. In particular, the CDS `FileUploadCheck` checksum/lab/routing path must participate correctly; retain existing non-import caller behavior unless deliberately changed and tested. Its checksum/content lock must remain effective through the enclosing unit's actual completion, or be replaced with proven database uniqueness/locking across all callers and nodes. Switching propagation must not release the content lock early. Adding an outer annotation while `REQUIRES_NEW` remains inside it is not acceptable proof.
   Preserve isolation as well as propagation: the existing lab path explicitly starts READ_COMMITTED for routing under MariaDB snapshot isolation. A participating inner template cannot change an existing outer transaction's isolation. The actual owner of a lab/routing unit must establish the required isolation before its first SQL, preserve report-lock ordering and avoid/reject incompatible pre-existing transactions. Verify concurrent routing and acknowledgement after the unit has already read data. Merely changing REQUIRES_NEW to REQUIRED is insufficient.
5. Flush before recording success and distinguish a known rollback, known commit and unknown commit acknowledgement. A lost connection after COMMIT may mean committed data. Recover by querying the atomic unit/source ledger after ownership is safely reacquired; never infer rollback from a client exception.
6. Persist required audit/outbox data atomically with the clinical unit. External audit delivery, indexing or integration can be retried independently with an idempotent event ID. If durable audit storage fails, the clinical unit must fail or remain explicitly unresolved according to the reviewed policy; do not silently drop audit. Use a failure-propagating audit API: legacy `LogAction.addLogSynchronous` catches persistence failure, while `addLogStrict` propagates it; verify the chosen implementation actually joins the unit. Inspect real upgraded table engines and transaction capabilities during runtime schema preflight rather than assuming all tables match fresh-install InnoDB baselines.

## Fencing and stale workers

1. Coordinate web and CLI jobs against the same database across processes/nodes. A local mutex, host `flock` or separate CLI pool does not serialize all writers.
2. Use a dedicated unreclaimable connection for any advisory import lock and repair #4548's pooled-connection lifetime. Also implement a database ownership epoch/token and row lock checked by every mutation unit inside that unit's transaction.
3. A unit obtains/checks the current epoch under a database lock before clinical writes and retains the required lock until commit. Ownership changes serialize through that same coordinator. A worker with an old token must fail before mutating or committing another unit.
4. A heartbeat timeout alone must not authorize takeover while an old transaction may still run. If its locks/connection cannot be shown released, stop and require reconciliation. Test network partitions, paused processes, expired connections and a delayed old worker resuming after a successor starts.
5. Avoid holding the ownership row in an outer transaction while a nested independent transaction attempts to lock it, creating self-deadlock. The reviewed transaction graph must show how each unit participates and how global/run/target lock ordering avoids deadlocks.
6. Lock loss stops starting units; in-flight outcomes are reconciled through atomic checkpoints and database ownership, not guessed from logs. Release/cleanup errors cannot rewrite known successful clinical commits as rolled back.

## Provenance and repeat identity

1. Add dedicated province-neutral import run, patient, unit, source-to-target and review/diagnostic structures through forward-only common Flyway migrations. Exact names and migration numbers are implementation choices to review. Allocate versions globally across common/ON/BC and active release lines; never edit published migrations.
2. Record run ID, source namespace/vendor identifiers, immutable package digest, XML and all referenced-attachment digests, source record identity/occurrence, target patient/rows, actor/provider, schema profile, ruleset, options, ownership epoch, stage timestamps and outcome. Use a stable source-record-to-target ledger across attempts, with a separate configuration/version conflict check.
   Source namespace is a stable approved vendor/instance provenance identity, selected from a server-side registry rather than an arbitrary free CLI string. A caller cannot choose a new namespace solely to bypass prior import protection. Namespace reassignment and cross-source collisions require explicit provenance review; retain destination/payload collision checks and prior lineage across that change.
4. Subsequent authorized clinical edits/deletions require an explicit reconciliation policy; never automatically restore, overwrite or duplicate them. Identical clinical values in distinct legitimate source records are not automatically duplicates. ## Files and side effects

1. Spool/validate/hash an attachment before committing a clinical reference. Use deterministic import-owned destinations and an idempotent staged-to-durable lifecycle. Account for rename across filesystem boundaries, fsync/durability requirements and document-directory permissions.
   Keep fresh attempt-owned spool files separate from retained/published destinations. 2. Either make a durable file available before the transaction references it, with a journaled orphan-cleanup path on rollback, or use a reviewed pending-reference mechanism whose readers cannot expose a missing file. A database commit and filesystem rename are not one transaction.

   Serialize orphan retirement with publication/adoption using a reviewed file-object lifecycle claim/lock or equivalent database protocol. A check for zero references followed by unlink is unsafe if another unit can adopt the object between them. Equal bytes may share physical storage under a reviewed ownership policy while preserving distinct patient/source occurrences and metadata. Do not impose global MD5 uniqueness or incidentally change normal upload responses.

Preserve legal combinations of inline and external content; use the specification's semantics or require review when conflicting. Do not silently choose one different payload or label non-PDF bytes as a PDF. Resolve only permitted local snapshot members; do not fetch a URL supplied in FilePath or execute imported HTML, scripts or templates.

# Error warning and completion reporting

## Disjoint patient outcomes

Use one versioned result contract across worker, browser, Java runner and Python/container wrappers. Proposed final patient outcomes are:

- `COMPLETE_WITH_NONLOSSY_WARNINGS`: all data is preserved correctly; warnings describe reviewed non-lossy transformations or operational information.
- `ALREADY_COMPLETE`: verified prior completed identical import; zero new clinical writes.
- `REFUSED`: policy/identity/permission prevented import before clinical writes.
- `FAILED_BEFORE_WRITE`: technical/input failure with no clinical commits.
- `CANCELLED_BEFORE_WRITE`: execution cancelled without clinical commits.
- `NOT_STARTED`: discovered and accounted for, but never executed because the selected batch policy, capacity pause or earlier failure stopped admission; include the exact reason and safe next action.
- `PARTIAL_COMMITTED`: exact committed units are known but other units/review items remain unresolved.
- `RECONCILIATION_REQUIRED`: outcome or provenance is uncertain, or clinical publication cannot safely proceed.

Warnings are attached facts, not an alternative outcome that can conceal missing data. Clinical completeness is separate from operational cleanup, diagnostic delivery and transport status. A staging deletion failure cannot undo a completed clinical unit or alone justify holding a clinically reconciled chart; release the clinical hold only after the required clinical/audit review, while keeping the unresolved operational failure visible. Run outcome is derived from patient outcomes, job state and reporting/cleanup status. The accounting invariant uses these disjoint patient categories; unstarted patients remain NOT_STARTED with their actual cause rather than being omitted or mislabeled as cancelled/refused. Unit/field accounting separately records normalized, preserved/unmapped, rejected, pending and committed values without double-counting. An incomplete discovery/parse inventory is explicitly unknown, never zero; distinguish source files, identified patients, source occurrences and synthetic target copies. A malformed unreadable source cannot be counted as fully inventoried just because some earlier records parsed.

## Diagnostic contract

Each diagnostic has a stable code, severity, run/patient/record ordinal, schema XPath or source location where available, stage, safe summary, clinical effect, whether writes occurred, retry/review action and protected detailed context. Separate validation errors, normalization notices, unresolved clinical mappings, identity refusal, transient infrastructure errors, unknown commit and cleanup/report-delivery failure.

General logs/stdout/stderr contain only safe run references, stages and counts. Keep patient names, HIN, DOB, clinical text, source filenames/paths, raw parser errors and credentials out. Protected reports can show authorized clinical context necessary for resolution, with the same access safeguards as the chart. Sanitize exception chains and SQL errors rather than logging PHI indirectly.

Stream full diagnostics to bounded durable storage; paginate the UI and clearly mark previews as limited. If a diagnostic cap is reached, retain complete counts and a reference to durable details, or fail safely if complete error evidence cannot be preserved. Do not silently discard the remainder or accumulate every warning in heap.

Every result view shows source totals, complete/no-op/refused/failed/partial/uncertain counts, outstanding review items, committed-stage evidence, normalization summary, cleanup status and next action. All-refused input must not show Imported Successfully. A generated log file or failed-to-write warning report cannot make the CLI return clean success.

Generate the actual protected ImportEventLog and Import Error Log files required by DP02.04/05, in addition to database checkpoints and UI/JSON. The event file uses source UniqueVendorIdSequence and per-category imported occurrences, including distinct Text/Binary report counts. The error file identifies every failed record for every affected patient. Retain complete file evidence through interruption/recovery; final generation reconciles committed checkpoints and file-write failures are visible delivery failures. General logs remain PHI-safe; the required patient identifiers belong in access-controlled result files, not ordinary stdout.

Generate immutable report files under unique attempt/manifest/report-generation paths, then select the authoritative report set through a fenced version/compare-and-set update after files are durably published. A stale projector must never overwrite a shared final filename or select stale counts after takeover. Run-ID downloads resolve the authoritative protected generation; old receipts remain explicitly historical. A crash between file creation and selection is a report-publication orphan to reconcile, not proof of clinical failure. Race two report generations and kill the publisher at both boundaries.

## Information delivered to the person running the import

The initiating authorized operator receives a visible run receipt immediately after durable acceptance: run/submission ID, source/profile and engine/ruleset references, effective options and dry-run/merge/synthetic mode, current stage and a persistent status/results location. Show safe source labels in the protected UI, not PHI-bearing file paths in general logs. Give progress and result access to the initiating operator and explicitly authorized delegates after reauthentication; revoked privileges do not retain historical PHI access merely because the user submitted a job. This is in-application/CLI reporting, not authorization for external email or messaging.

During execution, the UI and foreground CLI show timestamped stage changes, bytes/units processed, discovered/expected totals when known, actual committed units, per-outcome counts, warnings/review items and last durable checkpoint. Distinguish accepted, validated, planned, committed, clinically complete and report delivered. Use bounded paged/streamed event history with stable sequence IDs so reconnect can continue from the last event without duplicate rows or lost events. Do not log every byte/field or retain the whole history in browser/CLI memory. A live heartbeat, absence of errors or 100% bytes parsed does not mean clinical completion. Explain a stall, timeout, disconnection or stale status and show its next action.

Protected drill-down lets the operator inspect each source patient/target copy and category: expected source occurrences, actual newly committed occurrences, verified prior-complete no-ops, reviewed non-lossy transformations, unresolved/rejected/not-started items and exact diagnostic references. Preserve distinct original occurrences even where they share bytes. Imported occurrence counts in the required event file report what actually imported; planned/no-op/rejected counts have separate columns/sections and never inflate that count. Record target IDs and attachment byte/digest/reference checks in protected evidence, not only a human summary. A completed unit receipt is based on the atomic checkpoint; an audit event describing an attempt is not a commit receipt.

The terminal completion receipt includes: exact run/attempt and manifest version/digest; source/profile/ruleset/options identity; start/end and elapsed times; discovery completeness; disjoint source-patient and target-copy outcomes; per-category expected/committed/reused/pending/failed counts; outstanding clinical review; attachment/routing/contact/audit reconciliation; hold/publication state; warning/error code totals; and required ImportEventLog/ErrorLog file locations with generation/delivery/cleanup status. A protected machine-readable manifest accompanies human-readable reports so an operator can reconcile exact keys rather than trust totals. Name the supported retention and recovery/restore references. Never label the operation cleanly successful with NOT_STARTED, PARTIAL_COMMITTED, RECONCILIATION_REQUIRED, unresolved loss or required-report delivery failure.

Use an explicit completeness proof: discovery finished; every selected manifest occurrence/field has an accepted final disposition; expected and reconciled unit keysets match; dependent files/contacts/routing/audit agree; required clinical review is resolved; and clinical completion/hold release committed. Then separately establish required report delivery and operational cleanup. The final operator view must explain any difference between clinical completion and clean operational completion. Aggregate accounting is derived from these durable facts, not independently incremented action/CLI counters. If patient identity cannot be parsed, account for the failed source file and unknown patient inventory explicitly.

Logging/receipt fixtures L01–L09 cover clean success, non-lossy warnings, verified no-op, all-refused, mixed outcomes, never-started work, partial commit, unknown commit, and successful clinical completion with failed report delivery/cleanup. Assert every browser/CLI summary and downloaded file matches the same manifest/checkpoints, malformed source inventory remains unknown, protected drill-down identifies each failed occurrence, and reconnect after restart preserves the event sequence. Inject unwritable result storage, a broken stdout pipe and unavailable DB; require visible delivery/unavailable state and later durable recovery without new clinical writes. Include sentinel tests for PHI in ordinary logs and unauthorized report access.

## CLI contract

Preserve #3979's basic documented exit range for the first release unless the protocol review deliberately versions an extension: `0` means clean completion/explicit verified no-op or valid dry run; `1` invalid arguments; `2` configuration/runtime failure; `3` authorization failure; `4` failed, refused, busy, partial, unresolved or incomplete operation. Distinguish these cases in the structured result. A signal-interrupted process may use conventional `130`; its durable result still records committed/uncertain units. Document and test wrapper signal propagation.

A nonzero exit may coexist with committed clinical data. Automation must inspect the run result and resume/reconcile through the supported command, not resubmit the input automatically. Failure writing stdout or downloading the report changes delivery status without falsifying whether clinical units committed. Durable results remain retrievable by the run ID.

Required audit, cleanup and result-delivery failures preserve the primary error and actual commit outcome. A cleanup exception must not hide the validation/DB cause. A committed import with unresolved cleanup is not a clean final operation; recovery must be specific about what can be deleted and what is already in the chart.
