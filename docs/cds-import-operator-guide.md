# CDS import operator guide — release/2026.08

Use the existing **Administration → Data Management → Demographic Import** page or the paired `carlos-ctl cds-import` command. Both call the same CARLOS import engine. This work implements import. Export tickets #3973, #3946, #3959 and #3968 remain separate; #3979 is the main import feature reference.

Read the [web workflow](cds-import-web.md), [clinical normalization contract](cds-clinical-import-contract.md), [maintenance admission procedure](cds-maintenance-admission.md), [legacy projection safeguards](cds-legacy-projection-contract.md) and [durable ledger contract](cds-import-ledger.md) before enabling a deployment.

## Prepare the deployment and transfer

1. Install the complete candidate application and forward Flyway migrations using the normal CARLOS deployment procedure. Keep `cds.import.enabled=false` during installation. Stop or drain every old application node, background clinical task, integration/feed and external writer before the migration window. The physical datasource barrier covers participating guarded connections; arbitrary external database clients and already copied clinical information require operational controls.
2. Back up the database, configured document store, upload store and entire durable CDS state together. Verify a restore on a disposable instance. Imported source fields can reference durable spools, and documents can be adopted across verified runs. Deleting a run directory or restoring only the database breaks that evidence.
3. Use the same frozen application classes, dependencies, Java 25 runtime and timezone data for browser and CLI operation. Their implementation fingerprint and effective normalization policy are durable provenance. A changed implementation or policy refuses unsafe execution/resume; retain the matching candidate for recovery. Never edit recorded hashes to force compatibility.
4. Configure the private, absolute source, staging and upload roots, explicit source namespace/profile registration, clinical timezone and operator/provider delegation. The instance JVM calendar must agree with `cds.import.clinicalZone`; the web import refuses a mismatch. The one-shot CLI establishes its trusted configured timezone before application boot. Authorized web status remains available for diagnosing execution incompatibility. CLI recovery still requires the original source registration and applicable delegation; retain these during recovery.
5. A web importer requires live `_admin` write or explicitly granted `_cds_import` write capability, as well as its provider/patient scope. Migration `V1.0.59.21` registers `_cds_import` without granting it to roles. Ordinary clinical source-field readers require their own category and patient access. CLI operation requires an independently verified, expiring root-owned OS-operator delegation and the configured provider scope.
6. CARLOS loads root-owned import configuration for each application context. Configuration edits require a controlled context/process restart. Database account, provider, role, facility/program and patient restrictions are rechecked at execution boundaries. Use the supported cancellation action for an active run; changing a properties file alone does not cancel a running JVM.
7. Enable the datasource maintenance guard and follow the documented drain/activation procedure. `maintenanceMode` is explicit admission, not evidence that unguarded old software or external clients have stopped. The worker verifies physical ownership, native transactional engines, trigger visibility/approval and the actual target catalogue before writing. Keep normal clinical access closed while any chart remains held or reconciliation is incomplete.

Receive the original package, ReadMe/instructions, source audit material and ExportEventLog through the clinic's approved secure transfer process. Preserve their original names, hashes and chain of custody. Keep passwords and decryption keys outside the patient package and command arguments. The importer accepts unencrypted XML/ZIP inputs; decrypt an encrypted delivery in a private directory with the approved local tool, entering the passphrase through its protected prompt/key mechanism. Verify the decrypted archive and its vendor manifest, then import its unmodified relative directory layout. Retain both original encrypted delivery and the approved decrypted evidence according to clinic policy. Do not upload an encrypted archive and interpret refusal as a completed migration.

The registered profiles are `pcon-2024-02` and `omd-5.2`. The supplied PCON and 5.2 schema pairs have identical bytes; namespace or XSD hash cannot infer the applicable narrative profile. Registration records the agreed source contract. The uploaded specification bundle provenance and normative crosswalk are in the [implementation plan](cds-import-implementation-plan.md).

## Submit and verify a rehearsal

The browser accepts XML or ZIP and transfers bounded, hashed chunks with resumable offsets. A batch with attachments should be one ZIP containing the patient XMLs and their permitted relative references. The host command additionally accepts an approved directory. Patient XML discovery uses bounded content detection and accepts the official suffix-free naming convention; XML-looking members whose root cannot be classified within the discovery budget remain explicit candidates for full validation. A bare XML includes only its referenced adjacent attachments. ZIP path traversal, links, collisions, CRC failures, excessive expansion and unsupported archive forms are explicit refusals. Ancillary audit/readme files remain in the immutable accepted snapshot.

Perform a dry run with the intended source contract, provider, facility/program, identity/merge options and synthetic policy. Existing-chart merge is off by default. Read all schema, identity and native-constraint diagnostics. Review the complete discovered XML/file/byte inventory separately from patient occurrences; an unreadable XML cannot justify a fabricated patient count.

A dry run seals a plan and writes no clinical records. Its receipt explicitly distinguishes `DRY_RUN_COMPLETE` from clinical completion. Executing the same browser upload uses its separate execute acceptance identity. A repeated acceptance with the same submission and immutable options recovers its existing run; changing options is a new reviewed submission.

Reconcile source charts side by side, including every category and every choice supplied by the source. Inspect the complete original and normalized logical fields in their corresponding native module's **CDS source fields** view. Previews are explicitly bounded, and authorized original-value downloads retain the complete source. Native overflow markers are reconciliation notices, not excerpts presented as full clinical statements.

Check in particular:

- Patient identity, authority-qualified health numbers, DOB, exact name and active/merged-chart restrictions. Same health number under different known authorities is distinct; unknown/conflicting authorities cannot be resolved by guessing from a name.
- Medication currentness, strength/dose, prescribing authority, substitution, private notes and source author; source history does not authorize a new prescription. Incomplete projections are barred from renewal.
- Immunization refusal and unknown/year/month/full-date timing. A partial storage anchor must never be read as an exact January1 event. Supplied exact January1 remains exact.
- Unknown source note timestamps/authors, date-only notes, repeated contacts and nullable consent, care units, performed examinations and full goals.
- Report bytes and media/encoding warnings; both supplied representations and discrete observations. Source review metadata never creates a new local acknowledgement/signature.
- Laboratory flags/status, fractional/offset timestamps, original comments and blocked results. Source-blocked results require the separate sensitivity privilege and stay out of unrestricted legacy mirrors.
- Category-local residual/vendor fields, annotations and source-only overlength values. Legacy complete exports/APIs that cannot represent imported meaning refuse explicitly; consult the finite consumer inventory before enabling custom integrations.

## Completion, reports and recovery

Keep the run ID. A successful upload, HTTP202, printed acceptance, heartbeat or shell exit alone does not establish clinical completion. The status shows clinical state, discovery/seal state, committed/prior/pending units, per-patient outcomes, report delivery, cleanup and terminality separately. Read the complete protected **ImportEventLog**, **ImportErrorLog**, unit receipts and completion receipt. The seventeen event buckets distinguish Text/Binary Reports; helper source-field/contact/care units do not inflate source occurrence totals.

Every failed/review-required occurrence carries its source patient/copy, category, indexed source path where known, stable diagnostic code and proven outcome. Bounded operational failure evidence contains exception types, SQLState/vendor codes and limited class/method frames, with no exception messages, SQL text, credentials or patient values. Evidence/report delivery failures are visible operational failures and cannot rewrite a committed clinical outcome into rollback or success.

Use the existing run's supported **Resume** after correcting a transient operational problem. The engine verifies the sealed expected work, current authorization, row receipts, immutable file hashes and exact checkpoints. It skips only proven committed units. A lost commit acknowledgement requires reconciliation; blind whole-patient retry is unsafe. A changed existing chart or missing/corrupt referenced file is an explicit reconciliation conflict, never permission to overwrite it.

**Cancel** is durable and cooperative at bounded work boundaries. It preserves committed units and their evidence. Closing the browser or losing the foreground command does not undo committed data. A failed/partial patient remains held until supported recovery proves its complete workset; do not clear holds manually.

Corrections require the exact indexed field, original source identity, proposed logical value, clinical reason and current review version. Original XML/spools remain unchanged. A multi-error draft remains inactive until the combined corrected XML validates against the whole pinned schema and native preflight. Acknowledging a warning cannot remove a blocker. A decline remains a visible incomplete/refused disposition.

When a source or effective policy changed after an actual zero-write failure, submit the revised immutable input/options and use the explicit **Approve unwritten revision** review. Both revisions must have no clinical target, checkpoint, hold or uncertain commit, checked under the same durable locks. Old provenance and plans remain retained. Any evidence of clinical writes requires recovery of the original run; changing the source namespace or deleting ledger rows is not a supported workaround.

If an implementation update prevents an old zero-write attempt from resuming, cancel that attempt through the supported control and retain its run ID and evidence. Explicitly upload the original immutable package again under the same source namespace to create a new upload and acceptance on the current implementation, then review its **Approve unwritten revision** conflict. An upload already bound to an actual run does not become a new execution identity. Historical verification preserves the old acceptance, ruleset and cancellation, and checks its retained snapshot and, for web sources, the complete original chunk receipts. The source receipt digest and snapshot digest remain separate evidence. Cancellation alone does not prove that maintenance reopened: keep the retained window closed until a subsequent successful owner proves completion, zero holds and a verified maintenance release.

Report or cleanup failure can be retried independently without repeating clinical writes. `cleanup COMPLETE` means the bounded ownership/reconciliation checks succeeded; accepted source, parse evidence, corrections and prior reports remain intentionally retained. Automatic housekeeping removes only proven unaccepted/owned temporary artifacts. Unknown ownership and uncertain acceptance are retained with an administrative alert. Do not use filesystem globs to purge accepted or shared run files.

The engine releases its clinical maintenance barrier only after proving clinical completion and zero outstanding holds. This release precedes report delivery; a later report failure does not re-hold completed charts. `RELEASE_PENDING`, `RELEASE_DEFERRED` or a release-reconciliation diagnostic prevents a clean operational outcome. Use the completed run's supported **Resume** to retry release proof and delivery without repeating clinical writes.

Before declaring the migration operationally complete or lifting separate clinic downtime controls, verify every expected patient/copy and occurrence, required report delivery, cleanup disposition, release proof, zero unresolved holds and the maintenance procedure's downstream/backlog policy. Archive the receipt and reconcile with the source migration team. Retain evidence and backups according to clinic policy; this feature introduces no automatic patient-source purge policy.

## Resources, support and verification

The upload size, archive expansion, entry count, XML depth/symbols, scalar/binary capacities, free-disk reserve and duration have explicit deployment limits. Parsing, base64, file publication, diagnostics and reports stream with bounded buffers. Native field pages and prepared DTOs have fixed bounds; increasing heap does not replace these limits. Allow disk/inodes for original snapshot, bounded spools, document publication, retained review/report generations and backups. Use measured workload admission before a large production migration.

The CARLOS project does not set a clinic's migration service cost or promise vendor support terms. Agree with the source vendor and migration operator on extraction/decryption, source correction, side-by-side clinical validation, downtime, reconciliation, retention and support ownership before the window. Supply support with the run ID, stable diagnostic code and protected evidence through an approved channel; ordinary chat/email logs should not contain source patient data or credentials.

The required [native CI tier](../scripts/ci/run-cds-native-tier.py) creates its own isolated MariaDB, applies the complete Ontario Flyway chain to fresh databases, and fails when any required physical database suite is absent, skipped or unsuccessful. It never reuses a supplied clinical database. See [CDS import native contracts](../.github/workflows/cds-import-native.yml), the [browser harness](../scripts/demographic-cds-import-playwright-checks.js), [installed CLI gate](cds-import-cli-verification.md) and the companion repositories' launcher gates. The complete wire fixture is [cds-import-all-categories.xml](../src/test/resources/demographic/cds-import-all-categories.xml). Subsystem tests and schema validation are evidence for their stated boundaries; they do not constitute an OntarioMD certification claim.
