# eForm chrome styling: scoped Bootstrap

**Issue:** [#3944](https://github.com/carlos-emr/carlos/issues/3944) · **Applies to:**
`efmshowform_data.jsp`, `efmformadd_data.jsp`, `EFormRenderPdfHtmlComposer`

## The rule

An eForm page is a clinic-authored document. CARLOS adds its own chrome to it (the floating
toolbar, the save alert and the attachment picker), but **nothing CARLOS adds may restyle the eForm
itself**. Do not add a global stylesheet (the plain `bootstrap.min.css` or any other stylesheet whose
selectors match bare elements or common class names) to an eForm page or to the PDF render surface.

## Why

Most eForms are legacy HTML from the OSCAR Galaxy corpus. They were written for browser defaults
and place fields absolutely over a scanned page. Until 2026.08 both renderers added the full
Bootstrap 5 stylesheet with media `all`, and the server-side PDF renderer did the same. Bootstrap's
reboot changed the form underneath the toolbar, on screen and in every printed, faxed or saved PDF:

| Rule | Effect on a legacy eForm |
|---|---|
| `body { margin: 0; font-family: system-ui…; line-height: 1.5 }` | All flow content moves 8px up and left; text changes font and grows 24px lines. |
| `*, ::before, ::after { box-sizing: border-box }` | Inputs with a set width and padding shrink. |
| `h1`–`h6`, `p`, `table`, `label` margins and sizes | Headings shrink and lose margins; tables collapse borders. |
| Component classes (`.table`, `.row`, `.container`, `.small`, `.lead`) | A form that happens to use one of these names becomes a flex row, a full-width bordered table, a centred column and so on. |

The same cascade also hid the save alert: the plain stylesheet loaded after `oscar_alert.css`, so
Bootstrap's `.alert { position: relative }` beat `.oscar-alert { position: fixed }` and the alert sat
at the very end of the page, under the toolbar and usually below the fold.

OSCAR avoided this with a scoped Bootstrap 3 build for its toolbar
(`eform_floating_toolbar_bootstrap_custom.min.css`); the scoping was lost when the toolbar moved to
plain Bootstrap 5.

## How it works now

- `src/main/webapp/eform/eformFloatingToolbar/bootstrap-eform-scoped.min.css` is the vendored
  `library/bootstrap/5.3.8/css/bootstrap.min.css` with every rule confined to elements inside
  `.carlos-eform-ui`. `:root`, `html` and `body` selectors are rewritten onto the scope element, so
  Bootstrap's custom properties and base font land on the scope and are inherited by its contents.
  It is generated by `scripts/build-eform-scoped-bootstrap.js` with the dependency-free transform in
  `scripts/lib/css-scope.js`, and committed so the WAR build needs no Node step.
- Both renderers add the scoped copy instead of the plain stylesheet, and load
  `bootstrap.bundle.min.js` exactly once (`efmshowform_data.jsp` used to load it twice, which
  registers Bootstrap's data-api handlers twice: a `data-bs-toggle` collapse or dropdown in a form
  opened and immediately closed).
- The scope class is carried by plain containers, never by an element that needs a Bootstrap class
  itself:
  - `#toolbarWrapper`, created by `eform_floating_toolbar.js` around the toolbar fragment;
  - `#carlosEformDialogHost`, the `display: contents` element at the end of `<body>` that
    `eformDialogHost()` creates and the toolbar's jQuery UI dialogs are appended to (`appendTo`).
    The attachment picker hides rows with `.d-none`, so it needs the scope; with the scope above the
    dialog, where `<body>` was, the dialog keeps its jQuery UI font and colours;
  - the `.oscar-alert-host` element `oscar-alert.js` mounts each alert in. It is `display: contents`,
    because a box there would count as page content when the toolbar measures where the form ends.
- The PDF render surface (`EFormRenderPdfHtmlComposer.applyRendererViewProfile`) loads no Bootstrap
  CSS at all: the toolbar, alert and picker are not part of a PDF, and the PDF must match the screen.
  The Bootstrap script bundle stays in both places for form code that calls it.

An eForm that wants Bootstrap for its own content can still link it itself
(`../library/bootstrap/5.3.8/css/bootstrap.min.css`); the renderers no longer supply it implicitly.

## Changing it

- **Bootstrap upgrade:** point `SOURCE` in `scripts/build-eform-scoped-bootstrap.js` at the new
  vendored file, run `node scripts/build-eform-scoped-bootstrap.js`, and commit the result. The
  transform refuses CSS it cannot scope safely (nested rules, a selector that starts with a
  combinator, an at-rule such as `@import` or `@page`) instead of emitting a rule that escapes the
  scope.
- **New chrome on the eForm page:** put it inside an element with `class="carlos-eform-ui"`. If a
  library moves it elsewhere in the document (as jQuery UI does with dialogs), give the moved
  element the class itself.
- **Never** edit the generated file by hand; `scripts/eform-bootstrap-scope.test.js` fails when it
  differs from the generator's output.

## Tests

| Test | What it pins |
|---|---|
| `scripts/eform-bootstrap-scope.test.js` (`npm run test:scripts`) | The transform; the committed file matches the generator and every selector in it is scoped; neither renderer nor the PDF composer adds a Bootstrap stylesheet; one Bootstrap bundle per renderer; the scope on the toolbar wrapper and the dialog host; the alert helpers work whatever `this` is. |
| `scripts/eform-bootstrap-isolation-playwright-checks.js` (standalone tier, no Tomcat) | Builds each renderer's page from its JSP asset calls and asserts that a legacy eForm's boxes and computed styles equal the bare form's on screen and in print, that the toolbar, alert and picker are still styled by Bootstrap, and that the alert floats in view. |
| `scripts/eform-bootstrap-print-fidelity-playwright-checks.js` (core tier, installed app) | Imports a legacy eForm into a running CARLOS, opens it through the real renderer, compares it with the bare form, and checks the downloaded PDF's text positions against the screen. |
