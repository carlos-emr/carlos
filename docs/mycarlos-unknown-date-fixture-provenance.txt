Unknown-service-date interoperability fixtures

The manual test entry point is:
io.github.carlos_emr.carlos.integration.patientportal.PortalMyCarlosUnknownDateFixtureExport

It reads only the public FAKE delivery-contract.json and signed-PDF test
resources on the test classpath. It accepts a new output directory and either
canonical or legacy. It has no server, native-vault, approval or credential
arguments and performs no network or custody operation. Existing output
directories are refused. Only the generated package.json is intended for a
new native fixture; the temporary public-FAKE PKCS12 is removed after use.

From a CARLOS checkout using JDK25, on Unix:

  mvn -DskipTests compile dependency:build-classpath -DincludeScope=test -Dmdep.outputFile=target/mycarlos-fixture-classpath.txt
  umask 077
  CARLOS_FIXTURE_CP="target/classes:$(cat target/mycarlos-fixture-classpath.txt)"
  mkdir -p target/test-classes
  javac -J-Xmx256m -J-XX:ActiveProcessorCount=2 -proc:none --release 25 -cp "$CARLOS_FIXTURE_CP" -d target/test-classes src/test/java/io/github/carlos_emr/carlos/test/util/PdfSigningTestSupport.java src/test/java/io/github/carlos_emr/carlos/integration/patientportal/PortalMyCarlosUnknownDateFixtureExport.java
  java -Xmx256m -XX:ActiveProcessorCount=2 -cp "target/test-classes:src/test/resources:$CARLOS_FIXTURE_CP" io.github.carlos_emr.carlos.integration.patientportal.PortalMyCarlosUnknownDateFixtureExport target/FAKE-unknown-date-canonical canonical
  java -Xmx256m -XX:ActiveProcessorCount=2 -cp "target/test-classes:src/test/resources:$CARLOS_FIXTURE_CP" io.github.carlos_emr.carlos.integration.patientportal.PortalMyCarlosUnknownDateFixtureExport target/FAKE-unknown-date-legacy legacy

Use the workspace's build/resource wrapper when required by its instructions.
On Windows use the platform classpath separator, semicolon, and the shell's
equivalent for reading the generated dependency-classpath file. The Java entry
point, resources, arguments and generated packet format are the same.

The signing identity is deliberately public FAKE test material: SHA256 of the
shared keys.clinic_a.seed_text, interpreted as a positive integer modulo
(P256 order minus1), plus1. Its public key is the shared fixture SPKI. The
exporter requires the exact shared FAKE seed label. Recipient, device and
receiver data come from that same public fixture. It never reads deployed
private signing keys or actual native vault keys.

The actual pipeline is DocumentManifest -> PDFSigningUtil.signPDF ->
PortalMyCarlosSignedOriginal.verify -> ApplicationService.deliveryDocument ->
PDFSigningUtil.signMyCarlosPayload -> Composer.composeWithSigner. This checks
the CMS signature, pinned SPKI and exact embedded manifest before exporting the
real HPKE upload. Canonical mode embeds service_date:null in the PDF; legacy
mode embeds service_date:"". Both delivery manifests contain service_date:"".
Known dates, labels, signatures, hashes and patient/device bindings retain the
production validation. Native tests separately exercise strict date pairing,
the actual PDF helper, custody, receipts, reopening and backup.
