# REST prescription failure and recovery

`POST /rx/prescribe?demographicNo=...` retains its existing response shape. The prescription header, earlier medication replacements and source-medication archive changes now share the manager's transaction. Every input and stored source must belong to the prescription patient. A mixed-patient batch is refused before the header is created.

A successful response includes the prescription and medication IDs after the manager transaction has committed. Existing validation refusals retain `success: false`. A null write result after writes have begun throws `PrescriptionWriteException` across the transaction proxy; only after rollback does the resource translate it to the legacy failed response. This is distinct from a normal return that could commit earlier writes.

Unexpected storage/commit exceptions propagate through the normal safe REST error boundary. They are not converted to `success: false` or an empty successful prescription. A 5xx response, timeout, disconnected response, or response-conversion failure can mean the outcome is unknown. A commit acknowledgement can be lost after the database commits; even an attempted rollback cannot undo that committed work. Exception class alone cannot tell a remote client whether the write exists.

Do not automatically retry an uncertain prescription save. The legacy operation has no durable idempotency key, and retrying may create a second prescription and medication set. Retain the patient, provider, submission time and submitted medication details for reconciliation. An authorized caller can inspect `GET /rx/prescriptions?demographicNo=...` and the patient's current medication/history views. Compare the returned prescription/medication IDs and contents before deciding whether another write is necessary. If concurrent or similar prescriptions make the outcome ambiguous, require clinical reconciliation; absence in an incomplete/stale list is not proof of rollback. Never reconcile through logs containing clinical text or by granting another patient's access.

Known validation/authorization refusal permits correction of that request; a confirmed rolled-back write can be submitted as a new attempt. Rebuild the transfer objects from fresh chart data rather than reusing mutable in-process objects from the failed transaction. Do not advertise exactly-once delivery or infer idempotency from transaction atomicity.

Native qualification uses the actual Rx manager transaction annotations and production prescription/medication DAOs on generated, Ontario and BC MariaDB schemas. The legacy prescription text-header renderer and audit sink are isolated in these transaction fixtures and retain their separate tests. The cases check successful commit, rollback of a header/replacement/source archive after a late write refusal, and independently injected acknowledgement failures before and after the physical JDBC commit. The two commit-failure cases deliberately have the same outward exception while observing opposite durable outcomes. The manager never retries the non-idempotent write automatically.
