## Findings
No new release-introduced wire or stored-format defect beyond those already filed or raised by slice reviewers. Every breaking or silent-risk row in the table below points to the known issue or slice finding that covers it.

The cross-slice checks that turned up nothing new:
- **REST JSON is independent of the MOXy→Glassfish switch.** Jackson is the JSON provider on both refs, and neither ref uses Jettison or MOXy JSON. Of the new adapters, only the two temporal carriers reach JSON, and their JSON is unchanged (probe).
- **No production code persists JAXB XML.** The new package-level adapters therefore cannot change stored data; the only marshal site is the hidden MIDDLEWARE fax relay.
- **Stored JSON keys are unchanged** (CDS snapshot manifests, BPMH lists).
- **Base64 encoders are byte-identical**, and every legacy (lenient) decoder is retained.
- **No property key, Spring placeholder, web.xml parameter or request-parameter name** was renamed or removed. The only removed-key hits were commented-out tickler/waitlist mail code.

The pre-existing format defects found while comparing these paths are listed under **Pre-existing issues** (C2-P1 to C2-P4).

## Pre-existing issues
### C2-P1: REST prevention responses always report `refused`, `ineligible`, `never` and `deleted` as false; the SOAP service reports them correctly
- Severity: Medium
- Category: data-integrity
- Confidence: Confirmed (code-traced; JSON shape confirmed by probe)
- Commit: none (pre-existing)
- Pre-existing: yes (present on origin/main)
- Location (identical on main and release head):
  - `src/main/java/io/github/carlos_emr/carlos/webserv/rest/conversion/PreventionConverter.java:53-67`
  - `src/main/java/io/github/carlos_emr/carlos/webserv/rest/to/model/PreventionTo1.java:42,50-52,168-170`
  - `src/main/java/io/github/carlos_emr/carlos/webserv/rest/PreventionService.java:76-110`
  - `src/main/java/io/github/carlos_emr/carlos/commn/dao/PreventionDaoImpl.java:231-234`
  - Compare `src/main/java/io/github/carlos_emr/carlos/webserv/transfer_objects/PreventionTransfer.java:175-186` (main `:176-187`).
- Problem:
  - `getAsTransferObject` copies only id, demographic, date (and precision info), provider, type, next date and creator.
  - `PreventionTo1` keeps `char deleted/refused/never` at `'\0'`, `lastUpdateDate` at null and `creationDate = new Date()`.
  - Every REST prevention therefore serializes as `"deleted":false,"refused":false,"never":false,"ineligible":false,"deletedRawValue":"\u0000","lastUpdateDate":null` and `"creationDate":<time of the request>`.
  - The data set is `findUniqueByDemographicId`: the latest row per type with `p1.deleted='0'` and no refusal filter. A patient whose latest Flu record is refused (`refused='1'`) or ineligible (`'2'`) is reported as an ordinary prevention.
  - The SOAP `PreventionTransfer.toTransfer` copies deleted, refused, never, creation date and last-update date, so the same record reads differently on SOAP and REST.
- Evidence:
  - Probe JSON (identical on both refs): `{"id":null,…,"creationDate":1794174757342,"preventionDate":1784122200123,"preventionDateInfo":{…},…,"deleted":false,"refused":false,"never":false,"nextDate":null,"creatorProviderNo":null,"lastUpdateDate":null,"ineligible":false,"deletedRawValue":"\u0000"}`.
  - The converter has no `setRefused`/`setIneligible`/`setNever`/`setDeleted` call.
- Impact:
  - REST clients (`/ws/rs/preventions/active`, `/immunizations/{demographicNo}`, their `/precision` variants, and the OAuth `/ws/services` copies), such as patient-facing apps or integrations, show refused or ineligible immunizations as given.
  - Last-modified and creation times are unusable.
  - The JSON carries a NUL character.
  - Nothing in the tree consumes these endpoints, so nobody notices.
- Correction:
  - Copy `isRefused()`, `isIneligible()`, `isNever()`, `isDeleted()`, `getCreationDate()` and `getLastUpdateDate()` from the entity; consider exposing completed-externally (`'3'`).
  - Drop or fix `deletedRawValue`.
  - Add a converter unit test with refused and ineligible rows, and announce the corrected values to API clients.

### C2-P2: Specialist street-address components are written in one comma format and read by two parsers that disagree; editing a specialist contact rewrites the stored address with wrong fields
- Severity: Medium
- Category: data-integrity
- Confidence: Confirmed (code-traced; browser default-option behaviour inferred)
- Commit: none (pre-existing)
- Pre-existing: yes (present on origin/main)
- Location (same lines on main and release head):
  - writer: `src/main/java/io/github/carlos_emr/carlos/utility/DemographicContactCreator.java:286-336`
  - parser A: `DemographicContactCreator.java:205-227`
  - parser B: `src/main/java/io/github/carlos_emr/carlos/commn/web/Contact2Action.java:1149-1165`
  - edit prefill `Contact2Action.java:559`, save `Contact2Action.java:779-783`
  - form `src/main/webapp/WEB-INF/jsp/demographic/addEditProfessionalContact.jsp:309-333`
  - other writers: `EctConAddSpecialist2Action.java:176` (free text), `PhsStarHandler.java:696` (newline-separated)
- Problem:
  - The writer stores `address addr2, city, postal, province, country, `.
  - **Parser A** (patient contacts, REST demographic contacts, and the edit prefill):
    - 4+ parts → city=[1], postal=[2], province=[3]. Its `else if (length > 4)` branch is unreachable, so country is never read.
    - 3 parts → province=[1], country=[2].
    - 2 parts → province=[1], so a city becomes the province.
  - **Parser B** (`Contact2Action.fillContactNames`, used by `displayHealthCareTeam.jsp:64`, `manageHealthCareTeam.jsp:71`, `edit-view.jsp:403`): 4+ parts → province=[2] (actually the postal code) and country=[3] (actually the province).
  - Addresses typed in the specialist admin screen (`123 Main St, Toronto, ON M5V 1A1`) give province `Toronto` and country `ON M5V 1A1`.
  - The edit form's province `<select>` has no option matching `Toronto`, so the browser submits its first option (`AB`).
- Evidence: the writer's own 6-part value `a, Toronto, M5V 1A1, ON, CA, ` is read by A as city/postal/province with country dropped, and by B as province=`M5V 1A1`, country=`ON`. Saving the edit form then stores `123 Main St, , , AB, ON M5V 1A1, ` for the admin-entered example.
- Impact:
  - Health-care-team views show wrong province/postal/country.
  - Any edit-save of a specialist contact silently loses the country and can move the city into the province or replace the province with `AB`.
  - Referral and consult documents that print `streetAddress` then show the mangled address.
- Correction:
  - Use one parser shared with the writer, mapping index → field exactly as written; remove the unreachable branch.
  - Keep the original free-text address unless the user edited the components, or store components in separate columns.
  - Make the province select keep an unknown value instead of defaulting to the first option.

### C2-P3: On the OAuth REST API, an unannotated date-only field dated 1970-01-01 serializes as the time "00:00:00", and the same field's JSON type differs between `/ws/rs` and `/ws/services`
- Severity: Low
- Category: bug
- Confidence: Confirmed (probe)
- Commit: none (pre-existing)
- Pre-existing: yes (present on origin/main)
- Location:
  - `src/main/java/io/github/carlos_emr/carlos/webserv/rest/util/SmartDateSerializer.java:77-82` (same lines on main)
  - `src/main/resources/applicationContextREST.xml:57,84-92` (module registered only on the OAuth mapper)
  - `src/main/java/io/github/carlos_emr/carlos/webserv/rest/to/model/DemographicTo1.java:53,64,68,70,74-76`: `patientStatusDate`, `dateJoined`, `hcRenewDate`, `endDate`, `effDate`, `rosterDate`, `rosterTerminationDate` have no `@JsonFormat` or `DateOnlySerializer`. Only DOB is protected (`:205`).
- Problem:
  - `SmartDateSerializer` treats any Date on 1970-01-01 (local) as time-only and any local-midnight Date as a date string. Every other Date becomes an epoch number.
  - The session mapper (`/ws/rs`) always writes epoch numbers.
- Evidence: probe with `DemographicTo1`'s fields: `/ws/rs {"effDate":18000000,"hcRenewDate":1806465600000,"rosterDate":1784122200000}` versus `/ws/services {"effDate":"00:00:00","hcRenewDate":"2027-03-31","rosterDate":1784122200000}`.
- Impact:
  - OAuth clients see a time where a date was expected for epoch-day values (a common placeholder in imported data).
  - Clients sharing one parser across both APIs receive numbers on one and strings on the other.
- Correction: apply `DateOnlySerializer` (as for DOB) to every date-only field in the REST TOs, or make `SmartDateSerializer` decide by declared field type rather than by value.

### C2-P4: REST schedule date path parameters are parsed leniently; invalid or date-time values silently select another day with HTTP 200
- Severity: Low
- Category: silent-failure
- Confidence: Confirmed (probe of the exact construction)
- Commit: none (pre-existing; deliberately preserved by 1c411c36 #5494)
- Pre-existing: yes (present on origin/main)
- Location:
  - `src/main/java/io/github/carlos_emr/carlos/utility/IsoDates.java:39-41`
  - callers `webserv/rest/ScheduleService.java:158` (`/schedule/day/{date}`, `/{providerNo}/day/{date}`), `:516-517` (`fetchDays`), `:680-681` (`fetchProviderAppts`), `managers/ScheduleManagerImpl.java:392-393` (`fetchProvidersApptsCount`)
  - main: Ant `DateUtils.parseIso8601Date` at `ScheduleService.java:155,519-520,679-680`
- Problem: a fresh lenient `SimpleDateFormat("yyyy-MM-dd").parse` rolls invalid days and months over and ignores trailing text, including a `T…Z` time and zone.
- Evidence: `2026-02-30 → 2026-03-02`, `2026-13-01 → 2027-01-01`, `2026-07-15junk → 2026-07-15`, `2026-07-15T23:59:00Z → 2026-07-15` (zone ignored).
- Impact:
  - A client typo or a JavaScript `toISOString()` value returns another day's appointments, or the next day's for an evening UTC timestamp, with HTTP 200.
  - The surrounding `catch → 400 "Path parameter has the wrong format"` only fires for unparseable prefixes.
- Correction: parse with `LocalDate.parse` under `ResolverStyle.STRICT`, return 400 for anything else, and document the change for REST clients. Keep the lenient helper only where a compatibility decision requires it.
