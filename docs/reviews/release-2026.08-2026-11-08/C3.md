## Findings

### C3-1: Measurement and lab graph images now compete for the eForm renderer's two browser slots, and fail as unexplained 503 broken images
- Severity: Medium
- Category: regression
- Confidence: Confirmed (code); Plausible (how often it happens under load)
- Commit: 5f9ca145 (#5518)
- Location:
  - `src/main/java/io/github/carlos_emr/carlos/eform/util/BrowserChartRenderer.java:30,35,57-67`
  - `src/main/java/io/github/carlos_emr/carlos/eform/util/EFormBrowserPdfService.java:190-193,947-956`
  - `src/main/java/io/github/carlos_emr/carlos/encounter/oscarMeasurements/pageUtil/MeasurementGraphAction22Action.java:127-142`
  - `.../ScatterPlotChartServlet.java:111-117`
  - consumers: `src/main/webapp/WEB-INF/jsp/lab/CA/ON/labValuesGraph.jsp:212`, `src/main/webapp/WEB-INF/jsp/rx/chartDrugProfile.jsp:157`, `encounter/oscarMeasurements/DisplayHistory.jsp:290`, `HealthTrackerPage.jspf:699`, `TemplateFlowSheetPage.jspf:784`
- Problem:
  - On main, `encounter/GraphMeasurements` drew a PNG in-process with JFreeChart (`ChartUtils.writeChartAsPNG`, main `:186`). It had no shared limit.
  - It now opens a new chromedriver browser session for every image (`new EFormBrowserPdfService().createDriver(options)`, `:67`).
  - It takes one of `EFormBrowserPdfService.RENDER_SLOTS`: `new Semaphore(2, true)`, the same two fair slots that saved-eForm print, fax, archive and email PDFs use.
  - It refuses when 16 chart requests are already queued or after 30 s without a slot.
  - Any failure becomes `sendError(503)` → `errorpage.jsp` ("CARLOS Error: 503"). That covers busy renderer, CDP/driver error and invalid stored values.
  - The page consumers are bare `<img src=".../GraphMeasurements?...demographic_no=...">` with no `alt`/`onerror`, or `window.open` popups.
  - eForm renders queue behind waiting chart renders on the fair semaphore. They are refused ("Browser rendering is at capacity; please retry shortly.") after their own 30 s wait or when 4 eForm requests are already waiting.
- Evidence:
  - `private static final Semaphore SLOTS = EFormBrowserPdfService.RENDER_SLOTS;` and `if (!WAITERS.tryAcquire()) throw new IOException("Chart renderer is busy"); acquired = SLOTS.tryAcquire(30, TimeUnit.SECONDS);`
  - `MAX_CONCURRENT_RENDERS = 2; ... RENDER_SLOTS = new Semaphore(MAX_CONCURRENT_RENDERS, true); RENDER_WAITERS = new Semaphore(2 * MAX_CONCURRENT_RENDERS);`
  - `catch (IOException | ParseException | RuntimeException unavailable) { ... response.sendError(HttpServletResponse.SC_SERVICE_UNAVAILABLE); }`
  - `docs/release-notes-2026.08.md` does not mention graphs at all.
- Impact:
  - While the renderer is busy (an eForm fax or print batch, several providers opening graphs), lab-value and drug-profile graphs show a broken image, and graph popups show "CARLOS Error: 503" with nothing telling the user to retry.
  - Chart traffic can delay or refuse eForm print, fax and email PDFs, which previously competed only with each other.
  - Every 503 is a 5xx GET whose URL carries `demographic_no`, so the packaged WAF audits it with the session cookie (see C3-3).
  - Each graph view now costs a browser launch.
- Correction:
  - Give charts their own small pool, or a pooled and reused browser, rather than the eForm PDF slots.
  - Answer a busy renderer with a retryable message image, or an `onerror` placeholder plus `alt` text in the two `<img>` consumers.
  - Use 500/422, not 503, for invalid stored data.
  - Add a release-notes line that graphs now render through the bundled browser.

### C3-2: Refusal reasons passed to `sendError` by this release are never shown to users
- Severity: Low
- Category: silent-failure
- Confidence: Confirmed
- Commit: 980a1be0 (#5541), 9ee16eaa (#5602), 57054b73 (#5553), 1a159b41 (#5651)
- Location:
  - `src/main/webapp/WEB-INF/jsp/error/errorpage.jsp:205` (`CARLOS Error: ${_responseStatus}` only); the message is read only inside `if (_displayError)` (`:78-95`)
  - `PrescriptionPdfServlet.java:31`, `MsgAttachPDF2Action.java:288`, `RptDownloadCSVServlet.java:81,85,95`, `EctSaveEncounter2Action.java:225-226`, `HtmlEdit2Action.java:71`
- Problem:
  - New refusals carry user-facing explanations in the `sendError` message, for example "Invalid satellite clinic address", "Attachment item is unavailable", "Report is too large; narrow the report filters" and "The legacy encounter editor is retired. Use the modern chart to save notes."
  - `web.xml:729-731` sends every error to `errorpage.jsp`. That page renders only the status code and incident id. `jakarta.servlet.error.message` reaches the page only when `DISPLAY_ERROR=true` and response sanitization is off, which is never in production.
- Evidence: `<p>CARLOS Error: ${carlos:forHtml(_responseStatus)}</p>`; `Object _errMsg = request.getAttribute("jakarta.servlet.error.message"); if (_errMsg != null) request.setAttribute("_errorMessage", ...)` runs only inside `if (_displayError)`.
- Impact: Users get "CARLOS Error: 400/410/413" with no explanation, and the actionable advice ("narrow the report filters") is lost. Individual instances are already reported as S06-2 (413/500 CSV), S08-2 (410 legacy editor) and S15-2 (multisite Rx print 400). This row is the shared root cause. The Messenger attach 400 (stale chooser) is the only instance not covered elsewhere.
- Correction:
  - In `errorpage.jsp`, show `jakarta.servlet.error.message` for 4xx statuses when the message comes from a fixed, PHI-free application set, for example a request attribute `carlosUserMessage` or a resource key passed by the action.
  - Alternatively, give these routes dedicated refusal pages.

### C3-3: More routine non-404 4xx/5xx responses now reach the packaged WAF audit log with cookies or OAuth headers (the #5781 class)
- Severity: Low
- Category: privacy
- Confidence: Plausible (WAF configuration read; not run)
- Commit: e0759727 (#5561), abdba03e (#5649), 5f9ca145 (#5518), 9ee16eaa (#5602)
- Location:
  - `debian/assets/modsecurity/main.conf:102-104` (`SecAuditEngine RelevantOnly`, `SecAuditLogRelevantStatus "^(?:5|4(?!04))"`, `SecAuditLogParts ABFHZ`)
  - `webserv/rest/ScheduleService.java:296-305`, `email/admin/ManageEmails2Action.java:224,233`, `encounter/oscarMeasurements/pageUtil/MeasurementGraphAction22Action.java:140`, `messenger/pageUtil/MsgAttachPDF2Action.java:288`
- Problem: Besides `rx/ViewRenalDosing` (#5781) and the photo upload `input` path (S16-4), these responses are new on paths that answered 200 (or 404) on main. Part B of each audit record holds `Cookie: JSESSIONID`, `Referer` and, for OAuth clients, the `Authorization: OAuth ...` header:
  - REST `/schedule/updateAppointment` and the `/appointment/{id}/updateStatus|Type|Urgency` routes answer 409 `APPOINTMENT_STALE_VERSION`. This is routine for clients that echo a stale `AppointmentTo1` (#5784). The routes are exposed on both `/ws/rs` (session cookie) and the OAuth server (`applicationContextREST.xml:169`).
  - Manage Emails Resolve answers 409, 400 or 405 (stale list row, double request).
  - `GraphMeasurements` answers 503 when the renderer is busy. It is a GET with `demographic_no` in the query string (C3-1).
  - Messenger `Doc2PDF` answers 400 for a stale chooser. Its `Referer` is the chooser URL, which carries `demographic_no`.
- Evidence: `case STALE_VERSION -> Status.CONFLICT;`, `response.setStatus(HttpServletResponse.SC_CONFLICT);`, `response.sendError(HttpServletResponse.SC_SERVICE_UNAVAILABLE);`. The `main.conf:132-139` "RESIDUAL RISK" note already concedes that query strings and cookies reach this log.
- Impact: The PHI-adjacent audit log grows with session credentials and patient identifiers from normal clinical and integration traffic, not attacks. It is root-owned, 0640 and kept 30 days.
- Correction: Fix this together with #5781 at the WAF layer: either exclude application-generated 409/410 statuses from `SecAuditLogRelevantStatus` or mask Cookie/Authorization in part B. Alternatively, keep expected conflicts out of the audited status range.

### C3-5: New REST 400 refusals are not in the release notes or the API docs; negative paging that main accepted now fails
- Severity: Low
- Category: docs
- Confidence: Confirmed

- Category: silent-failure
- Confidence: Confirmed
- Pre-existing: yes (present on origin/main)
- Commit: n/a (main `src/main/webapp/WEB-INF/jsp/administration/index.jsp:465-499`, unchanged except #5681 directives)

  - Any 4xx/5xx therefore leaves the panel exactly as it was, with no message. This includes the 403 `securityError.jsp`, the 500 `errorpage.jsp`, a WAF 403 and a CSRF rejection (redirected to errorpage, which is normalised to 500).

- Severity: Low
- Category: bug
- Confidence: Plausible (the insertion is confirmed in code; the visual effect was not run)
- Pre-existing: yes (present on origin/main)
- Commit: n/a (main `src/main/webapp/js/newCaseManagementView.js.jsp:467,1445,4512`)

## Checked and found OK
- `errorpage.jsp` normalises status <400 to 500 and `securityError.jsp:43` sets 403, so jQuery and CarlosAjax failure branches fire for mapped denials.
- `ResponseSanitizationFilter.sanitizationReason` (`:655-666`) replaces only stack traces and `/ws` 5xx bodies, so the new 4xx JSON bodies (ManageEmails, `ScheduleService` maps, `addNewQueue`) pass through.
- `JSONUtil.jsonResponse` calls `getWriter()` before `setContentType`, but `ResponseDefaultsFilter:234` already sets UTF-8, so non-ASCII text is safe.
- CXF session and OAuth servers use the Jackson provider, so the `Map` error entity in `ScheduleService` serialises. Every affected method `@Produces` JSON.
- Every new `sendError` path returns `NONE` (or `return` in servlets). The CSV, Dx XLSX and graph paths buffer before the headers and check `isCommitted()` before `reset()`/`sendError`.
- Every 405 sets `Allow: POST` (filter, `HtmlEdit2Action`, `ManageEmails`, `addNewQueue`).
- The new error bodies carry no PHI or ids: `AppointmentUpdateException` messages are fixed, `validateFieldLengths` names fields only, and the ManageEmails messages are static.
- 403 vs 404: BC guard 404 only on non-BC deployments. ManageEmails 404/409 and appointment 404/409 sit behind write privileges for data the user can already list.
- `ProviderProperty2Action` `status="error"` (#5617) is still rendered by `setDocDefaultQueue.jsp:106-156` (it checks for null only).
