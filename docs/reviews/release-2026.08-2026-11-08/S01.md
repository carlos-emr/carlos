## Findings
### S01-1: Editing an existing CPP item shows hex escapes in its issue labels ("Social\x20History\x20as\x20part\x20of\x20cp\x70")
- Severity: Medium
- Category: regression
- Confidence: Confirmed
- Commit: 23154da2 (#5459)
- Location: `src/main/webapp/WEB-INF/jsp/casemgmt/viewNotes.jsp:177-185` (`.append(SafeEncode.forJavaScript(iss.getIssue().getDescription()))` at :183), `:198`, `:207` (`'<carlos:encode value='<%= strNoteIssues.toString() %>' context="javaScriptAttribute"/>'`), `src/main/webapp/js/newCaseManagementView.js.jsp:1180-1187` (label = `escapeNoteText(issueArray[idx + 2])`), `:1201`
- Problem: Issue descriptions in the edit-existing-item payload are JS-encoded twice. They are first encoded with `forJavaScript` in the scriptlet and then again by the `javaScriptAttribute` tag. After JS decoding, the label therefore still contains the inner escapes, and `escapeNoteText` renders them as text. Encoder 1.4.1 left spaces and letters alone, so the double encoding was invisible for ordinary descriptions. 1.6.0 escapes every space and a final c/i/p/r/s/t, so it is now visible on every label. The "Add Item" popup (viewNotes.jsp:103) shows correct labels, because `cppIssue` (CaseManagementView2Action.java:1208) uses the raw description under the same outer tag. #5459 fixed the CPP ext-field transport (`getNoteExts`), but not this neighbouring issue field in the same `showEdit` call.
- Evidence: Real encoder jars, with the result evaluated in Node:
  - 1.6.0: `forJavaScriptAttribute("65;OMeds;" + forJavaScript("Other Meds as part of cpp"))` = `65;OMeds;Other\\x20Meds\\x20as\\x20part\\x20of\\x20cp\\x70`; the JS value is `"Other\x20Meds\x20as\x20part\x20of\x20cp\x70"`.
  - 1.4.1: `"Other Meds as part of cpp"`.
  - The 7 seeded CPP issue descriptions all contain spaces (`V1.0.2__on_data.sql`: 'Social History as part of cpp', …).
  - `CppMetadataEncodingUnitTest`, `cpp-edit-round-trip.cjs` and the doc's Chromium check cover only `noteExts`.
- Impact: Every user editing any existing CPP item (Social/Medical History, Ongoing Concerns, Reminders, Other Meds, Risk Factors, Family History, plus any user-linked issue) sees garbled issue names in the popup. The labels are display-only: checkbox values are issue ids, so saving is unaffected. This is a clear visible regression versus beta7 (main), on a core encounter screen.
- Correction: Build `strNoteIssues` like the Add path, or like the fixed ext transport. Use the raw description, or URI-component-encode each `;`-delimited component and `decodeURIComponent` after splitting in `showEdit`, so a `;` in a description cannot shift the triplets. Leave the outer `javaScriptAttribute` tag and `escapeNoteText` as the context encoders. Add the issue label to the Node round-trip regression.

## Out of scope but notable
- `TotpGenerator` (new in 1c411c36) formats codes with `Locale.getDefault()` to keep java-otp parity. On a JVM whose default locale uses non-ASCII digits (ar, fa, th-u-nu-thai, …), generated codes never match typed ASCII digits. The behaviour pre-exists and is unlikely for Canadian (en/fr) deployments; `Locale.ROOT` would be correct for a protocol value.
- `ChartNotesAjax.jsp:1014-1016` puts JS-encoded template names inside a JS string that is later evaluated as code. A template name containing `'` breaks `ajaxInsertTemplate(...)`. This pre-exists (`\x27` under 1.4.1 too) and is not made worse by 1.6.
