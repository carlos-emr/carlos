## Findings

### S02-1: ENC(...) keystore passwords: the outbound path still uses the ciphertext as the password, so the explicit message never reaches an admin, and the Javadoc and doc say otherwise
- Severity: Low
- Category: docs
- Confidence: Confirmed (code trace)
- Commit: 9c662151 (#5463)
- Location: `src/main/java/io/github/carlos_emr/carlos/integration/ebs/client/ng/PlaintextCryptoPasswordEncryptor.java:13-16`, `docs/migration/ebs-without-jasypt.md:46-52`, `src/main/java/io/github/carlos_emr/carlos/integration/ebs/client/ng/EdtClientBuilder.java:313-315`, `src/test/java/io/github/carlos_emr/carlos/integration/ebs/client/ng/EdtWsSecurityWithoutJasyptUnitTest.java:248-257`
- Problem: Outbound signing loads `SIG_PROP_FILE` through CXF `AbstractWSS4JInterceptor.loadCryptoFromPropertiesFile` → `WSS4JUtils.loadCryptoFromPropertiesFile` (CXF 4.1.9 lines 302-314). That method swallows the failure that `PlaintextCryptoPasswordEncryptor.decrypt` causes and retries with `CryptoFactory.getInstance(propFilename, classLoader)`, which passes a null encryptor (WSS4J `CryptoFactory` 182-188). Merlin then returns the literal `ENC(...)` text as the keystore password (`Merlin.decryptPassword` 1549-1557).
  The request is signed before any response exists, so a deployment with `ENC(...)` values always fails at that point, with a generic keystore "password incorrect"/credential-load error. The explicit "ENC(...) ... not supported ... see docs/migration/ebs-without-jasypt.md" text can only come from the inbound path, which a real EBS exchange never reaches.
  Despite that, the class Javadoc says it avoids "treating ciphertext as a password", and the doc says the values "are never passed through as plaintext". The doc does concede that the outbound path "can instead report a keystore-loading error". The outbound test case only asserts `WSSecurityException`.
- Evidence: `catch (Exception e) { //ignore } return CryptoFactory.getInstance(propFilename, classLoader);` (WSS4JUtils:311-314); `if (passwordEncryptor == null) { ... LOG.debug(error); return password; }` (Merlin:1552-1556).
- Impact: Minimal in practice. `ENC(...)` never worked with the EBS callback, because `ClientPasswordCallback` rejects `PASSWORD_ENCRYPTOR_PASSWORD`, and the outbound fallback behaved the same with Jasypt. But an operator following the migration doc gets a misleading "wrong password", and the docs contradict the code.
- Correction: Correct the Javadoc and doc to say that outbound failures appear as a keystore password error. Optionally, at first use, scan the resolved signature properties for `ENC(` and throw the explicit message. That keeps the lazy loading. Assert the outbound root cause in the test.

### S02-3: The release notes say nothing about the EBS transport switch, the 110 jars removed from the WAR, or `ENC(...)` being unsupported
- Severity: Low
- Category: docs
- Confidence: Confirmed (absent from the notes)
- Commit: 9748d012 (#5469), 112feaec (#5467), 9c662151 (#5463)
- Location: `docs/release-notes-2026.08.md:1-62`. The only EBS section is "HCV and MCEDT transport diagnostics" (:11-17).
- Problem: Three upgrade-relevant changes are undocumented:
  1. MCEDT and HCV now use CXF's URLConnection transport. The 240 s receive setting is now an idle-read timeout with no total deadline. Requests above 4 KB are chunked, and JVM proxy/trust settings apply. This also fixes the "Unsupported protocol: TLS" failure of every EBS HTTPS exchange on main/beta6/beta7 (see "Out of scope").
  2. The WAR no longer ships these libraries: HttpClient/HttpCore 4 and HttpAsyncClient, commons-beanutils 1.11, Jasypt, Netty, Artemis, the jakarta.json and json-bind APIs, nimbus-jose-jwt, micrometer-core, JAXB XJC/codemodel, and CXF tools/testutils, `cxf-rt-rs-client` (the JAX-RS `ClientBuilder` provider), `cxf-rt-javascript` (`?js`), `ws-mex`, `ws-rm`, `metrics`, `sse`, `rs-http-sci`, `undertow` and `netty`.
  3. `ENC(...)` Crypto passwords are explicitly unsupported (see `docs/migration/ebs-without-jasypt.md`).

  #5746's checklist does not cover these, and #5747 covers only CARLOS's own API types.
- Evidence: `grep -i "cxf\|httpclient\|jasypt\|beanutils" docs/release-notes-2026.08.md` returns nothing. The lockfile diff around 9748d012 is listed under Coverage.
- Impact: The removals are loud failures, not silent ones: a JSP compile error or NoClassDefFoundError. They affect only site-local JSPs, Jasper templates or plugin jars that used these libraries; no in-tree consumer exists. Sites that saw MCEDT/HCV outages on beta6/7 get no explanation or upgrade guidance.
- Correction: Add an "Upgrade notes: web services and bundled libraries" section covering items 1-3. This could be folded into #5746/#5747.

## Checked and found OK
- **Jasypt use before removal:** Jasypt was only WSS4J's implicit `ENC(...)` fallback, built in `WSHandler.getPasswordEncryptor` and `WSS4JUtils.getPasswordEncryptor`. No CARLOS code, Spring bean, DB value or shipped config used it. The default `clientKeystore.properties` is plaintext. The other Jasypt constructors (StAX and policy interceptors, STS, SAML) are on paths CARLOS never runs.
- **Encryptor coverage:** `PlaintextCryptoPasswordEncryptor` is supplied wherever an EBS Crypto loads: in/out handler maps (EdtClientBuilder:271, :313) and the request context (:193-194). The inbound `DEC_PROP_REF_ID` path and the outbound `SIG_PROP_FILE` path both pick it up through `getOption`, so there is no NoClassDefFoundError path. The Jasypt exclusions (cxf-rt-ws-security, the direct wss4j-common/dom declarations) and the enforcer ban hold; the lock has no Jasypt artifact.
- **CXF feature → module inventory, all present:**
  - core: `cxf:bus`, `META-INF/cxf/cxf.xml`, `@GZIP`, StaxUtils, CachedOutputStream, AttachmentDeserializer, MTOM.
  - frontend-jaxws: 14 `jaxws:endpoint`s, `WebServiceContextImpl`, `JaxWsProxyFactoryBean`.
  - frontend-jaxrs: three `jaxrs:server`s including the OAuth 1.0a surfaces, JAXBElementProvider, FormEncodingProvider, JAXRSUtils, extension mappings, RuntimeDelegate.
  - transports-http: CXFServlet, HTTPServerPolicy, HTTPConduit, TLSClientParameters.
  - bindings-soap and wsdl, frontend-simple: `?wsdl` / WSDLGetInterceptor.
  - databinding-jaxb; ws-security, security, security-saml, ws-policy and ws-addr (with WSS4J 4.0.2, xmlsec, OpenSAML 5.2.3, ehcache); features-logging.
  - Jackson provider: `jackson-jakarta-rs-json-provider`.
  - Jettison `JSONProvider` and `?_wadl` were already excluded before the slice. No `http-conf:`, `sec:` or `jaxrs-client` namespaces are used.
- **Libraries removed with the aggregate:** no runtime users. Packages grepped: commons-beanutils 1.x (the Java hits are Spring `BeanUtils`; JasperReports 7.1 uses beanutils2), `org.apache.http`, jakarta.json, nimbus, micrometer-core, XJC, Netty, Artemis, configuration2, jctools, snakeyaml. The undertow SSE ServletContainerInitializer and CXF's JAX-RS SCI only did work for Application subclasses, and there are none.
- **Transport scope:** URLConnection is selected only for EBS, through request-context keys (EdtClientBuilder:176-177). The conduit class is still `HttpClientHTTPConduit`, which delegates to its URLConnection superclass (`HttpClientHTTPConduit:346-374`). Other CXF clients would keep the JDK HttpClient conduit, but none exist in main code.
- **TLS with "TLS" under URLConnection:** `SSLContext.getInstance("TLS")`. The socket factory wrapper enables all non-SSLv3 protocols, and JDK 25 disables TLS 1.0/1.1, so the result is TLS 1.2/1.3. Trust comes from the JVM default; hostname verification uses CXF `DefaultHostnameVerifier` (with SNI); there is no client certificate (EBS signs at message level).
- **Proxy:** CXF `ProxyFactory` (`http.proxy*`), otherwise the JDK ProxySelector. Equivalent to the JDK HttpClient conduit.
- **Retries:** none from CXF (AutoRedirect off). Requests above the 4096 B threshold go out in chunked streaming mode, so the JDK's one-shot POST retry cannot apply to them. CXF-6227 means smaller requests are not put in fixed-length mode and could be retried once over a stale keep-alive connection, but signed EBS envelopes (BST, signature, UsernameToken, EBS/IDP headers) are, by my estimate, above 4 KB.
- **Thread safety:** a new HttpURLConnection per call, and `HttpsURLConnectionFactory` is synchronized. The attachment ThreadLocal belongs to the calling thread; the concurrent-download test covers it.
- **Reply ownership:** EBS keeps the replay until POST_INVOKE, and closes it on a downstream fault (handleFault), on a SOAP Fault (in-fault-chain cleanup) and on a failing fault chain (RECEIVE guard; CXF does honour `getAdditionalInterceptors`, PhaseInterceptorChain:248-252). Closing is idempotent, and nothing reads the stream after POST_INVOKE (download content is a `byte[]`).
- **Tests are real:** the transport test does loopback HTTPS against an independent WSS4J-verifying peer, covering signed and encrypted SOAP and MTOM, tamper, untrusted signer and expiry, stall, truncation, faults, TLS 1.2/1.3, hostname, mTLS, shared-Bus isolation and concurrency. The Jasypt test does real WSS4J sign/decrypt with PKCS12/JKS keystores and both property prefixes, plus lazy/late provisioning. The doc's count of 22 builder cases matches the code.
- **Doc statements verified:** the inventory, the per-client keys and the `usePolicy=ALWAYS` override (AsyncHTTPConduit:162-194). "Without the settings ... Unsupported protocol: TLS ... predates #5469" is true: the netty-client factory is registered under its class name, so on main hc's `HTTPConduitFactory` won.
- **Other changes:** removing the unused beanutils import from billingAddReferralDoc.jsp is safe; the CI `::error` annotation escaping is correct.

## Out of scope but notable
- main / beta6 / beta7: every MCEDT and HCV HTTPS call fails with "Unsupported protocol: TLS". The cause is CXF 4.1.9 `HttpClientHTTPConduit:433-436` building `SSLParameters` with `{"TLS"}`, together with `EdtClientBuilder.configureSsl`'s `setSecureSocketProtocol("TLS")`, on the AsyncHTTPConduit sync path. The release fixes it (112feaec); any site on beta7 has no working MCEDT or HCV. This deserves a note in the release notes or an advisory.
- `HCValidationFactory` builds a new CXF client per validation and never destroys it (pre-existing). The URLConnection transport makes this cheaper than the JDK HttpClient conduit was.
- `EdtClientBuilder:184` sets the misspelled `com.sun.xml.internal.webserv.request.timeout`, which nothing reads (pre-existing).
- `DelegateFactory.edtDelegates` is an unsynchronized static HashMap (pre-existing).
- mimepull left the WAR with 1650895f (#5526, another slice). The EBS MTOM path does not use SAAJ MIME parsing, and the MTOM transport tests pass. Worth a line for the #5526 reviewer.
