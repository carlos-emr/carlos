## Coverage
- Commits reviewed in full: ad7ce1c2 (#5466), 6ea14c74 (#5468), d55d0205 (#5458). - Cross-tree survey: I checked all 151 main files that use XML APIs. Every application-level JAXP factory goes through `XmlUtils`, which already used `newDefaultInstance()` on main, or through a hardened local factory (`SvgReferences`, `FaxXmlResponseParser`, the CDS classes). I found no `org.apache.xerces` string, provider system property or `META-INF/services` override anywhere in `src/main`, `debian/` or `.devcontainer/`. I also traced the libraries whose default discovery changes provider: JDOM's default reader, XMLBeans, HAPI DefaultXMLParser (only reached after `Hl7XmlMessageValidator`), OpenSAML/xmlsec, SAAJ, Spring/Struts/Log4j config, JAXB `DatatypeFactory`, and DOM Load-Save through `XmlUtils.writeNode`.
- Empirical checks (scratch only, JDK 21):
  1. JDK limit semantics under JDK-25-equivalent `jdk.xml.*` values. Predefined references count against `maxGeneralEntitySizeLimit` / `totalEntitySizeLimit` in both text and attribute values. Character references and CDATA do not count. `entityReplacementLimit` does not count them. The CDS reader overrides (`0`) work.
  2. An equivalence harness ran the **main-branch Xerces-XSModel classification algorithm** (old `Frame.configure`, `whitespace`, `identity`) over the JDK's internal Xerces-lineage XSModel of the pinned XSDs. It compared the result with the new `CdsSchemaModel` classification for every global element and its whole content tree, every named and built-in type, and every xsi attribute. Fields compared: type namespace and name, whitespace, streaming mode, identity. Result: **552 contexts, 0 mismatches**.
  3. Downloaded (data-only inspection) batik-util 1.19: the Xerces SAX driver is commented out, so Batik uses JAXP. Downloaded jakarta.servlet.jsp.jstl 3.0.1: no `META-INF/services`, no shaded Xerces, and its SHA-256 matches the doc.
- Not covered: running the Maven suites (no JDK 25 here); standalone Xerces 2.12.2 itself (the JDK's internal XSModel stood in for it); the separate carlos-ctl repository.

## Findings
### S03-1: Release notes omit the standalone-Xerces removal and the JAXP provider switch
- Severity: Low
- Category: docs
- Confidence: Confirmed
- Commit: ad7ce1c2 (#5466)
- Location: `docs/release-notes-2026.08.md` (whole file); `pom.xml:2338-2356` (new `ban-global-xerces-providers`)
- Problem: The WAR no longer ships `xercesImpl-2.12.2.jar`. That removes the `org.apache.xerces.*`, `org.apache.xml.serialize.*`, `org.apache.html.dom.*` and `org.apache.wml.*` packages. Every default-discovery JAXP lookup (`DocumentBuilderFactory/SAXParserFactory/SchemaFactory/DatatypeFactory.newInstance()`, `DOMImplementationRegistry`, `XMLReaderFactory`) now resolves to `java.xml` and inherits the JDK 25 `jaxp.properties` limits. This is documented only in `docs/cds-xml-providers.md`. The release notes do not mention it, and the open release-notes umbrella (#5746) does not list it either.
- Evidence: `grep -i "xerces\|jaxp\|xml provider" docs/release-notes-2026.08.md` returns nothing. The lock diff for ad7ce1c2 is exactly `('xerces','xercesImpl') ('2.12.2','compile') -> None`. In-tree code has no remaining reference, so the in-tree migration is complete.
- Impact: Sites with local JSP overlays, plugins or report code that import Xerces classes (for example the old `org.apache.xml.serialize.XMLSerializer` idiom common in OSCAR-era code) get `NoClassDefFoundError` after upgrade. Integrators are not told that large XML handled by default-discovery parsers can now be refused (see #5790). Nothing in the product warns them.
- Correction: Add an upgrade note: Xerces is no longer bundled, and these packages are gone. Default discovery is now the JDK. Point to `docs/cds-xml-providers.md` for the limits. Add the item to #5746's checklist (and optionally #5747's list for custom-code authors).

## Checked and found OK
- CDS SAX reader: `newDefaultInstance`, FSP, disallow-doctype, external entities off, `load-external-dtd` off, XInclude off, `ACCESS_EXTERNAL_DTD=""` on the reader, throwing EntityResolver. Every setter failure maps to `CDS_SECURE_XML_PARSER_UNAVAILABLE` (fail closed, no silent loss).
- CDS validation:
  - The SchemaFactory and ValidatorHandler set `ACCESS_EXTERNAL_DTD`/`SCHEMA=""` and FSP and use the allowlist resolver (only `cds_dt` plus the exact DT systemId).
  - The compiled schema is grammar-pool-only, so instance `xsi:schemaLocation` hints are never loaded.
  - `element-default` and `augment-psvi` are recognized by the JDK and fail closed if not.
  - error → counted and blocking; fatal → recorded and rethrown; warnings stay non-blocking. Nothing is downgraded.
- JDK-limit ordering:
  - Depth: root = 1. The JDK limit is depth+1, and CDS checks `stack.size() >= maxXmlDepth` first.
  - Attributes: the JDK count includes xmlns, and its limit is set above CDS's 128 ordinary attributes plus aliases.
  - Names: the JDK limit is 1 + max(name, URI).
  - In every case CDS raises its own code first. Tests cover all three, plus 300k escapes.
- `CdsSchemaModel` metadata DOM: FSP, disallow-doctype, XInclude off, no entity expansion, `ACCESS_EXTERNAL_*=""`. Unsupported constructs (list, union, any, complexContent, simpleContent, groups, global attributes) fail closed at class init. Latent nit with no current effect: `declaration()` resolves `xs:attribute ref` against element declarations. It still fails closed, and the pinned XSDs have no attribute refs.
- Anonymous type names (`#AnonType_…`) match Xerces/JDK `genAnonTypeName` (the root contributes ""). The xsi built-ins match SG_XSI. The `bounded` set omits ID/IDREF/ENTITY, which has no effect because they are not `plainString`. Raw lexical values, not validator output, are stored, so no Xerces/JDK normalization difference reaches clinical values. Encoding is decided by `CdsXmlText` (character stream), not the parser.
- Snapshot refactor (`ProbeInput`, `probeCandidate`, `parseReferences`, `ReferencedFilesHandler`, `CountingSource`) is behaviour-identical, including exception mapping, `RootFound` order and the malformed-XML candidate policy.
- `CdsRulesetFingerprint` already covers `demographic/cdsimport/**/*.class`, so the new `CdsSchemaModel` is fingerprinted.
- JDOM: all production parsing uses `createSecureSAXBuilder()`. The only production `new SAXBuilder()` is inside it, and JSPs have none. FSP is supported on the JDK XMLReader, and on JDK 25 the jaxp.properties limits outrank the FSP state, so there is no behaviour change. The warm-up uses JDOM's `reuseParser` cache, and setters reset the engine. `SAXBuilderEngine` resets its handler, so there is no document retention.
- There is no dedicated repo lint or ArchUnit test for a new `new SAXBuilder()`. Detection relies on the generic Sonar S2755 / CodeQL `java/xxe` rules, which are expected to model JDOM2's SAXBuilder (not verified here). Test code uses `new SAXBuilder()` only on synthetic or bundled XML.
- Hostile-XML tests:
  - DOCTYPE with a `file:` entity is refused by the main parser (`CdsXmlParserUnitTest:116`).
  - Snapshot discovery makes no fetch for external DTDs, general entities or parameter entities (loopback observer).
  - The schema-metadata reader refuses DTDs.
  - The JDOM DOCTYPE, entity and XInclude variants are refused or left unexpanded.
- Library defaults after the provider switch: OpenSAML, xmlsec, XMLBeans and JasperReports set JDK-recognized hardening or fall back silently to JDK properties, so no hardening is lost. Batik 1.19 uses JAXP. Struts DTD validation under the JDK is CI-checked by `scripts/lint/check-struts-dtd.sh` (JDK 25).
- d55d0205: src contains no JSTL XML taglib URIs or `org.eclipse.tags.shaded` references; the JSTL jar facts and the pom comments are accurate.
- `docs/cds-xml-providers.md`, the `cds-import-architecture.md`/`ledger.md` updates and `jdom2-maintenance.md` claims match the code. The JDOM2 file count is a dated snapshot: 30 at 6ea14c74, 28 now.
- The upgrade path needs no config keys and leaves no stale jar in Debian or devcontainer deployments. Prepared imports from an earlier runtime are refused by design and documented.
