## Findings

### S04-1: Literal-'+' Content-ID decoding no longer matches CXF's own attachment IDs
- Severity: Low
- Category: regression
- Confidence: Confirmed
- Commit: 4b302882 (#5710)
- Location: `src/main/java/io/github/carlos_emr/carlos/integration/ebs/client/ng/AttachmentResolverSpi.java:128`, `:151`; `src/main/java/io/github/carlos_emr/carlos/integration/mcedt/mailbox/CidPrefixResourceResolver.java:84`, `:101`; `src/test/java/io/github/carlos_emr/carlos/integration/ebs/client/ng/AttachmentResolverSpiUnitTest.java:58-63,200-207`
- Problem: #5710 changed the cid-URI decoding to keep a literal `+` ("a cid URI is not form data"), but the
  attachment IDs it is compared against are produced by CXF, which URL-decodes the `Content-ID` header with
  `URLDecoder` and so turns `+` into a space. Before #5710 both sides decoded the same way and matched.
- Evidence: resolver `URLDecoder.decode(resourceId.replace("+", "%2B"), "UTF-8")` then
  `a.getId().equals(resourceId)`; main used plain `URLDecoder.decode(resourceId, "UTF-8")`. cxf-core 4.1.9
  `AttachmentUtil.cleanContentId` (lines 356-379): `id = URLDecoder.decode(id, UTF_8)`, called from
  `createAttachment(...)` line 411, which `AttachmentDeserializer.createAttachment` uses for every MTOM part.
  For `Content-ID: <urn:a+b>` CXF stores `urn:a b`; the resolver now looks for `urn:a+b` → no match. The new
  test mocks `Attachment.getId()` as `"urn:FAKE_EBS+ATTACHMENT_ID"`, an id CXF's parser cannot produce, so it
  proves only the resolver half.
- Impact: any MCEDT/HCV response whose Content-ID contains `+` (e.g. base64-style IDs) now fails signature/
  ciphertext reference resolution ("EBS attachment could not be resolved") where it resolved before. The MCEDT
  spec sample uses numeric IDs (`cid:2341682853256`), so this is unlikely, but the change can only break, never
  fix, CXF-parsed attachments.
- Correction: decode exactly as CXF does (plain `URLDecoder`), or match either form; replace the mock test with
  one that builds the attachment through CXF (`AttachmentUtil.createAttachment` with a real Content-ID header).

### S04-2: Blank Date elements still fault the SOAP reader, unlike the Calendar fix that preserves MOXy's null
- Severity: Low
- Category: breaking-change
- Confidence: Confirmed
- Commit: 1650895f (#5526) (left incomplete by 4b302882 / 1e16750c)
- Location: `src/main/java/io/github/carlos_emr/carlos/utility/xml/DateXmlAdapter.java:39-40`; contrast `CalendarXmlAdapter.java:56-61`; `docs/jaxb-provider-compatibility.md:73-77`; consumer `src/main/java/io/github/carlos_emr/carlos/webserv/MeasurementWs.java:85` (`MeasurementTransfer.dateObserved/createDate`, WSDL `MeasurementService.wsdl:79,81` minOccurs=0 xsd:dateTime)
- Problem: the migration deliberately kept MOXy's "empty/whitespace optional date = null" rule for Calendar
  (the Calendar adapter takes a String, trims, returns null). `DateXmlAdapter` takes an `XMLGregorianCalendar`,
  so Glassfish's built-in parser sees the blank text first and raises a validation error. CXF's SOAP reader
  aborts on any validation event (`DataReaderImpl` installs `WSUIDValidationHandler`, which returns false).
- Evidence: probe with the release adapters on jaxb-runtime 4.0.9, event handler returning false (as CXF):
  `<createDate/>` → `UnmarshalException`; `<start/>` (Calendar) → null. Native MOXy 5.0.0, same handler:
  `<createDate/>` → null (`XMLConversionManager.convertStringToXMLGregorianCalendar`: trimmed empty → null).
- Impact: on installs that ran MOXy on beta6, a SOAP `addMeasurement` request with an empty date element now
  gets a SOAP fault instead of being accepted (Glassfish-era installs behaved like this already). REST XML is
  lenient (null), so only SOAP strict reads are affected; a narrow but undocumented gap in the "preserve MOXy
  inputs" contract.
- Correction: give `DateXmlAdapter` a String value type (keep `@XmlSchemaType(dateTime)`) and mirror the
  Calendar trim/empty→null rule, or document Date's stricter behaviour; add a strict-handler test on
  MeasurementTransfer.

### S04-3: AppointmentExtTo.toString now prints patient name, phones, email, notes and demographicNo
- Severity: Low
- Category: privacy
- Confidence: Confirmed
- Commit: 1650895f (#5526)
- Location: `src/main/java/io/github/carlos_emr/carlos/webserv/rest/to/model/AppointmentExtTo.java:239-251`; `src/test/java/io/github/carlos_emr/carlos/utility/xml/AppointmentDtoReliabilityUnitTest.java:67-83`; `docs/jaxb-provider-compatibility.md:174-175`; policy `docs/security-object-diagnostics.md:3,19,25`
- Problem: main's toString had an operator-precedence bug, so it returned only `df.format(appointmentDate)`.
  The "fix" makes it return the full description including `lastName`, `firstName`, `phone`, `phone2`,
  `email`, `demoCell`, `notes`, `demographicNo`, and a new test pins that. That conflicts with the safe-
  diagnostics policy introduced by #5486/#5512 ("must not expose ... patient fields"), whose audit ran at
  112feaecb7b, before this change, and only covered reflective toStrings, so this case was never reviewed.
- Evidence: `+ ", lastName=" + lastName + ", firstName=" + firstName + ", phone=" + phone ... + ", email=" + email`;
  the test asserts `.contains(", appointmentDate=2026-07-15, startTime=2026-07-15,")` on the full string.
- Impact: latent. I found no current log or exception sink for this DTO, but any future
  `logger.x("..." + appointment)` or `List.toString()` of the response content would write PHI to the logs.
- Correction: return `AppointmentExtTo[appointmentNo=…]` (or `Type[protected]` as in #5486) and change the test
  to assert that patient fields are absent.

### S04-4: Nothing checks the packaged WAR for a second JAXB provider, the failure mode behind #5476
- Severity: Low
- Category: test-gap
- Confidence: Confirmed
- Commit: 1650895f (#5526)
- Location: `docs/jaxb-provider-compatibility.md:5-6`; `pom.xml:1589-1600`; `src/test/java/io/github/carlos_emr/carlos/utility/xml/JaxbProviderDiscoveryUnitTest.java:49-65`; `debian/rules:133-137`
- Problem: the doc requires that MOXy "and its dependencies must not appear in WEB-INF/lib", and the commit
  says it guards provider discovery against drift. The only guard checks ServiceLoader order on the Maven
  test classpath, where MOXy is present by design. In Tomcat, WEB-INF/lib order is directory order, and that
  is exactly what made beta6 install-dependent. No WAR check exists (debian/rules runs
  check-war-container-apis.py and check-war-commons-logging.py only; grep finds no JAXBContextFactory check).
- Evidence: `grep -rl "JAXBContextFactory|persistence.moxy" scripts debian .github` matches only the non-CI
  WarWireCompatibilityProbe.
- Impact: a future dependency that brings MOXy (or another JAXB provider) back at compile scope would again
  flip REST/SOAP wire formats per install, with no failing check.
- Correction: add a debian/rules WAR check (like check-war-commons-logging.py) that requires exactly one
  `jakarta.xml.bind.JAXBContextFactory` provider (`org.glassfish.jaxb`) and no `org.eclipse.persistence*` jars.

## Known issues re-confirmed
- #5721 XML-1 (character literal vs numeric): still unfixed at head. Explicitly pending; WSDLs say `xsd:string`, beta6 Glassfish said `xs:unsignedShort`.
- #5721 XML-2 (cleared-calendar date-only): fixed by #5722 for the four DTOs; no other bound production Calendar property still uses the set-state adapter.
- #5721 XML-3 (empty map omitted) and XML-4 (illegal `final` on anonymous types): fixed at head.
- #5721 XML-5 (sequence): AppointmentExtTo XML fixed (probe matches main Glassfish byte order); DrugTransfer still alphabetical, so still unfixed for it.
- #5748 (birthday date-time for MOXy-era installs): unfixed (deliberate).
- #5749 (JSON key order): still unfixed. After #5722, AppointmentExtTo JSON follows the XML propOrder, not main's field order (probe); DrugTransfer is alphabetical.
- #5746 (release notes): still says birthday XML "retains the published `xs:dateTime` form" and lists none of the #5722 wire changes.
- #5720 (qualification): the new `main-glassfish-…`/`main-moxy-…` lanes are registry commands that need the beta6 deb, a candidate WAR and Tomcat jars. CI runs only the harness unit tests (ci-validation `unittest discover`; release-verification says it "does not certify release readiness"). `releaseReady` stays false, so this remains unfixed. The in-repo MOXy corpus comes from release commit 112feaecb7b, not beta6, so comparing against beta6 itself is left to that manual verifier.
- #5745 (CXF attachment cache files): not touched by this slice; still open.

## Checked and found OK
- A JAX-WS implementation (CXF) is present for every SOAP service and client; namespaces of all 14 SEIs match the static WSDLs; `classpath:` WSDL locations and address rewriting work (CXF source).
- No Metro, JDK-internal or JAXB-RI-specific properties, `jaxb.properties`, MOXy APIs or `com.sun.xml.*` imports in src/main or JSPs. The only `com.sun.*` references are istack `@NotNull` (still on the classpath) and the dead timeout key noted below.
- saaj-impl, jakarta.xml.ws-api, jakarta.xml.soap-api, stax-ex, asm, angus-activation and jaxb-runtime all stay at compile scope. jaxb-impl 4.0.9 on main held the same `org.glassfish` classes, so there was no third provider.
- Golden tests are real: the frozen MOXy corpus comes from an old-stack WAR (with documented hand additions); the beta6 Glassfish XSDs are hash-pinned (re-hashed, all OK); the JSON baseline was captured before the migration. Every top-level bound type has a frozen entry (the leftovers are ObjectFactory/Service/adapter classes the test excludes).
- Stream ownership: JAXB marshal never closes caller streams (Glassfish closes only streams it creates); the resolvers hand back unread attachment streams; DownloadInInterceptor no longer swaps streams; the ImportZipInputStream change matches JDK semantics.
- `RestXmlAnnotationIntrospector` is wired into all three JAX-RS servers' JSON providers, and other `ObjectMapper`s don't use JAXB introspection.
- `copyTo`, ProfessionalSpecialist, ConsultationRequestTo1 and BpmhForm2Bean changes are genuine fixes, with no consumer regressions found.
