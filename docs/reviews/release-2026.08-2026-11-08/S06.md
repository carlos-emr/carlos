## Findings

### S06-1: Report by Template refuses whole reports that ran before; fixed limits, no setting, not in the release notes; misleading CSV message
- Severity: Medium
- Category: breaking-change
- Confidence: Confirmed
- Commit: c5add8d9 (#5560)
- Location: `src/main/java/io/github/carlos_emr/carlos/report/reportByTemplate/ReportResultBudget.java:30-35,78-80,102-104,148-160,186-197`; `src/main/java/io/github/carlos_emr/carlos/report/reportByTemplate/SQLReporter.java:57-63,128-134,170-178`; `src/test/java/io/github/carlos_emr/carlos/report/reportByTemplate/SQLReporterSessionStorageTest.java:145`; `docs/release-notes-2026.08.md` (no mention)
- Problem: Every Report by Template request now has fixed limits, set as `static final` constants with no property or override: 10,000 rows, a 5 MiB CSV, 10 MiB of HTML, 256 columns, 64 Ki characters per cell, 32 queries and 30 s. A sequence shares one budget. Going over any limit throws the whole report away (`return false` → `reportConfiguration.jsp`). On main, none of these limits existed, and a CSV over 5 MiB still showed the HTML report (`generated == true`; main's version of the same test asserted `isTrue()`, release asserts `isFalse()`). The CSV case now shows `CSV_EXPORT_LIMIT_MESSAGE`, "Report result is too large to download as CSV". That suggests only the download was held back, when in fact nothing is shown. HTML is always larger than its CSV (about 9 more bytes per cell). For cells longer than about 8 characters it is less than twice the size, so the 5 MiB CSV limit is reached before the 10 MiB HTML limit, and the real cap is about 5 MiB of data: for example 10k rows × 20 columns × about 26 characters. Column and cell refusals reuse "exceeds the row, size or time limit", which does not name the limit that was hit. A deadline spent waiting for a pool connection (`db_max_wait` = 20 s by default) is also reported as "narrow your search".
- Evidence: `static final int MAX_ROWS = 10_000; … MAX_COLUMNS = 256; MAX_CELL_CHARACTERS = 64 * 1024; MAX_QUERIES = 32; TIMEOUT_SECONDS = 30;`. `if (result[1] == null) { request.setAttribute("errormsg", result[0]); … return false; }`. Shipped forms wider than 256 columns: formRourke2009 (1,227 columns), formBCAR2012 (840), formBCAR2007 (814), formBCAR (695), formRourke2006 (627), formRourke (425), formRourke2020 (346), formBCHP (265), formGrowthChart (261); `select *` templates on these are now refused. `grep -i report docs/release-notes-2026.08.md` → nothing.
- Impact: Large practices (FHTs and clinics with more than 10k active patients) lose practice-wide lists after upgrading, for example rostered, recall and screening lists, and BC antenatal `select *` exports. Users get a message, so this is not silent, but there is no workaround except splitting reports by hand, and a sequenced template cannot be split because the budget is shared.
- Correction: Add an upgrade note listing the new limits. Make the row, time and CSV limits configurable through properties, keeping the current values as defaults. For a CSV over the limit, either keep showing the HTML and only suppress the export (the old contract, now with the alert that #5553 added to `resultReport.jsp`), or change the message to say the report was not shown. Give column, cell and timeout refusals their own messages.

### S06-3: On the shipped MariaDB driver, report columns of a binary BLOB type now fail ("Data type BLOB cannot be decoded as Reader")
- Severity: Low
- Category: regression
- Confidence: Confirmed (traced in the driver source; not executed)
- Commit: c5add8d9 (#5560), 57054b73 (#5553); triggered by the later 710fb1ac driver switch
- Location: `src/main/java/io/github/carlos_emr/carlos/report/reportByTemplate/ReportResultBudget.java:129-153`; `src/main/java/io/github/carlos_emr/carlos/report/data/ConfiguredReportQuery.java:228-256`; `src/main/java/io/github/carlos_emr/carlos/utility/MariaDbCompatibilityDriver.java:209-219`
- Problem: Both readers send every JDBC type outside their "scalar" list to `getCharacterStream`. In MariaDB Connector/J 3.5.11:
  - A binary BLOB column reports as `VARBINARY`/`LONGVARBINARY` (`BlobColumn.getColumnType`).
  - `ReaderCodec.decodeText` throws `SQLDataException("Data type BLOB cannot be decoded as Reader")` when `column.isBinary()` is true.
  - The compatibility driver adapts `getCharacterStream` only for date/time columns.

  The old code used `getString`, which still decodes BLOBs on MariaDB (`BlobColumn.decodeStringText` → `readString`). Under Connector/J 9.6, where the budgets were validated, `getCharacterStream` worked.
- Evidence: Schema BLOBs holding text: `formBPMH.allergies` and `formBPMH.drugs` (`V1__baseline_schema.sql:4153-4154`), `emailLog.body` (:3107), `eform.errorLog` (:3011). Any Report by Template that selects one of these, or an expression returning a binary BLOB, now shows "An SQL query error has occured Data type BLOB cannot be decoded as Reader" (or a JSON column on a MySQL server). This affects RBT and every `ConfiguredReportQuery` caller.
- Impact: Few reports are affected, but the ones that are fail completely. The error is visible.
- Correction: For `BINARY`/`VARBINARY`/`LONGVARBINARY`/`BLOB` columns (and on a decode `SQLDataException`), use `getString` and keep the length checks, or read `getBinaryStream` with a byte limit. Add a MariaDB-tier test that selects a BLOB column through both readers.

### S06-4: Group-name validation failures in Report by Template show a 500 error page
- Severity: Low
- Category: bug
- Confidence: Confirmed
- Commit: 8def0e6b (#5688)
- Location: `src/main/java/io/github/carlos_emr/carlos/managers/RBTGroupManager.java:87-117`; `.../reportByTemplate/actions/RBTAddGroup2Action.java:63`; `.../RBTAddToGroup2Action.java:65`; `src/main/webapp/WEB-INF/jsp/oscarReport/reportByTemplate/templateGroups.jsp:329-331`; `struts-report.xml:36-39`

- Impact: Only affects administrators creating groups. It is an edge case, but the error is confusing.
- Correction: Catch `IllegalArgumentException` in the add actions, set the message as an `errormsg` request attribute and show it on `templateGroups.jsp`.

### S06-5: Every budget refusal destroys a pooled connection and logs a WARN stack trace when cleanup runs
- Severity: Low
- Category: silent-failure
- Confidence: Plausible
- Commit: c5add8d9 (#5560)
- Location: `src/main/java/io/github/carlos_emr/carlos/db/ReportQueryDeadline.java:104-122`
- Problem: Closing a cursor that was not read to the end aborts the connection, then closes the `ResultSet` asynchronously. In MariaDB Connector/J, `StandardClient.abort` closes the socket. `Result.close()` then calls `skipRemaining()`, because the result is not marked loaded. That read on the closed socket throws `SQLException("Error while streaming resultSet data")`. `closeAborted` logs it as `WARN "Could not close aborted report resources"` with a stack trace, on every row/cell/CSV/HTML/time refusal.
- Evidence: `catch (SQLException | RuntimeException e) { MiscUtils.getLogger().warn("Could not close aborted report resources", e); }`. MariaDB `Result.close(): if (!loaded) { skipRemaining(); }` and `catch (IOException ioe) { throw exceptionFactory.create("Error while streaming resultSet data", "08000", ioe); }`.
- Impact: Normal refusals produce stack traces in the logs, which hides real cleanup failures and causes alert fatigue. Functionally the connection is still invalidated and the pool is not leaked.
- Correction: After an intentional abort, treat close failures as expected and log them at DEBUG; keep WARN for close failures without an abort. To confirm: run the Playwright row-budget step on the MariaDB build and grep `catalina.out`.

## Checked and found OK
- RBT: no silent truncation. JDBC `maxRows` = remaining + 1, the renderer counts rows itself, and a template's own `LIMIT` overriding `SQL_SELECT_LIMIT` is still caught.
- The CSV limit is inclusive at exactly 5 MiB; failed sequences clear `csv-/sql-/resultsethtml-` attributes and do not run later queries.
- Deadlines on MariaDB ≥ 10.1/10.3 (packaging needs ≥ 11.4) are enforced by the server (`SET STATEMENT max_statement_time=…, SQL_SELECT_LIMIT=… FOR`). `abort` sends QUIT, or KILL when the reader holds the lock. Timeouts map to `SQLTimeoutException` (SQLSTATE 70100) → the limit message.
- `MariaDbCompatibilityDriver` translates `setFetchSize(Integer.MIN_VALUE)` to 1, so streaming works on the shipped driver. MariaDB DAO CI runs `ConfiguredReportQuery.read` and an RBT render.
- `ReportQueryDeadline`: the timer is cancelled on close (JDK Delayer removes cancelled tasks), expiry is guarded against close by `synchronized`, and cleanup runs on virtual threads. A double close through `DbConnectionFilter.releaseThreadConnections` is harmless (DBCP guard wrapper).
- `ConfiguredReportQuery`: overloads resolve correctly (int seconds vs long deadline); the overflow row, the identifier limit and the output limit throw rather than truncate; the first column wins for a repeated label, including NULL; `readFirst` sees the end of the result with `maxRows = 1`.
- `BilledProviderReportDao`: a script check confirmed that all 44 SQL strings (22 metrics × dx/service) and their metric-key pairings match main's JSP after whitespace normalisation (deleted-status filters, creator, billing-date vs service-date, distinct counts, age expressions). Parameter order matches; `?n` renumbering is safe (no `?` or `:` in literals).
- Demographic CSV: all four branch conditions, field/caption order, `demographic_no` add/remove and extension latest-only vs per-patient (`order by date_time` ascending, so the last value wins) match main; NULL extension values no longer cause an NPE.
- `RptReportCreator.getSelectField` separator fix (`ret.length() < 8` → `isEmpty()`), caption trimming and save-variant scope match main.
- QBE is untouched by this slice (`RptByExampleData` still has 1,000 rows, 1 M characters and 15 s; the `carlos_report` rules and the grant file are unchanged). The documented QBE numbers are accurate.
- `RBTGroupManager`: linear whitespace strip, code-point length, control-character refusal; every group-name output site in `templateGroups.jsp` and `homePage.jsp` is now encoded for its context; legacy escaped names still round-trip through the hidden fields for add/remove/delete.
- New Spring beans (`ReportConfigurationService`, `BilledProviderReportDao`, `AntenatalReportDao`) are picked up by the broad component scan.

## Declined to judge
- MySQL servers (not packaged): `canUseServerMaxRows` and `canUseServerTimeout` are false. MariaDB Connector/J then applies `maxRows` on the client by calling `skipRemaining()`, which reads and discards every remaining row at the limit. An oversized report would stream the whole result for up to 30 s. Not judged because packaging requires MariaDB ≥ 11.4.
- A race between `DbConnectionFilter.releaseThreadConnections()` and the asynchronous abort contradicts the doc's "connection stays checked out until abort and cleanup finish". With `SQL_SELECT_LIMIT` on the server, any drain is bounded, so the effect is negligible.
- DBCP `removeAbandonedTimeout = 15` s (default `carlos.properties`) is shorter than the 30 s report deadline. When the pool is busy, a 15–30 s report connection can be reclaimed, and the user sees an SQL error instead of the limit message. This is existing pool configuration.
- Overload footgun: `getBoundedReportResultSet(…, int, long, …)` takes an absolute nanosecond deadline and the caller adds the overflow row; `(…, int, int, …)` takes seconds and the method adds it. Passing seconds as a `long` gives an already-expired deadline. No current misuse.

- Sequenced RBT "no results" text is encoded twice (`Encode.forHtml(sql) + "<br/>"`, then `carlos:forHtml` in `resultReport.jsp`), so users see entity text and a literal `<br/>`. Same on main. (Cosmetic; left here rather than in Pre-existing issues.)

### S06-P1: Configured form/demographic report SQL takes raw WHERE fragments from request parameters; the report validator allows UNION and subqueries
- Severity: High
- Category: security
- Confidence: Confirmed
- Pre-existing: yes (present on origin/main)
- Commit: not introduced by the slice; 57054b73 (#5553) rewrote `RptDownloadCSVServlet` and routed the reads through `ConfiguredReportQuery`/`RptReportCreator` but kept the pattern
- Location: release `RptDownloadCSVServlet.java:231-237` (`readSelections`/`readFilters`), `RptFormQuery.java:160-166,205-233`, `RptReportCreator.getWhereValueClauseParameterized` release:249-308 / main:274-332, `LegacyJdbcQuery.validateReportSelectQuery` release:489-508 / main:362-381; same logic on main at `RptDownloadCSVServlet.java:259-331,358-375` and `RptFormQuery.java:151-214`
- Problem: The report filter builder reads request parameters named `value_<n>` whose value is a complete SQL predicate (for example `demographic.demographic_no=${startDate1}`, rendered into the page as a hidden field at `reportFilter.jsp:152`). Only the `${…}` placeholders inside that predicate become JDBC binds (`getWhereValueClauseParameterized`); the surrounding SQL text — column names, operators, parentheses, and any predicate with no placeholder — is concatenated verbatim into the WHERE clause and executed. A value with no `${…}` is passed through unchanged. The only gate before execution is `validateReportSelectQuery`, which (unlike the stricter `validateSafeSelectQuery`) deliberately permits `UNION` and subqueries, rejecting only stacked statements, comments and file-access functions. A caller who can post to these report endpoints therefore controls SQL structure, not just bound values. This is an authenticated SQL-injection / data-exfiltration path into the clinical schema (demographics, billing, labs).
- Evidence: `validateReportSelectQuery` Javadoc: "intentionally allows UNION because existing report templates use UNION". `getWhereValueClauseParameterized` binds only `${…}` occurrences and returns the rest of `value` as literal SQL (`return new ParameterizedSql(value, params)`). The report-typed-queries Playwright check itself posts `value_1=demographic.demographic_no=${…}` as a form field, confirming these are request-supplied predicate strings.
- Impact: A logged-in user with report access (see S06-P2 for how weak that gate is) can read or correlate arbitrary PHI through crafted filter predicates and UNIONs. High because it reaches the full clinical database under an ordinary session.
- Correction: Do not accept SQL predicate text from the client. Represent filters as a server-side definition (column + operator + bound value chosen from an allowlist) and build the WHERE clause from that, binding every value. If request-supplied fragments cannot be removed immediately, run these reports through the restricted `carlos_report` reporting account (as Query by Example already does) so injection cannot reach writable or sensitive tables, and tighten the validator for these entry points.

### S06-P2: `reportDownload` servlet enforces only "a session exists", not the report privilege
- Severity: Medium
- Category: security
- Confidence: Confirmed
- Pre-existing: yes (present on origin/main)
- Commit: not introduced by the slice; 57054b73 (#5553) rewrote the servlet and kept the gate
- Location: release `RptDownloadCSVServlet.java:72-74` (`HttpSession session = request.getSession(false); if (session == null) return;`); main `:63-66`; mapping `web.xml:637-640` (`/report/reportDownload`); contrast the paired JSP gate `reportResult.jsp:7-10` which requires `_report,_admin.reporting` read
- Problem: The servlet's only access check is that an HTTP session exists. It calls no `SecurityInfoManager.hasPrivilege`.
