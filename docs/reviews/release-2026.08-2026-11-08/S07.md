## Findings

### S07-1: Two BC billing release checks now look for "button" roles the JSPs never render, so the BC suite fails
- Severity: Medium
- Category: test-gap
- Confidence: Confirmed
- Commit: 5f9ca145 (#5518)
- Location:
  - `scripts/billing-bc-associations-playwright-checks.js:50`, `:58`
  - `scripts/billing-bc-private-codes-playwright-checks.js:142`
  - markup: `src/main/webapp/WEB-INF/jsp/billing/CA/BC/billingSVCTrayAssoc.jsp:123`, `src/main/webapp/WEB-INF/jsp/billing/CA/BC/billingPrivateCodeAdjust.jsp:105`
- Problem:
  - The commit changed the deployed checks from `getByRole('link', {name:'Edit'|'Delete'})` to `getByRole('button', …)`.
  - The JSPs deliberately kept the row actions as `<a href="#" onClick=…>Edit</a>` / `Delete`. The comment there reads "NOSONAR Web:S6844 - the link markup displaytag rendered … kept as it looked".
  - An `<a href>` has the ARIA role `link`, and nothing on these pages adds `role="button"` (only `carlos-tables.js` sort headers get it).
  - The standalone fixture (`dependency-tables-playwright-checks.js:15`) renders row actions as real `<button>`s, which is why the mismatch never showed up.
- Evidence:
  - I ran Playwright 1.61.1 against the exact markup `<tr><td>12345</td><td><a href="#" onClick="…">Edit</a><br /><a href="#" …>Delete</a></td></tr>`. Result: `getByRole('button',{name:'Edit'})` count 0, `getByRole('link',{name:'Edit'})` count 1, `getByRole('button',{name:'Delete'})` count 0.
  - In `playwright-suite.json`, both checks are `tiers:["core"]`, `provinces:["BC"]`, with no `expectedFailure`.
  - The release plan's `packaged-full` browser lane runs every check for both ON and BC.
  - Only 5f9ca145 touched these scripts in the release range.
- Impact:
  - The BC packaged-full qualification run fails at the Edit and Delete steps (locator timeout). That blocks release readiness or invites an `expectedFailure` pin.
  - Meanwhile the only end-to-end coverage of the migrated BC tray-association and private-code tables (create, reopen, delete) is lost.
- Correction:
  - Revert the three selectors to `getByRole('link', …)`, since the markup was intentionally kept.
  - Alternatively, convert the row actions to `<button type="button">` and drop the NOSONAR comment.
  - Either way, make the `dependency-tables` fixture use the same row-action markup as the JSPs.

### S07-2: Measurement graphs now need the eForm render browser and share its 2 slots; failures show only a broken image
- Severity: Medium
- Category: silent-failure
- Confidence: Confirmed (mechanism); how often it happens depends on load
- Commit: 5f9ca145 (#5518)
- Location:
  - `src/main/java/io/github/carlos_emr/carlos/eform/util/BrowserChartRenderer.java:30,35,57-67,88-91`
  - `src/main/java/io/github/carlos_emr/carlos/encounter/oscarMeasurements/pageUtil/MeasurementGraphAction22Action.java:134-141`
  - `src/main/java/io/github/carlos_emr/carlos/encounter/oscarMeasurements/pageUtil/ScatterPlotChartServlet.java:107-116`
  - `src/main/java/io/github/carlos_emr/carlos/eform/util/EFormBrowserPdfService.java:190-192`
  - `src/main/java/io/github/carlos_emr/carlos/eform/util/EFormBrowserRendererStartupValidator.java:91-92`
- Problem: JFreeChart drew every `/encounter/GraphMeasurements` PNG in the JVM. Now each image:
  - launches a fresh headless Chromium through the `carlos-emr-render-browser` chromedriver service;
  - competes for the same `RENDER_SLOTS` (2, fair) used for eForm print, fax and archive;
  - waits up to 30 s, with 16 waiters, then answers HTTP 503 with no body.
- No diagnosis is possible in three places:
  - Every failure cause (renderer down, both slots busy with eForm renders of up to 90 s, chromedriver version mismatch, a draw-script exception) is logged only as `Measurement graph unavailable (IOException)`.
  - `BrowserChartRenderer` drops the cause message, e.g. "Chart renderer is busy" or `RenderBrowser`'s PHI-free "HTTP 500, javascript error".
  - The renderer-readiness warning still says only "eForm print/fax/archive will fail".
- Evidence:
  - `if (!acquired) throw new IOException("Chart renderer is busy");`
  - `log.warn("Measurement graph unavailable ({})", unavailable.getClass().getSimpleName()); … response.sendError(SC_SERVICE_UNAVAILABLE)`
  - `logger.warn("Chart rendering failed ({})", failure.getClass().getName()); throw new IOException("Chart rendering failed");`
- Impact:
  - On every packaged install, a render-browser outage now also takes down the drug-profile timeline (`rx/chartDrugProfile.jsp`), the lab-value graph (`lab/CA/ON/labValuesGraph.jsp`) and the flowsheet, Health Tracker and History plot pop-ups.
  - During eForm fax or print bursts, graphs can intermittently show as broken images.
  - Clinicians get no message; admins cannot tell "busy" from "down" from "draw bug".
  - Standalone WAR deployments without chromedriver lose all graphs (they worked before).
  - None of this is in the release notes (see S07-4).
- Correction:
  - Log the redacted cause message, or at least a fixed reason code (busy, unavailable, draw-failed), at WARN.
  - Say in the readiness warning and the release/upgrade notes that measurement graphs depend on the render browser.
  - Consider reserving capacity so chart traffic and eForm PDFs cannot starve each other (separate semaphore or priority), and/or reuse one browser session for short chart renders.

### S07-3: A single reading (or constant series) between about 4.5 million and 67 million now fails with 503 instead of drawing
- Severity: Medium
- Category: regression
- Confidence: Confirmed
- Commit: 5f9ca145 (#5518)
- Location:
  - `src/main/webapp/library/chartjs/carlos-chart-draw.js:311-327` (the 1e-8 minimum-range widening), `:397-401` (the new guard)
  - consumer: `MeasurementGraphAction22Action.java:134-141`
- Problem:
  - With one value v, or all values equal, the value axis is widened to v ± 5e-9, so the selected tick unit is about 5e-10.
  - `Math.ceil(lower / unit)` then exceeds `Number.MAX_SAFE_INTEGER` once |v| is above about 4.5e6.
  - The new guard `if (!Number.isSafeInteger(first) || … ) throw new Error('Chart numeric axis has too many ticks')` aborts the draw.
  - The "widening lost to rounding" fallback only starts at about 6.71e7.
  - JFreeChart 1.5.6 does the same arithmetic in doubles (`calculateVisibleTickCount`, `MAXIMUM_TICK_COUNT` guard) and never throws. It drew the point, with its item label on lab charts, over a degenerate axis.
- Evidence (bundled Chart.js plus `carlos-chart-draw.js` in Chrome, 1000×600, the lab-chart style `actualLabChart` produces):
  - Draws: single 37, 99, 4,000,000, 4,500,000, 67,200,000, 70,000,000.
  - `ERROR: Chart numeric axis has too many ticks`: single 4,510,000, 5,600,000, 9,000,000, 12,500,000, 45,000,000, 66,000,000, −6,000,000; two equal readings of 12,500,000; the medication-combined chart with one 12,500,000 lab value.
  - The JFreeChart fixtures cover only a single 70.0 reading and a varying 1.2e8–3.5e8 series.
- Impact:
  - A clinician graphing a patient's first viral load (HIV RNA copies/mL, HCV RNA or HBV DNA IU/mL, routinely in the millions) gets a broken image. This happens only when the result carries no "low-high" reference range, which is common for "<20"-style ranges.
  - Under JFreeChart the same request produced a chart showing the point.
  - This is distinct from known #5814 (the invisible marker and unreadable ticks, which both renderers share).
- Correction:
  - Mirror JFreeChart: compute the tick count in doubles, and when it is unusable draw no ticks or a single tick at v instead of throwing.
  - Alternatively, apply the 10% widening whenever v/unit is outside the safe-integer range.
  - Add fixtures for single values of 5e6, 1.25e7, 4.5e7 and a negative value.

### S07-4: Release and upgrade notes say nothing about #5518's format, dependency and customisation-breaking changes
- Severity: Low
- Category: docs
- Confidence: Confirmed
- Commit: 5f9ca145 (#5518)
- Location: `docs/release-notes-2026.08.md` (no mention); `docs/dependency-footprint-5472.md:142-143`
- Problem: The notes omit:
  1. Report by Template and Clinical Reports "Export to XLS" now download `oscarReport.xlsx` (OOXML content type) instead of BIFF8 `oscarReport.xls`.
  2. Measurement graphs require the render-browser service and answer 503 without it (S07-2).

  5. Table paging and sorting are now client-side, so bookmarked displaytag `d-…-p/s/o` URLs no longer select a page or sort.
- `dependency-footprint-5472.md` still says "These changes are proposed for review; #5472 requires sign-off on output differences before merging". The change is merged, and #5472 (still open) records no sign-off.
- Evidence: `rg -i 'xlsx|chart|displaytag|selenium' docs/release-notes-2026.08.md` finds nothing.
- Impact: Operators and integrators are not warned about the file-format change, the new runtime dependency, or broken local customisations.
- Correction: Add an upgrade-notes section covering items 1–5, extend #5747/#5746, and update the footprint doc's status line.

## Checked and found OK
- **No remaining references to the removed libraries:** no `<display:`/`display-el:` tags, no displaytag taglib declarations, no `org.jfree`, `org.openqa`, `org.apache.poi` or `org.displaytag` imports in `src/main`, and no Spring, Struts, web.xml or log4j references. displaytag CSS files still exist and are still used.
- **Dependency-lock delta:** removed displaytag, checker-qual, auto-service-annotations, jfreechart and 8 Selenium jars; poi, poi-ooxml, poi-ooxml-lite, commons-compress, commons-math3, SparseBitSet and curvesapi are now test scope. No main code uses commons-compress. The JSTL API 3.0.2 is now declared at compile scope and the EL API stays `provided`.
- **Converted tables, all 26:**
  - Header and cell counts match, including the `caisi:isModuleLoad`, `security:oscarSec` and `IsPropertiesOn` columns.
  - Sortable flags, `defaultsort`/`defaultorder`, `pagesize`, `sort.amount=list` and banner placement are preserved.
  - Empty messages are preserved. Boolean getters are primitive `isX()`. No `_rowNum` or export features were used.
- **Table security and accessibility:** all new output is encoded (`forHtml`, `forHtmlAttribute`, `forUriComponent`, `forJavaScriptAttribute`). Displaytag printed raw values before, so this is a security improvement. `Site.getCssBgColor` is regex-sanitised.
- **`carlos-tables.js`:** DOM APIs only, no `innerHTML`, CSP-friendly external script; nested tables handled; hidden-page controls are disabled and unchecked, so hidden rows are never submitted; BigInt integer comparison; nulls sort first; stable sort.
- **Table assets fragment:** keys present in all 5 locales; included exactly once per page (by test); static paths excluded from Struts.
- **`SpreadsheetExport`:** `_x005F_` and control-character escaping (traced overlapping cases); unpaired surrogates; row and column limits (an improvement over HSSF's 65,536 rows / 256 columns); validation runs before any byte for `write()`; Woodstox is the runtime StAX implementation and its `close()` does not close the ZIP stream.
- **Chart data mapping versus main:**
  - The same, by design: daily `addOrUpdate`, BP diastolic-then-systolic order, A1c-as-percent, the y-axis title from `getTypeDescription`, the secondary axis.
  - Fixed: CML lab dates (previously a `ParseException`), LOINC values now plotted, reference ranges looked up by measurement ID, empty data now drawn as an empty chart instead of returning 500.
- **Chart rendering:** PHI goes into Chromium only as script arguments; the render-browser unit runs `--log-level=WARNING`, so arguments are not logged; the Debian package depends on `fonts-dejavu-core`.
- **`RenderBrowser`:** wire parity with Selenium; Long/Double result conversion is compatible with the `instanceof Number` readers; the interrupt-safe DELETE; no proxy, no redirects, HTTP/1.1; the 90 s read timeout is kept.
- **#5646 (`jobTypes.jsp`):**
  - The form is serialised before inputs are disabled; out-of-range pages are clamped.
  - A missing job type returns 500, which leads to the load-error alert, so the editor does not get stuck in "loading".
  - None of the other 38 DataTables initialisations re-initialises on refresh (all run at page load or retrieve only).

## Declined to judge
- Exact chart pixel parity for every variant; I relied on the recorded fixtures and the CI chart-draw check. Two possible cosmetic differences:
  - Item labels use JS `toFixed` (rounding exact binary ties half-up) where Java `DecimalFormat` rounds HALF_EVEN, e.g. 0.125 → "0.13" instead of "0.12".
  - Month names and number grouping are hard-coded English (en-US), whereas JFreeChart used the JVM default locale (e.g. en_CA "Sep." vs "Sep").
- Whether maintainers accepted #5472's output differences outside GitHub (a process question).
- `RenderBrowser` behaviour against a real chromedriver in edge cases (code reading only); the opt-in `java-browser-pdf` lane covers it.
