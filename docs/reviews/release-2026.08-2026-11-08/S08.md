## Findings

### S08-1: Messenger can no longer attach the patient's current encounter; only a frozen "Historical encounter" (or nothing) remains, with no modern replacement
- Severity: Medium
- Category: regression
- Confidence: Confirmed
- Commit: 9ee16eaa (#5602)
- Location: `src/main/java/io/github/carlos_emr/carlos/messenger/pageUtil/MsgPdfAttachmentResolver.java:63-66,135-145`, `src/main/webapp/WEB-INF/jsp/messenger/generatePreviewPDF.jsp:94,164-173,297-310`, `src/main/java/io/github/carlos_emr/carlos/casemgmt/service/CaseManagementManagerImpl.java:279-284`, `src/main/java/io/github/carlos_emr/CarlosProperties.java:180-185`
- Problem: Until this release the Debian skeleton (built from `src/main/resources/carlos.properties`, which on main has no `AbandonOldChart`) ran every packaged install with the code default `false`, so each modern note/CPP save was mirrored by `eChartDao.saveEchart` into a new `eChart` row holding the running encounter text and CPP. The Messenger chooser's "Encounter" item (latest `eChart` row → `/encounter/ViewEcharthistoryprint`) therefore attached the patient's recent notes. With mirroring forced off, `eChart` freezes at the upgrade: the item now shows only "Historical encounter: <cutover timestamp>", and patients first charted after the cutover (every patient on a fresh install) get no encounter item at all. The chooser's `Item` enum has only DEMOGRAPHIC, ENCOUNTER (legacy store) and PRESCRIPTIONS, and the modern chart has no other "send notes via Messenger" path, so the capability is lost rather than migrated. #5599's pre-merge review asked to "hide or repoint" this item; #5602 relabelled it instead.
- Evidence: `case ENCOUNTER: EChart chart = eChartDao.getLatestChart(demographicNo); if (chart == null || ... || !hasClinicalContent(chart)) return Optional.empty(); ... "messenger.generatePreviewPDF.historicalEncounter"`; `git show origin/main:src/main/resources/carlos.properties | grep -i abandon` → no key; `persistNote`: `if (!Boolean.parseBoolean(properties.getProperty("AbandonOldChart", "false"))) return eChartDao.saveEchart(...)` — now never taken.
- Impact: Every upgraded Debian clinic: a provider attaching chart notes to an internal message gets an old dated snapshot or nothing. Not silent (labelled), but a working workflow disappears. #5762 lists the relabel only as a release-notes gap.
- Correction: Add a current-encounter item rendered from a modern chart print route (patient's current notes/CPP, same `_eChart r` + record-access checks), keep the historical item separately labelled, and document the change in the release notes (#5762).

### S08-2: The retired CAISI legacy editor still renders and accepts typing; every Save/Sign ends on a generic "CARLOS Error: 410" page and the text is lost
- Severity: Low
- Category: silent-failure
- Confidence: Confirmed
- Commit: 9ee16eaa (#5602)
- Location: `src/main/webapp/WEB-INF/jsp/encounter/Index2.jsp:188-202,245-261`, `src/main/java/io/github/carlos_emr/carlos/encounter/pageUtil/EctSaveEncounter2Action.java:224-227` (and stale class Javadoc `:90-95`), `src/main/webapp/WEB-INF/jsp/error/errorpage.jsp:70-96,205,250-252`
- Problem: Retirement is enforced only when the editor posts. `IncomingEncounter` → `Index2.jsp` still renders the full editor under CAISI when the request carries `casetoEncounter` (no redirect at :196), with Save, Sign/Save/Exit, Sign/Save/Bill, Verify/Sign and Split Chart enabled. Each press is a native POST answered with `sendError(410, "The legacy encounter editor is retired. Use the modern chart…")`, but `errorpage.jsp` shows that message only when `DISPLAY_ERROR` is on and response sanitization is off. Production users see only "CARLOS Error: 410", and the unsaved typing is lost. The class Javadoc still documents 409/412 conflict answers that can no longer occur.
- Evidence: `if (request.getParameter("casetoEncounter") == null) { … sendRedirect(hrefurl); return; }` (else the editor renders); `<p>CARLOS Error: ${carlos:forHtml(_responseStatus)}</p>` with `_errorMessage` set only `if (_displayError)`.
- Impact: Small reach. No shipped link carries `casetoEncounter` (the `navigation.jsp:248` `eURL` is built and never emitted), so only bookmarked or typed CAISI URLs reach it. Those users lose work with an unexplained error. The only browser check for the editor (`legacy-encounter-editor-isolation`) now always SKIPs.
- Correction: Refuse at render time: have `IncomingEncounter`/`Index2.jsp` ignore `casetoEncounter` and forward to `casemgmt/ViewForward`, or render a read-only "retired, use the modern chart" page. Answer the 410 with a fixed explanatory page. Update the Javadoc. Pin it with a unit or JSP test.

### S08-3: The new record-access check in the consult "other medications" prefill throws mid-page and truncates the consultation form
- Severity: Low
- Category: bug
- Confidence: Plausible (code path confirmed; post-commit rendering outcome not executed)
- Commit: 9ee16eaa (#5602)
- Location: `src/main/webapp/WEB-INF/jsp/encounter/oscarConsultationRequest/ConsultationFormRequest.jsp:2445-2459`
- Problem: For a new request with `currentMedications=otherMedications`, the added scriptlet does `throw new SecurityException("Patient record access denied")` about 2,400 lines into the page, after thousands of lines of markup and script have been flushed. Jasper cannot forward to an error page once the response is committed, so the user gets a page cut off at the Medications section. Missing `_eChart`/`_casemgmt.notes` rights get a graceful banner instead (`consultationCppUnavailable`). With the default `currentMedications` the same record-restricted user gets the whole page (see Out of scope).
- Evidence: `if (!securityInfoManager.isAllowedAccessToPatientRecord(loggedInInfo, Integer.valueOf(demo))) { throw new SecurityException(...); }` inside the `<form>` body; the page's only other record check is for fax (`:223`).
- Impact: Rare: it needs the non-default `currentMedications=otherMedications` and a record-restricted patient. The result is a broken page and an exception in the log rather than a clear refusal.
- Correction: Treat missing record access like missing rights (set `consultationCppUnavailable`, skip the prefill), and enforce record access once in the gate or page header before any patient data renders.

## Checked and found OK
- `EctSaveEncounter2Action`:
  - Every check runs before the 410: global and patient `_demographic w`, record access, POST-only, button whitelist, `_eChart w`, `_eChart.verifyButton`, identifier validation.
  - Exit writes only `encounterWindow`.
  - It is registered as an unconditional mutator (`MutatorActionGetRejectionContractUnitTest.java:266,819`).
  - CSRF is covered by the global CSRFGuard.
- The override sits in the shared 1-arg `getProperty`, so `getProperty(k,d)`, `isPropertyActive` and `getBooleanProperty` agree. All nine legacy branches now take the modern path, and every eChart writer is gated or behind the 410.
- Static init order is fixed (`activeMarkers` before the singleton). The constructor path (LogSafe, MiscUtils, `PathValidationUtils.resolveConfiguredFile`) never re-enters `getInstance()`.
- `ensureModernChartRollbackSafety`:
  - a true flag needs only a shared-lock read, so 0640 root:carlos works;
  - the exclusive lock re-reads before writing;
  - it only appends, on the same inode;
  - `parseBoolean` matches beta6 readers, so treating `yes`/`true␠` as rollback-unsafe is correct.
- Java and postinst append identical bytes under POSIX record locks. Startup runs before the Spring listener (web.xml order), and failure aborts the deploy.
- Chart entry is unchanged by the commit. All `IncomingEncounter` links (day sheet, search, demographic, labs, HRM, Rx, Messenger, PMM) redirect to `casemgmt/ViewForward`; only CAISI with `casetoEncounter` (unlinked) renders the editor.
- Historical prints check patient ownership before copying fields and require `_eChart r` plus record access. The history report gate requires `_report r`, record access and patient `_demographic r`. The header link requires `_report r`.
- `CppTextLoader`:
  - its patient-scoped request wrapper stops another patient's `chartContext` from choosing the program;
  - it requires `_demographic`, `_eChart` and `_casemgmt.notes` read;
  - it reads the latest non-archived revisions and applies program `filterNotes`;
  - the `IssueType.name()` lookup relies on the CI collation (`issue` is utf8mb4_general_ci), the same pattern as `fetchIssueNote`;
  - default ON/BC roles hold `_casemgmt.notes`.
- The Messenger 400 is sent before staging, earlier attachments are kept, and the capture wrapper never commits the real response. Since `eChart` is frozen, a stale-chooser 400 is practically unreachable.
- New output is encoded (`carlos:encode`, `forHtml`, `forHtmlAttribute`, `forUriComponent`). No PHI is logged: the warning logs a sanitized config value, and the error names the file path only.
- Stored preferences: `hide_old_echart_link_in_appointment` still hides the modern E link (unchanged). `encounterWindow` rows are only used by the dormant editor. Historical `eChart` rows are no longer updated in place (`updateEchartOngoing` is gated), so they are now immutable.
- #5518 interaction: it replaced graph and table libraries (JFreeChart to Chart.js, displaytag). It touched the same bundles and devcontainer file but none of the cutover code. All four #5602 keys survive in every bundle; no conflict found.
