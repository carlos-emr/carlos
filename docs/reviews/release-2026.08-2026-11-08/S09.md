## Findings

### S09-1: Lifecycle doc and wrapper javadoc contradict the shipped code
- Severity: Low
- Category: docs
- Confidence: Confirmed
- Commit: decec19b (#5495) (doc table, privacy behaviour change), 3bd9b5ec (#5682) (logout publication change)
- Location: `docs/response-filter-lifecycle.md:18`, `src/main/java/io/github/carlos_emr/carlos/commn/printing/PrivacyStatementAppendingFilter.java:69-70`, `src/main/java/io/github/carlos_emr/carlos/app/LogoutBroadcastFilter.java:735-737,1060`
- Problem: (a) The ownership table says JavaMelody "Adapts writer output to its monitoring stream". That was
  JavaMelody 2.6.0 (main): `FilterServletResponseWrapper.createWriter()` built a PrintWriter over
  `getOutputStream()`, so the sanitizer saw a stream. In the 2.9.0 the release ships,
  `CounterServletResponseWrapper.createWriter()` returns `new CounterResponseWriter(getHttpServletResponse())`,
  i.e. it calls the downstream `getWriter()`; every JSP/writer page now reaches the sanitizer's writer capture.
  (b) The privacy filter's class javadoc still says the once-per-request guard is "a temporary session attribute if
  session is available, or request attribute otherwise"; decec19b made it request-only. (c) LogoutBroadcast's wrapper
  javadoc still says "Content-Length is deferred while wrapped" / "Caches string Content-Length header values until the
  final append decision is known"; since #5495/#5682 stream lengths and known-non-HTML writer lengths are published at
  once.
- Evidence: javamelody-core-2.9.0-sources `CounterServletResponseWrapper.createWriter(){ this.writer = new CounterResponseWriter(getHttpServletResponse()); }`, `CounterResponseWriter(HttpServletResponse r){ this(r.getWriter()); }`; 2.6.0 has no `createWriter` override. Privacy `isConfidentialtyNotePrinted()` uses only `request.getAttribute/setAttribute`. Logout `setContentLengthLong`: `if (responseOutputStreamObtained || (responseWriterObtained && isKnownNonHtml())) applyDeferredContentLength();`.
- Impact: The doc is the reference CLAUDE.md points maintainers to before touching these filters. Its JavaMelody row
  leads a reader to conclude that, in production, pages reach the sanitizer as pass-through streams (not inspected
  at 2xx and replayed differently), which is the opposite of what 2.9.0 does. That is exactly the kind of wrong
  model that caused earlier filter regressions.
- Correction: Update the table row (JavaMelody 2.9.0 forwards writer calls to the downstream writer and counts them;
  only stream calls go through its counting stream). Fix the privacy class javadoc (request attribute only) and the
  two logout javadoc sentences (streams and known non-HTML writers publish at once; only HTML/unknown writer lengths
  wait for the append decision).

### S09-2: Decorated static HTML keeps the bare file's HEAD length and validators
- Severity: Low
- Category: bug
- Confidence: Confirmed (traced in code; not executed)
- Commit: decec19b (#5495), 3bd9b5ec (#5682)
- Location: `src/main/java/io/github/carlos_emr/carlos/commn/printing/PrivacyStatementAppendingFilter.java:194-198` (no-channel branch → `completeWithoutStatement()`), `:378-383` (`completeWithoutStatement()` publishes the pending length), `:199-200` (decoration path); `src/main/java/io/github/carlos_emr/carlos/utility/ResponseDefaultsFilterResponseWrapper.java:106` (weak → strong ETag)
- Problem: Before #5495, the length DefaultServlet set framed the body, so the appended notice was cut off and static
  `.html/.htm` responses were byte-identical to the file. Now the length is held back and the notice is really
  delivered on GET (file + ~800 bytes, chunked). The entity metadata was not adjusted:
  - HEAD: DefaultServlet's `doHead` opens no channel but sets type and `setContentLengthLong(fileLength)`. The privacy
    filter reaches `completeWithoutStatement()` ("no channel") and publishes the file length. So HEAD advertises n
    while GET of the same URL returns n plus the notice.
  - Validators: DefaultServlet's ETag/Last-Modified describe the file only, and ResponseDefaultsFilter's default
    `forceStrongETag` turns `W/"…"` into a strong ETag. When an operator changes `confidentiality_statement.vN`, the
    representation changes but the validators do not, so conditional GETs return 304 and browsers keep printing the
    old notice. A strong ETag plus `Accept-Ranges` also invites the Range/If-Range requests behind #5782.
- Evidence: Tomcat 11.0.27 `DefaultServlet.doHead` → `serveResource(…, serveContent=false)`; full branch:
  `if (resource.isFile() && contentLength >= 0 && (!serveContent || …)) response.setContentLengthLong(contentLength)`.
  Privacy doFilter: `if (!isResponseWriterObtained() && !isResponseOutputStreamObtained()) { completeWithoutStatement(); }` → `contentLength.publishPending()`.
- Impact: Minor protocol inconsistency on about 37 static pages (help, calculators, close/notice pages). HEAD users
  (link checkers, proxies) see a wrong length. After a statement change, cached printouts can show an outdated
  confidentiality notice. Nobody would notice without comparing responses. Same root cause as #5782 (206).
- Correction: Fix it with #5782. Either do not decorate DefaultServlet resources and non-200 responses, or, when
  decorating, drop `ETag`, `Last-Modified` and `Accept-Ranges`. Do not publish the metadata length for a no-channel
  (HEAD) response whose type/route GET would decorate: remove it, or add the notice length. Add a static `.html`
  fixture plus HEAD and Range cases to `ResponseFilterLifecycleIntegrationTest`.

## Checked and found OK
- `DeferredContentLength`: transitions are consistent; CSRF `publishNow` is never reached with a pending value
  (acquisition always publishes pending first; writer-capture lengths are suppressed).
- Retraction cascades: a wrapper's remover calls `super.setHeader("Content-Length", null)`, every outer wrapper maps
  that to `remove()`, and Tomcat's coyote `checkSpecialHeader` turns null into `setContentLength(-1)`. Retraction is
  skipped once committed, and Tomcat then also ignores the late `setContentType`, so no response is decorated under a
  stale length.
- #5682: untyped streams publish at acquisition and retract if the type becomes HTML before commit. A type set after
  the declared bytes are written is ignored by the facade (app-committed), so the response is not decorated. No case
  was found where a published length later frames a rewritten body.
- Forward path with `suspendWrappedResponseAfterForward=false`: `resetBuffer()` then "close anyway"
  (`getWriter().close()` / `getOutputStream().close()`) is absorbed by the shields; nested forwards discard the prefix
  once; idempotent CSRF injection.
- `sendError`/`sendRedirect`: not intercepted by logout/privacy; lengths published afterwards are ignored by a
  suspended facade; error pages use the ERROR dispatch (sanitizer and COOP only).
- 304 (no type/channel) is not decorated; 204/304 bodies are dropped by Tomcat; no `startAsync` anywhere and the
  sanitizer is not async-supported; CARLOS wrappers are not INCLUDE-mapped and ApplicationHttpResponse swallows
  header/reset calls from includes (FormTransportContainer uses include).
- Large downloads: streams pass through every wrapper unbuffered, and the sanitizer's capture is bounded. The slice
  adds no buffering.
- Security: no sanitizer bypass through the new reset semantics; LoginFilter matching is tight; no PHI in new log
  lines (URIs and header values are `LogSafe`-sanitized).
- Tests: the lifecycle IT runs real Tomcat 11, JavaMelody and CSRFGuard in `web.xml` order (read from the
  descriptor), both shipped context settings, and runs in CI (`make install --run-tests`). Only CsrfGuardFixture calls
  `CsrfGuard.load`, and it restores the singleton. `scripts/login-playwright-checks.js` has no expectation affected by
  this slice.

## Out of scope but notable
- The CSRF FORWARD capture (`CharArrayWriter`) is unbounded. A large HTML page forwarded to a JSP is held whole, plus
  the `toString`/`substring` copies, before the sanitizer's bounded capture. The doc's "bounded capture" paragraph
  applies to the sanitizer only. This predates the slice; the new `resetBuffer()` override slightly reduces it.
- `CsrfGuardScriptInjectionFilter.writeToResponse` stream fallback still uses the raw `getCharacterEncoding()` with
  `content.getBytes(encoding)`, so an unusable name throws `UnsupportedEncodingException`. decec19b's "centralize
  charset fallback" did not migrate it. Reachable only via stream-then-forward plus a bad charset name.
- Authenticated HEAD of a static HTML page: LogoutBroadcast opens no channel and appends its script, so HEAD's
  Content-Length is the script's length. This is pre-existing.
- PrivacyStatementAppendingFilter sets a 1 MiB container buffer on every non-Struts response, every static asset
  included. This is pre-existing.
