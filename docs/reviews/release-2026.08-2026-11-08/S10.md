## Declined to judge
- Config-dependent WCB/Demographic entity hydration. The WCB enrichment now loads the whole `wcb` row, including NOT NULL zero-default DATETIME/DATE columns (`formCreated`, `formEdited`, `w_dob`, `w_servicedate`, `w_doi`), where main read only three text columns. With the packaged/O19 `db_name` (`zeroDateTimeBehavior=round`) this is harmless. If an install's JDBC URL omits `zeroDateTimeBehavior`, `MariaDbJdbcCompatibility` defaults to `EXCEPTION`. A legacy zero-date WCB row would then fail to load: PDF reports would be silently truncated at that bill, and the CSV would return 500. I did not treat this as a finding because it requires a non-default config and the same entity is already loaded by the WCB form list on main.
- MariaDB Connector/J and the compatibility-driver behaviour that these queries rely on: `table.column` label lookup (`b.billingtype`, `teleplanS00.t_aja1`), `getObject(LocalDate)` through the compat proxy, and `useOldAliasMetadataBehavior` / `round`. These belong to the 710fb1ac slice. The `bc-flyway` lane exercises them only with the test URL (`CONVERT_TO_NULL`, no alias option).

### S10-P1: BC billing PDF reports are silently truncated at the first unreadable row
- Severity: Medium
- Category: silent-failure
- Confidence: Confirmed
- Pre-existing: yes (present on origin/main)
- Location (main → release): `MSPReconcile.getBillsByType` catch `MSPReconcile.java:1299-1300 → :1382-1383`; `getPayments` `:1502-1503 → :1637-1638`; `getPrivatePayments` `:1582-1583 → :1708-1709` and `:1655-1656 → :1766-1767`; non-strict `reportReadFailure` `→ :138-144`; caller `CreateBillingReport2Action.java:104,115,195,225 → :118,129,209,239`
- Problem: In legacy PDF mode (`new MSPReconcile()`), every row-level failure inside the report loop is caught after the loop, logged as `"Error"`, and the method returns the rows built so far. Failures covered include a DB read, a `NumberFormatException` re-thrown from `getAmountOwing` (release `:1336-1341` re-throws in non-strict mode), a null `service_date`, and a provider or S00 lookup. The PDF is then filled from that partial list. Bill counts, patient counts and `amtSubmitted`/totals are computed from the truncated list.
- Evidence: `} catch (Exception e) { reportReadFailure(e); } return billSearch;` with `reportReadFailure` → `MiscUtils.getLogger().error("Error", exception)` when `!failOnReadError`. #5662 (closed) showed that legacy rows with blank or malformed amounts and service dates exist in the field. Its fix (#5670) made only the strict CSV path keep such rows.
- Impact: Invoice, Accounts Receivable, Write-off, Rejected and Payments/Refunds PDFs can show a plausible but incomplete report with understated totals. No message appears in the UI. Billing staff cannot tell that the report is incomplete.
- Correction: In PDF mode, either fail the request with a deliberate error before headers are sent, or keep the row with a visible "unreadable" marker, matching the CSV contract. Do not return the partial list as if it were complete.

### S10-P2: BC billing PDF actions return an empty or broken attachment with HTTP 200 instead of an error
- Severity: Medium
- Category: silent-failure
- Confidence: Confirmed
- Pre-existing: yes (present on origin/main)
- Location (main → release):
  - `CreateBillingReport2Action.java:111 → :125` (`cfgHeader` sets `application/pdf` and `Content-Disposition: attachment` before any query runs)
  - REP_PAYREF: `:195 → :209`; provider check `MSPReconcile.java:1721` (main) → `BillingmasterDAO.java:627,635` + `MSPReconcile.java:1634-1635`
  - REP_MSPREMSUM swallow: `:190-191 → :204-205`
  - `OscarDocumentCreator.java:227-229 → :203-205` (`catch (JRException ex) { log }`)
- Problem:
  - (a) Choosing a provider without an OHIP/MSP practitioner number on the Payments/Refunds PDF throws `"Provider must have ohip no!"`. The PDF attachment headers are already set and nothing catches the exception (the `try` has only `finally`). The user gets a download, not a readable validation message.
  - (b) For REP_MSPREMSUM, a `SQLException` while acquiring the report connection is logged and swallowed, and `NONE` is returned, so the user gets an empty attachment.
  - (c) `OscarDocumentCreator.fillDocumentStream` swallows every `JRException`. This includes expression failures from a single bad row, such as `new Double($F{amount})` on a blank amount in `pdf_rep_invoice`/`pdf_rep_wo`/`pdf_rep_rej`, or `$F{t_s00type}.equalsIgnoreCase(...)` on a null in `pdf_rep_msprem`. Every BC billing PDF in this action then returns a 0-byte or truncated file with status 200.
- Evidence: see the code at the locations above. This violates the CLAUDE.md "Direct Response Actions" rule that the action must own its error response. #5777 covers only the REP_MSPREM read failure; #2064 tracks the general cleanup.
- Impact: Users get blank or corrupt "PDF" downloads with no explanation. One bad legacy row makes a whole report unavailable, and only the server log records why.
- Correction: Run the queries and the Jasper fill into a buffer before calling `cfgHeader`. Let `fillDocumentStream` propagate `JRException`, or return a status the caller checks. On failure, answer `sendError(...)` (400 for the missing-OHIP validation case) and `return NONE`.

### S10-P4: The Payments/Refunds PDF drops S00 rows with zero or unparseable paid amounts, including their adjustments
- Severity: Medium
- Category: bug
- Confidence: Confirmed (code path); how often it occurs is plausible
- Pre-existing: yes (present on origin/main)
- Location (main → release): `MSPReconcile.getPayments` `:1436,1488,1496 → :1555,1620,1628`; `convCurValue` returns `"0"` on parse error `:2051-2053 → :2017-2019`; totals in `CreateBillingReport2Action.java:204,209 → :218,223`; private payments `:1578,1651 → :1704,1762`
- Problem: In PDF mode, a remittance row is kept only `if (dblAmount != 0)`. A Teleplan S00 record with paid amount 0 is silently dropped even when it carries adjustment codes and amounts (`t_ajc1`/`t_aja1..7`), for example a claim fully offset by an adjustment. An unparseable paid amount is also dropped, because `convCurValue` logs and returns `"0"`. The dropped rows' adjustments are therefore missing from `sumPayed.addAdjustmentAmount(...)`. The release's own CSV fix (`keepCsvPayment`, `MSPReconcile.java:204-214`: "Preserve malformed rows and zero payments with adjustments") treats this as an error, but the PDF path was left unchanged.
- Evidence: `double dblAmount = Double.valueOf(b.amount).doubleValue(); … if (dblAmount != 0) { …list.add(b) }` compared with `return sign != 0 || !bill.adjustmentCode.isEmpty();` in the CSV path.
- Impact: The Payments/Refunds and Payment Summary PDFs under-report MSP adjustments and do not show the claims they apply to. The PDF and CSV versions of the same report now disagree.
- Correction: Apply the `keepCsvPayment` rule in PDF mode too: keep zero-paid rows that carry an adjustment, and mark unparseable amounts instead of treating them as $0.

### S10-P5: Zero-date legacy rows break WCB and private-payment reads when the JDBC URL omits `zeroDateTimeBehavior`
- Severity: Low
- Category: data-integrity
