### S11-1: Inboxhub now hides HRM count failures and shows partial counts (HTTP 200) where main returned HTTP 500
- Severity: Low
- Category: silent-failure
- Confidence: Confirmed
- Commit: 71e68173 (#5695)
- Location: `src/main/java/io/github/carlos_emr/carlos/mds/data/CategoryData.java:134-142`; `src/main/java/io/github/carlos_emr/carlos/inboxhub/inboxdata/LabDataController.java:285-289` (catch is older, unchanged); `src/main/webapp/WEB-INF/classes/struts-provider.xml:35-44`
- Problem: On main the HRM count queries ran through a JPA `EntityManager`. They failed with an unchecked
  `PersistenceException`, which escaped `populateCountsAndPatients()`. The Inboxhub's Struts package deliberately
  maps no generic exception, so the result was HTTP 500 with a full stack trace. The new `CategoryData.count()`
  wraps every DAO, JPA and transaction failure in a checked `SQLException`. `LabDataController.getCategoryData`
  catches `SQLException`, logs it, and returns the half-filled `CategoryData`. The page then renders normally.
  HRM_PATIENT runs third in `populateCountsAndPatients`, so a failure there also leaves DOCUMENT/LAB/HRM
  UNMATCHED and ABNORMAL at 0.
- Evidence: `CategoryData.java:138-141` `catch (DataAccessException | PersistenceException | TransactionException failure) { throw new SQLException("Could not read inbox category counts", failure); }`. `LabDataController.java:286-288` `categoryData.populateCountsAndPatients(); } catch (SQLException e) { MiscUtils.getLogger().error(e); }`. `struts-provider.xml:38-41` says a generic mapping is not declared because "every unexpected NPE/DAO failure would become an unlogged HTTP 200 … page. Unmapped exceptions keep the web.xml error path: HTTP 500". The DMS inbox (`documentManager/inboxManage`) is unaffected: "error" and runtime exceptions both reach `errorpage.jsp`.
- Impact: Narrow. Lab and document count failures were already swallowed this way on main, because
  `LegacyJdbcQuery` threw `SQLException`. Only HRM-specific failures move from a loud 500 to an Inbox with
  wrong counts. The list itself is fetched separately and can disagree with the counts. The error is logged.
- Correction: Make `LabDataController.getCategoryData` show an error and return the failure path instead of a
  half-populated result. The alternative is to keep HRM failures unchecked. Either way, cover "count fails →
  user-visible error" with a test.

## Pre-existing issues

### S11-P1: A CML lab with no HIN can be filed to a different patient by DOB, sex and initials alone
- Severity: Medium
- Category: data-integrity
- Confidence: Confirmed (code path); a wrong-patient match also needs exactly one blank-HIN patient that matches
- Pre-existing: yes (present on origin/main)
- Location: main `src/main/java/io/github/carlos_emr/carlos/lab/ca/on/CML/ABCDParser.java:130-190` (`hinMod` at 138-142, SQL at 155-171); release `ABCDParser.java:129-163` (`hinMod` at 136, call at 149-151) and `src/main/java/io/github/carlos_emr/carlos/commn/dao/LabRoutingLookupDao.java:152-165`
- Problem: CML patient matching always runs `hin=?` with the lab's HIN, even when that HIN is blank. Blank-HIN
  labs are a normal input: the B record's field 7 may be empty, and the release's own CML fixture has
  `"F", "", "20000101"`.
  - With a blank HIN, the query matches every demographic whose stored `hin` is `''`, then filters by DOB and
    sex. By default it also filters by first-letter name prefixes. With `LAB_NOMATCH_NAMES=yes` it ignores names
    entirely.
  - When exactly one such patient matches, the lab is routed into that chart.
  - The HL7 path treats a blank HIN as missing and requires full first and last name, DOB and sex, for patient
    safety (`LabRoutingLookupDao.java:116-121`). CML has no equivalent guard.
- Evidence: `ABCDParser.java:136` `String hinMod = new String(hin);`. `LabRoutingLookupDao.java:154` `"... FROM demographic WHERE hin=?1"`, with `params.add(hin)` and no blank check. The count is then `count != 1 → demo="0"` (`ABCDParser.java:156-159`), so a single match is accepted.
- Impact: For blank-HIN patients (newborns, uninsured, out-of-province) a CML result can go into the wrong chart
  when another blank-HIN patient shares DOB, sex and initials. Nothing tells the user this happened.
- Correction: Treat a blank or UNKNOWN CML HIN as missing. Either leave the lab unmatched or apply the HL7 rule
  (exact full names + DOB + sex). Never match on `hin=''`. Add a fixture with two blank-HIN patients.
