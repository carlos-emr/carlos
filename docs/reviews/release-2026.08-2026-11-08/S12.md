### S12-1: The "new appointments" day sheet no longer marks appointments as Daysheet Printed when viewed, and the new Acknowledge button marks rows the user may never have seen
- Severity: Low
- Category: breaking-change
- Confidence: Confirmed (mechanism). Impact depends on workflow and is Plausible.
- Commit: b6fa8255 (#5694)
- Location: `src/main/webapp/WEB-INF/jsp/report/reportdaysheet.jsp:130-139, 186-205`, `src/main/java/io/github/carlos_emr/carlos/appointment/service/AppointmentDaySheetService.java:53-76`, `docs/release-notes-2026.08.md` (no entry)
- Problem:
  - Until now, opening `/report/ViewReportdaysheet` in "new" mode (`dsmode` missing or not `all`)
    archived each appointment in status `t` ("To Do") and set it to `T` ("Daysheet Printed").
  - Now a GET only displays the sheet. Staff must click a new button, "Acknowledge new
    appointments", which sends a POST.
  - The POST form carries only the filters (`provider_no`, `sdate`, `orderby`, …). It does not
    carry the IDs or `editVersion` of the rows that were shown. The POST runs `findDaySheet` again
    and acknowledges every row that is in status `t` at that moment.
  - The "stale edit version" check compares two reads made within that same POST, microseconds
    apart. It does not compare against the rendered page.
  - Scenario: a user prints the GET preview (the Print button is always shown), then clicks
    Acknowledge. Any appointment booked in between becomes "Daysheet Printed" although it was
    never on a printed sheet.
  - Reloading the POST result page posts again and renders an empty sheet.
  - Neither the behaviour change nor the new button is in the release notes.
  - No browser check covers the new-mode GET/POST branch. `report-daysheet-labs-playwright-checks.js`
    only opens "All appointments" (`dsmode=all`).
- Evidence: `boolean acknowledge = newOnly && "POST".equals(request.getMethod()) && "true".equals(request.getParameter("acknowledge"));` acts on `daySheetRows = appointmentDao.findDaySheet(...)`, which is queried in the same request. The form's hidden fields are `acknowledge, dsmode, provider_no, sdate, edate, orderby, rosteredStatus, sTime, eTime`. Main's JSP called `appointment.setStatus("T")` and `archiveAppointment` directly on GET.
- Impact:
  - Reach is low. The only in-app link to "new" mode is `appointment/appointmentaddrecordprint.jsp:144`.
    That page is itself a dead-route candidate: nothing links to it, and its
    `btnAddApptPrintPreview` label is unused. Direct or bookmarked URLs (and the default when
    `dsmode` is omitted) still reach it.
  - Clinics that still use it will see appointments stay "To Do" and pile up on every later "new"
    sheet. With print-then-acknowledge, some appointments are marked printed without ever being
    printed.
- Correction:
  - Put the displayed `appointment_no` and `editVersion` pairs in the POST form, and acknowledge
    only those rows (intersected with a fresh locked read). Show a count of skipped rows.
  - Add a release-note entry, plus a browser check of the GET (no write), POST (writes) and
    reload behaviour.
  - Or, since the only entry route is dead, retire "new" mode and the Acknowledge path.

### S12-2: eForm AP query failures now log only the exception class, so a broken AP cannot be identified
- Severity: Low
- Category: silent-failure
- Confidence: Confirmed
- Commit: b6fa8255 (#5694)
- Location: `src/main/java/io/github/carlos_emr/carlos/eform/EFormUtil.java:656-659, 711-714`, `src/main/java/io/github/carlos_emr/carlos/eform/data/EForm.java:1192-1195`, `src/main/java/io/github/carlos_emr/carlos/form/pageUtil/FrmXmlUpload2Action.java:190-191`
- Problem:
  - `readApValues` and `readApJson` replaced logging with the stack trace and SQL message by
    `logger.error("eForm AP query failed (causeType={})", e.getClass().getName())`. The lenient
    path is the one `EForm.putValuesFromAP` uses for every rendered eForm.
  - That path renders the field blank with HTTP 200 and logs neither the AP key nor any SQL error
    code.
  - A missing column in lenient mode now produces the visible placeholder but no log line at all
    (before, each one was logged).
  - Similarly, `FrmXmlUpload2Action` used to log the cause type of an `XmlImportException`. It now
    logs only `JDBCUtil$XmlImportException`, which hides whether the cause was a bad name, a bad
    XML body or an unknown table.
- Evidence: Old: `catch (SQLException sqe) { logger.error("Error", sqe); }` and `logger.error("Blocked unsafe SQL execution in legacy eForm path", secEx)`. New: `catch (RuntimeException e) { logger.error("eForm AP query failed (causeType={})", ...); return strict ? null : new ArrayList<>(); }`.
- Impact: An administrator whose custom AP SQL breaks (a typo, or a schema change after
  upgrade) sees blank clinical fields, plus a log line that names neither the AP nor the reason.
  Dropping the message protects PHI, but the AP key and the SQLState/vendor code are not PHI.
- Correction: Pass the AP key down, or log it in `EForm.putValuesFromAP`, and log the root
  `SQLException`'s SQLState and error code (not its message). In `FrmXmlUpload2Action`, log the
  cause class again.

### S12-3: The eChart Forms module now runs an extra registry query for every registered form on every chart open
- Severity: Low
- Category: regression
- Confidence: Confirmed
- Commit: b6fa8255 (#5694)
- Location: `src/main/java/io/github/carlos_emr/carlos/commn/dao/EncounterFormDaoImpl.java:55-61, 64-66`, `src/main/java/io/github/carlos_emr/carlos/encounter/data/EctFormData.java:225-263`, `src/main/java/io/github/carlos_emr/carlos/encounter/pageUtil/EctDisplayForm2Action.java:99-112`
- Problem:
  - `getPatientFormsAsArrayList` already validates the table with `validateFormTable`, which
    calls `findByFormTable`.
  - `findPatientHistory` then runs `requireTable`, which calls `findByFormTable` again.
  - There is no cache. The comment "EncounterFormDaoImpl caches form-table lookups" is false:
    `findByFormTable` is a plain JPQL query and the entity is not `@Cacheable`.
  - So each registered form costs three queries instead of two. The seeded registries have 43
    form tables on ON and 54 on BC, so every eChart open runs about 43–54 extra queries. The same
    duplication applies to `getShortcutFormValue` and the grouped history.
- Evidence: `requireTable`: `(!Set.of("form","formGrowth0_36").contains(table) && findByFormTable(table).isEmpty())`, called from `findPatientHistory`. `validateFormTable` → `isKnownEncounterFormTable` → `findByFormTable` was already called for the same table.
- Impact: Small but systematic latency on the most frequently loaded clinical page. Not a
  correctness problem.
- Correction: Validate once, either by letting the facade pass an already-validated table or by
  caching the registry lookup in the DAO. Fix the misleading comment.

### S12-4: The BC third-party billing address search now shows "no results" when the database read fails
- Severity: Low
- Category: silent-failure
- Confidence: Confirmed
- Commit: b6fa8255 (#5694)
- Location: `src/main/webapp/WEB-INF/jsp/billing/CA/BC/onSearch3rdBillAddr.jsp:68-82`, `src/main/java/io/github/carlos_emr/carlos/commn/dao/Billing3rdPartyAddressDaoImpl.java:134-146`
- Problem:
  - The BC picker moved from its own JDBC query to the existing ON
    `Billing3rdPartyAddressDao.findAddresses`. Before, a failed query raised an exception, which
    reached the JSP's `errorPage`.
  - The DAO catches `Exception`, logs it and returns an empty list, so a DB failure now looks like
    "no matching address".
  - The DAO also pages with `ORDER BY company_name LIMIT x,y` and no unique tie-breaker, which the
    CLAUDE.md paging rule forbids. This is not a regression: the old BC JSP had the same
    non-unique order. But BC now inherits it through the DAO.
  - Search mode `id` is no longer accepted. The UI never offers it.
- Evidence: `catch (Exception e) { MiscUtils.getLogger().error("error", e); return new ArrayList<Billing3rdPartyAddress>(); }`. The old BC JSP had no catch around `LegacyJdbcQuery.queryResultsPaged` (the page has `errorPage=`).
- Impact: On a transient DB error, BC billing staff may conclude the payer address is missing and
  create a duplicate.
- Correction: Let the DAO propagate the failure, or return a failure indicator so the JSP shows an
  error. Add `id` as a tie-breaker to the ORDER BY.

  for documented external callers.

## Checked and found OK
- AP values (strict and lenient): the SELECT policy is still enforced (`EFormSqlSafety` →
  `validateReportSelectQuery`). Params are bound (null → `setObject` null). Last-row, empty-row,
  missing-column and failure semantics match. Case-insensitive and qualified labels resolve. The
  statement and result set are closed. No outer transaction is reachable from the servlet/JSP
  callers.
- The group-count, library and patient listing SQL is equivalent to the old SQL: same WHERE
  clauses, sentinel, implicit GROUP BY order and ORDER BY name resolution. Unqualified sort columns
  resolve to the same columns, and the CAST projections keep DATE/TIME text. All projection
  column orders were checked against record constructors: `EFormListingRow`,
  `AppointmentDaySheetRow`, `LabPatientChoice`, `ReportChoice`, `HistoryRow`, `BillStateRow`,
  `PlannerRow`, `CdmPatientRow` and the BC rules. No mismatches.
- Day-sheet SQL: the "all" and "new" predicates are identical. ORDER BY `start_time` still
  resolves to `a.start_time`, and the `phone`/`sex` sort keys resolve to the select-list `d.*`
  columns (provider has the same names) as before. Times and dates are still bound as strings.
  Acknowledgement is transactional, locks rows in ID order, archives first, is guarded by POST and
  CSRF, and is covered by the CSRF route test.
- Report index provider/group choices: the SITE and TEAM predicates (including the reused named
  parameter) and the doctor/active filter are identical.
- Lab patient search: the comma and first-name handling (including the `kw+"%"` quirk), DOB
  padding, the allowlisted ORDER BY, page bounds (the JSP clamps to 1..500, so the DAO's IAE is
  unreachable) and the merged-patient exclusion are identical.
- Form history: grouped/plain/XML SQL and date-only creation values are unchanged, and every
  `formCreated`/`formEdited` column in the Flyway schema is DATE, DATETIME or TIMESTAMP, so
  `NativeQueryValues.asDate` never throws. All seeded `form_table` names pass `requireTable`'s
  regex.
- XML import: the filename still owns the patient and timestamp; `ID`, `demographic_no` and
  `formEdited` from the body are ignored; unknown columns still fail; the whole archive rolls back
  on checked and unchecked errors; the self-invocation inside `importArchive` is covered by the
  class-level transaction.
- `FrmSetupForm2Action` VT NULL/whitespace retention and `getColumnName` semantics are unchanged.
  The patient-isolation tests were rewritten against the DAO without losing assertions.
- Patient-scope and privilege checks are unchanged: `_lab` on PatientSearch, `_report`/
  `_admin.reporting` on the report pages (the reportindex auth include is now unconditional),
  `_admin` w plus POST-only on fixRolesOnNotes, and patient binding added to the antenatal print.
  Output encoding is preserved, and the new hidden inputs use `SafeEncode.forHtmlAttribute` and
  `carlos:forHtmlAttribute`.
- No new `field = SpringUtils.getBean` shims: the static-final `EncounterFormDao` fields became
  accessor methods. No new entities, so persistence.xml needs no change. No per-row DAO calls were
  introduced.
- New MariaDB-tier tests are required in CI (`maven-project.yml:338`, `verify-mariadb-dao-reports.py:58-62`)
  and still present at head. The day-sheet integration test checks native-projection `editVersion`

  physical-table history query (`GROUP BY date(formEdited)` with non-aggregated columns). Only the
  XML and Growth grouped paths are tested. The SQL is unchanged except for the CAST, so the risk is
  low.

### S12-P1: Stored XSS in the antenatal planner. Saved risk/checklist values are written into a JavaScript string without escaping quotes
- Severity: Low
- Category: security
- Confidence: Confirmed (sink and missing escape). Reachability is limited.
- Commit: none (pre-existing). The neighbouring print JSP was touched by b6fa8255.
- Location: `src/main/webapp/WEB-INF/jsp/decision/antenatal/antenatalplanner.jsp:81-89, 118` (main and release are identical), `src/main/java/io/github/carlos_emr/SxmlMisc.java:75-95, 216-222` (main and release)
- Problem:
  - When saved, every `risk_*` and `checklist_*` request value is stored in `desaprisk` after
    `SxmlMisc.replaceHTMLContent`. That function escapes only `& < >`; the `'` and `"` escapes are
    commented out.
  - On every later view the stored XML is emitted raw inside a double-quoted JavaScript literal:
    `xmlText = "<xml><planner><%=risk_content%><%=checklist_content%></planner></xml>";`.
  - So a value such as `";alert(document.cookie);//` breaks out of the string and runs in every
    viewer's session. A legitimate `"` or newline in a value breaks the planner's script.
- Evidence: `str = SxmlMisc.replaceString(str, "<", "&lt;"); //  str = SxmlMisc.replaceString(str,"\"","&quot;");`. The gate is `ViewDecision2Action` (`_form` r to view, w to save).
- Impact: Any user with `_form` write can plant script that runs for other clinicians viewing that
  patient's planner. Every in-app planner link is commented out (`formbcar*.jsp`), so both the
  attacker and the victim need the direct URL. This lowers reach but not exploitability.
- Correction: Emit the content with `SafeEncode.forJavaScript`, or move it into a non-script
  data element. Escape quotes in `createXmlDataString` values, or reject them.
- Pre-existing: yes (present on origin/main)
- Disclosure: private

### S12-P3: Day-sheet status updates need only report read privilege, and on main they fire on GET
- Severity: Low
- Category: security
- Confidence: Confirmed
- Commit: none (pre-existing). b6fa8255 moved the write to POST but kept the gate.
- Location: `src/main/java/io/github/carlos_emr/carlos/report/gate/ViewReport2Action.java:73` (main and release), `src/main/webapp/WEB-INF/jsp/report/reportdaysheet.jsp:40, 205-240` (main: archive and `setStatus("T")` on GET), `:40, 130-139` (release: POST)
- Problem: The day-sheet route archives appointments and sets them to `T` for every provider
  visible to the user. The only check is `_report` read (gate) plus `_report,_admin.reporting`
  read (JSP). No `_appointment` write is required.
