## Findings
### S13-1: Devcontainer DrugRef can no longer start: its properties now name the MariaDB driver, but the image is built from drugref2026 `master`, which only ships MySQL Connector/J
- Severity: Medium
- Category: regression
- Confidence: Confirmed
- Commit: 710fb1ac (#5460)
- Location: `.devcontainer/development/config/shared/volumes/drugref2.properties:2-3`, `.devcontainer/docker-compose.yml:38-49`, `.devcontainer/drugref/Dockerfile:8-15`
- Problem: The slice changed the devcontainer DrugRef settings to `db_url=jdbc:mariadb://db:3306/drugref2` and
  `db_driver=org.mariadb.jdbc.Driver`. The `drugref` compose service still builds DrugRef from
  `DRUGREF_BRANCH:-master`, and the Dockerfile cannot take a commit SHA. The MariaDB migration exists only on drugref2026's
  unmerged `fix/mariadb-connector` branch (the `debian/drugref.pin` commit; see #5744). drugref2026 `master` (57c8642)
  still has only `mysql-connector-j` 9.1.0. Its datasource is `com.zaxxer.hikari.HikariDataSource` with
  `driverClassName=${db_driver}` and `jdbcUrl=${db_url}?serverTimezone=UTC`.
- Evidence: `git show origin/master:pom.xml` (drugref2026) lists `com.mysql:mysql-connector-j:9.1.0` and no `mariadb` artifact.
  `spring_config.xml:32-34` on master has `HikariDataSource`, `${db_driver}` and `${db_url}?serverTimezone=UTC`.
  `HikariConfig.setDriverClassName("org.mariadb.jdbc.Driver")` throws "Failed to load driver class …", so the `/drugref2`
  context fails to deploy. A `jdbc:mariadb:` URL would also have no MySQL driver to accept it. Devcontainer CARLOS uses
  `drugref_url=http://drugref:8080/drugref2/DrugrefService` (`volumes/carlos.properties:247`). The CI dev-image test in
  `container-images.yml:492-531` only checks that Tomcat answers any HTTP code, and mounts no properties, so CI cannot see this.
- Impact: Every fresh devcontainer, and the published `carlos-drugref-dev` image, now has no working DrugRef. Drug search,
  interaction checks and the devcontainer prescription UI checks (e.g. `ui-tests:test4`) fail. Packaged installs are not
  affected, because they build from the pin.
- Correction: Revert the devcontainer `drugref2.properties` to the legacy values (`jdbc:mysql://db:3306/drugref2`,
  `com.mysql.cj.jdbc.Driver`). Both the master build and the pinned build accept them. Alternatively, build the devcontainer
  DrugRef from the pinned revision (fetch by SHA), or merge drugref2026#18 first and keep `master`. Make the dev-image
  smoke test request `/drugref2/` and require HTTP 200.

### S13-2: getString on DOUBLE/FLOAT/BIT columns no longer matches Connector/J, so Report by Template, Query by Example, fixed and clinical reports, and legacy form loaders change output silently
- Severity: Low
- Category: silent-failure
- Confidence: Confirmed (code-traced in both drivers; not run against a server)
- Commit: 710fb1ac (#5460)
- Location: `src/main/java/io/github/carlos_emr/carlos/utility/MariaDbCompatibilityDriver.java:210-220` (only temporal columns are intercepted), `MariaDbJdbcCompatibility.java:206` (`transformedBitIsBoolean=false`); consumers `report/reportByTemplate/ReportResultBudget.java:107,125-137`, `report/data/RptResultStruct.java:180-193`, `report/data/ConfiguredReportQuery.java:228-236`, `form/FrmRecordHelp.java:143` / `form/FrmCostQuestionnaireRecord.java:110`; doc claim `docs/mariadb-connector-migration.md:32-36`
- Problem: The adapter preserves Connector/J's string form only for DATE, DATETIME and TIMESTAMP. Three cases differ:
  - DOUBLE/FLOAT `getString`: Connector/J returned `String.valueOf(double)` (`StringValueFactory.createFromDouble`), giving
    "100.0" and "1.0E10". MariaDB returns the server text ("100", "10000000000").
  - BIT(1) `getString`: Connector/J returned "1"/"0" (`createFromBit` → `createFromLong`). With the adapter's forced
    `transformedBitIsBoolean=false`, MariaDB's `BitColumn.decodeStringText` returns "b'1'" for true and "b''" for false.
  - BIT(1) `getObject` and `getColumnClassName` also become `byte[]` instead of Boolean. No main-code consumer of that was
    found; Hibernate entity reads go through `getBoolean`, which the adapter handles.
- Evidence: All three report readers call `rs.getString(column)` for `Types.BIT/REAL/FLOAT/DOUBLE`. FLOAT/DOUBLE columns
  exist in `drugs.takemin/takemax`, `favorites`, `formCostQuestionnaire.*Cost*`, `validations`, `criteria` and
  `vacancy_client_match` (V1 baseline :2849, :3222, :4372-4399, :11339). BIT(1) columns are `LookupCodeValue.active`,
  `dashboard.active/locked`, `indicatorTemplate.active/locked` and `tickler_category.active` (V1 baseline :756, :2369, :9415,
  :11211). All of these tables are `reportable` for Query by Example (`carlos_report_grants.sql:197,372,387,543`).
  `JdbcConnectorMariaDbIntegrationTest` asserts only `getBoolean` and type names for BIT, and never reads DOUBLE.
- Impact: Report HTML and CSV exports change cell text silently. For example, a dose of `1.0` becomes `1`, and BIT flags
  read `b'1'` or `b''`. The same happens in legacy form fields such as the Cost Questionnaire. Spreadsheets or scripts that
  consume template CSVs may break. The new doc's claim that the existing conversion contract is preserved is inaccurate.
- Correction: Two options:
  - Extend `textValue` to render BIT columns via their long value and DOUBLE/FLOAT columns via `String.valueOf(rows.getDouble(..))`
    (and `String.valueOf(rows.getFloat(..))` widened as Connector/J did). Add DOUBLE/FLOAT/BIT `getString`/`getObject` cases to
    `JdbcConnectorMariaDbIntegrationTest`.
  - Or document the new format in the connector doc and the release notes.

### S13-3: Legacy `yes`/`no` boolean option values, which Connector/J accepted for every boolean property, now fail every connection unless the option is on the adapter's short list
- Severity: Low
- Category: breaking-change
- Confidence: Confirmed (code-traced; harness shows the value passed through unchanged)
- Commit: 710fb1ac (#5460)
- Location: `src/main/java/io/github/carlos_emr/carlos/utility/MariaDbJdbcCompatibility.java:148-152,440-447,485-491`
- Problem: Connector/J's `BooleanPropertyDefinition` accepts TRUE/FALSE/YES/NO, case-insensitive, for every boolean
  property. The adapter normalizes `yes`/`no` only for the options in `BOOLEAN_OPTIONS`. Every other option is passed through
  unchanged. MariaDB `Configuration.handleBooleanField` accepts only `""`, `1`, `true`, `0` and `false`, and otherwise throws
  `IllegalArgumentException`. That surfaces as `SQLException("error parsing url: Optional parameter X must be boolean …")`
  on every connect.
- Evidence: Options affected include `allowPublicKeyRetrieval`, `useServerPrepStmts`, `cachePrepStmts`, `useCompression`,
  `allowMultiQueries`, `useAffectedRows`, `tcpKeepAlive`, `useLocalSessionState`, `yearIsDateType` and
  `createDatabaseIfNotExist`. Scratch harness: `settings("jdbc:mysql://127.0.0.1:3306/carlos?allowPublicKeyRetrieval=yes")`
  returns the property `allowPublicKeyRetrieval=yes` unchanged.
- Impact: An upgraded install whose operator-written URL uses such a token stops starting: the pool, Flyway runner and QBE
  connections all fail. The packaged and carlos-ctl URLs use `true`/`false`, so this is rare. Unlike #5770, the error at
  least names the option.
- Correction: For legacy-scheme URLs, map `yes`/`no` (case-insensitive) to `true`/`false` for every option whose MariaDB
  `Configuration.Builder` field is Boolean. Alternatively, refuse those values with the adapter's own configuration error
  and list them in the connector doc.

### S13-P1: CARLOS fails to start whenever `db_name` has no `?query`, because `AuditLogManager` cuts the schema name at `indexOf("?")` in a field initializer
- Severity: Medium
- Category: bug
- Confidence: Confirmed
- Commit: n/a (pre-existing; relevant to 710fb1ac's config contract)
- Location: `src/main/java/io/github/carlos_emr/carlos/managers/AuditLogManager.java:65` (main :65); bean created eagerly via `src/main/resources/spring_managers.xml:23` (`component-scan … managers`)
- Pre-existing: yes (present on origin/main)
- Problem: `String dbName = …getProperty("db_name").substring(0, …getProperty("db_name").indexOf("?"));` is an instance-field
  initializer of an eager `@Service` singleton. With a plain `db_name=carlos`, `indexOf` returns -1 and `substring(0,-1)`
  throws `StringIndexOutOfBoundsException` while the Spring context starts. A missing key throws NPE instead.
- Evidence: `QueryByExampleSqlValidator.applicationSchema` handles the same key safely
  (`configuredName.split("\\?", 2)[0]`, `QueryByExampleSqlValidator.java:211-216`). The adapter accepts option-less
  URLs, and the new doc describes `jdbc:mariadb://host:port/database` configuration.
- Impact: Any install whose `db_name` carries no JDBC options cannot start; the error is a cryptic BeanCreationException
  for `auditLogManager`. All shipped templates include `?zeroDateTimeBehavior=…`, so this is rare.
- Correction: Parse lazily inside `purgeAuditLog`, using the same split as `applicationSchema` (or reuse it), and refuse an
  empty name with a clear message.

### S13-P2: The audit-log purge deletes rows its own backup excluded, and the backup command ignores the configured database endpoint
- Severity: Low
- Category: data-integrity
- Confidence: Confirmed
- Commit: n/a (pre-existing)
- Location: `src/main/java/io/github/carlos_emr/carlos/managers/AuditLogManager.java:93,113-119,163`; `src/main/java/io/github/carlos_emr/carlos/commn/dao/OscarLogDaoImpl.java:331` (main: same lines)
- Pre-existing: yes (present on origin/main)
- Problem: The cut-off is set to 23:59:59 with milliseconds 0; the date comes from `SimpleDateFormat("yyyy-MM-dd").parse`
  (`AuditLogPurge2Action.java:61-69`).
  - The backup dumps `-w "dateTime < '<day> 23:59:59'"`, but the purge runs
    `delete from OscarLog WHERE created <= ?1` on the same `log.dateTime` DATETIME(0) column. Rows logged at 23:59:59 on
    the cut-off day are deleted and never written to the backup.
  - The mysqldump argv carries no `--host`/`--port` from `db_uri`, so it always reads the local default server.
  - It passes `--password=<db_password>` on the command line, which is briefly visible in the process table; carlos-ctl
    deliberately avoids this.
- Evidence: `vars[4] = "dateTime < '" + formatter2.format(endDateToPurge) + "'"` (:116) versus `WHERE created <= ?1`
  (`OscarLogDaoImpl.java:331`), where `created` maps to `@Column(name="dateTime")` (`OscarLog.java:54-56`).
  `vars[1..2] = --user/--password` (:113-114). The WAR default enables the feature with
  `log.purge.mysqldump=/usr/bin/mysqldump` (`carlos.properties:1383`).
- Impact: Audit records from the final second of the cut-off day are lost without a backup, silently. With a non-local
  database the backup fails and the purge aborts (fail-safe, but the feature is unusable).
- Correction: Use the same predicate for both, e.g. `dateTime < '<day+1> 00:00:00'` and `created < day+1`. Pass host and
  port from the parsed `db_uri`, and supply the password through `MYSQL_PWD` or a defaults file rather than argv.

### S13-P3: Audit-log purge refusals end in HTTP 500 instead of their message, because of an operator-precedence bug
- Severity: Low
- Category: silent-failure
- Confidence: Confirmed
- Commit: n/a (pre-existing)
- Location: `src/main/java/io/github/carlos_emr/carlos/admin/web/AuditLogPurge2Action.java:82` (main :82)
- Pre-existing: yes (present on origin/main)
- Problem: `"Error. " + e.getCause() != null ? e.getCause().getMessage() : e.getMessage()` parses as
  `("Error. " + e.getCause()) != null ? …`, which is always true. The code therefore calls `e.getCause().getMessage()` even
  when there is no cause. Every refusal `AuditLogManager` throws without a cause hits this NPE inside the catch block:
  missing mysqldump, invalid `log.purge.minDays`, "purge aborted because specified date is within N", and a non-zero
  mysqldump exit.
- Evidence: `throw new Exception("purge aborted because specified date is within " + numDays)`
  (`AuditLogManager.java:101-103`) has no cause.
- Impact: An administrator who picks a date inside the minimum-retention window gets the generic error page, not the reason.
- Correction: Change it to `"Error. " + (e.getCause() != null ? e.getCause().getMessage() : e.getMessage())`.

### S13-P4: `admin/AuditLogPurge` performs the destructive purge on GET, outside both the GET guard and CSRFGuard
- Severity: Medium
- Category: security
- Confidence: Confirmed in code (end-to-end exploit not run)
- Commit: n/a (pre-existing)
- Location: `src/main/java/io/github/carlos_emr/carlos/admin/web/AuditLogPurge2Action.java:54-78`; `src/main/webapp/WEB-INF/classes/struts-admin.xml:65` (main: same); `src/main/java/io/github/carlos_emr/carlos/app/HttpMethodGuardFilter.java:92-120,174-187`
- Pre-existing: yes (present on origin/main)
- Disclosure: private
- Problem: `execute()` checks `_admin.auditLogPurge` but never the HTTP method. The route name `AuditLogPurge` matches no
  `MUTATOR_ACTION_PREFIXES` or `MUTATOR_ACTION_NAMES` entry and is absent from `MUTATION_INTENT_PARAMS_BY_ROUTE`. CSRFGuard
  protects only `POST,PUT,DELETE,PATCH` (`Owasp.CsrfGuard.properties:97`), and the session cookie is SameSite=Lax, which
  is sent on top-level cross-site GET navigations. A crafted link such as `…/admin/AuditLogPurge?dateBegin=2010-01-01`,
  opened by a logged-in admin (`admin` holds `_admin.auditLogPurge` `x`, `V1.0.2__on_data.sql:35837`), runs the dump and
  then deletes the audit rows.
- Evidence: The page itself posts (`auditLogPurge.jsp:145`), but nothing refuses GET. The class is not registered in
  `MutatorActionGetRejectionContractUnitTest` (grep finds no reference).
- Impact: Cross-site destruction of audit-trail records older than `log.purge.minDays` (default 10 years). It needs
  `log.purge.mysqldump` to resolve to a working binary, and a backup file is written first (see S13-P2 for its gap).
- Correction: Reject non-POST in the action before any side effect, or add the route to `MUTATOR_ACTION_NAMES`. Register
  the class in the GET-rejection contract test.

### S13-P5: The MariaDB DAO CI lane does not use the packaged JDBC conversion options, although the doc says it does
- Severity: Low
- Category: test-gap
- Confidence: Confirmed
- Commit: n/a (pre-existing; risk raised by 710fb1ac)
- Location: `src/test/java/io/github/carlos_emr/carlos/test/base/MariaDbDaoTestContextInitializer.java:53-54` (main :45-46); `docs/test/hibernate-mariadb-regressions.md:74` (main :72)
- Pre-existing: yes (present on origin/main)
- Problem: The DAO lane connects with `zeroDateTimeBehavior=CONVERT_TO_NULL` and no `useOldAliasMetadataBehavior`.
  Packaged installs, via carlos-ctl `init-config`, the WAR default and the devcontainer, use `zeroDateTimeBehavior=round`
  with `useOldAliasMetadataBehavior=true`. The doc still claims the lane "retains the packaged SQL-mode, collation and

- Evidence: 710fb1ac moved ROUND and the alias metadata policy out of the driver into the new `MariaDbCompatibilityDriver`.

- Impact: A DAO, native-query or Frm*Record regression that appears only with ROUND or the alias policy passes CI. For
  example, a zero date arrives as `0001-01-01` in production but as `null` in CI.
- Correction: Run the Flyway DAO lane with the packaged `db_name` options, or add a second pass with them, and correct the
  doc sentence.

## Checked and found OK
- Upgrade path for beta installs (Critical-risk check): `/etc/carlos-emr/carlos.properties` from carlos-ctl 1.3.1 has
  `db_driver=com.mysql.cj.jdbc.Driver`, `db_uri=jdbc:mysql://127.0.0.1:3306/` and the db_name options. `setDriverClassName`
  maps the driver, and `normalizeUrl`/`settings` accept the URL; the harness produced the expected properties. No maintainer
  script rewrites JDBC config, and none needs to.
- carlos-ctl `db-*` FLYWAY_URL (`jdbc:mysql://…?useSSL=false&allowPublicKeyRetrieval=true&characterEncoding=UTF-8&connectionCollation=utf8mb4_general_ci`)
  is translated by `FlywayRunner.jdbcUrl`. The runner jar bundles the adapter classes and the TLS service file, and Flyway
  detects MariaDB from the URL and the product name.
- `jdbcCompliantTruncation`: both drivers append `STRICT_TRANS_TABLES` when it is true (MariaDB
  `StandardClient.addTruncationCommand`). Shipped URLs set it false, and FLYWAY_URL/DrugRef default to true on both drivers,
  so session `sql_mode` is unchanged.
- Old existing DrugRef `drugref2.properties` values work with the pinned DrugRef: `DrugrefDataSource` normalizes the
  driver and URL and adds UTC only when no zone is set. Its `isMysql()` accepts `jdbc:mariadb:`, and its adapter copy is
  identical to CARLOS's.
- No main code references `com.mysql.*` classes, the MySQL exception types, `CommunicationsException` or `08S01`.
  `CdsJdbcAdmissionGuard` now requires `org.mariadb.jdbc.Connection`, which always uses UTF-8.
- `MariaDbPreferredTlsPlugin`: a fresh instance per handshake (ServiceLoader per call), so `verifyIdentity` cannot race.
  PREFERRED skips verification only when there is no host `sslMode`. VERIFY_CA/VERIFY_FULL use JSSE roots or the configured
  store with hostname verification. No weakening compared with Connector/J was found.
- Update counts use FOUND_ROWS in both drivers (`useAffectedRows=false`), so the optimistic-lock and stale-edit checks are
  unchanged. Hibernate JDBC batching is not enabled, and there are no `executeBatch` callers outside the CDS guard.
- Hibernate dialect is set explicitly (`OscarMySQL5Dialect`, no-arg constructor), so metadata-based resolution does not
  apply. MySQLDialect maps 1205/1213/1062 by vendor code, which MariaDB also sends.
- `WebappShutdownResources`: `OscarSpringContextLoader` is declared after `Startup` in web.xml, so its pool closes first
  and only then is the scheduler shut. Closing only the webapp-owned scheduler is unit-tested.
- MariaDB's internal-field reflection (`fieldPackets`, `rowDecoder`/`fieldLength`/`rowBuf`) is guarded by the exact 3.5.11
  pin in the pom, the Flyway runner build and the DrugRef check, and by the required 32-case connector test.
- `LegacyJdbcQuery` report streaming, `ReportQueryDeadline` abort, `setMaxRows`/`setQueryTimeout` (`SET STATEMENT`
  prefixes) and the QBE access-denied and timeout mappings behave equivalently.

## Declined to judge
- CPU cost of the reflective proxy on every ResultSet getter. Each call allocates `getMetaData()` and `Set.of(...)`; temporal
  reads also format and re-parse, and the alias policy reflects on every `getTableName`, e.g. per row in `ConfiguredReportQuery`.
  This is probably tens of milliseconds per large page and was not measured, so I am not reporting it.
- Native-URL corner cases: URL-decoding of `+`/`%` in native option values, unlike MariaDB itself; a non-canonical `timeZone`
  spelling bypassing `hasExplicitTimezone`; native `sslMode=allow` now requiring CA trust. These are documented or need
  hand-written native URLs that no shipped configuration uses.
- MariaDB driver DEBUG/TRACE logging through SLF4J (SQL text, server error text, packet dumps). Root defaults to WARN, and
  Hibernate already logs equivalent SQL at DEBUG.

## Out of scope but notable
- carlos-ctl 1.3.1 (separate repo) still writes MySQL-style `db_driver`/`db_uri`/FLYWAY_URL for new installs, so the
  compatibility layer is permanent for packaged installs. "New configuration uses `org.mariadb.jdbc.Driver`"
  (`docs/mariadb-connector-migration.md:26`) describes only the WAR and devcontainer defaults.
- `MariaDbDaoTestContextInitializer`, `IsolatedJpaTestDatabase` and `AppointmentUpdateDaoIntegrationTest` now reject
  `jdbc:mysql:` URLs, so the full DAO suite never runs through the legacy-scheme path that packaged installs use. The
  connector test's `legacy=true` parameter covers that path.
