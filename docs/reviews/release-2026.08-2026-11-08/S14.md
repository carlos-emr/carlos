## Findings

### S14-1: A comment-only edit to the logging.properties conffile triggers a dpkg prompt on hosts where it was edited
- Severity: Low
- Category: breaking-change
- Confidence: Confirmed
- Commit: dcb21112 (#5488), 710fb1ac, 5f9ca145 (#5518). Sibling of known #5767, which covers only carlos.xml.
- Location: `debian/assets/tomcat/logging.properties:41-56` (release head); installed by `debian/rules:287` as
  `/etc/carlos-emr/tomcat/logging.properties`, which dh_installdeb auto-registers as a conffile.
- Problem: three commits changed only the comment block about OpenTelemetry in this conffile. dpkg compares
  conffile bytes, not meaning. On any host where the operator edited the file, the upgrade raises a conffile
  prompt for a change with no effect. A scripted `apt-get -y` without `--force-confdef/--force-confold` and without
  a TTY aborts with "end of file on stdin at conffile prompt".
- Evidence: `diff <(git show origin/main:debian/assets/tomcat/logging.properties | grep -v '^\s*#') <(git show
  origin/release/2026.08:… | grep -v '^\s*#')` shows the non-comment content is identical. README.Debian:966-971
  points operators at this file to "match the retention here … to your own obligations", so edited copies are
  expected. No maintainer script or carlos-ctl verb edits the file, so only operator-edited hosts are affected.
- Impact: clinics that tuned log retention get an unexpected prompt, or a failed unattended `apt-get` run.
  unattended-upgrades keeps the old file and is not affected.
- Correction: restore the beta6 bytes of the conffile and put the explanation in docs (as suggested for #5767).
  Otherwise, batch the comment change with a functional change and call it out in the upgrade notes.

### S14-2: A generated key is written to the last file loaded, which is a legacy home-directory file whenever one exists; the log does not name the file
- Severity: Low
- Category: breaking-change
- Confidence: Confirmed
- Commit: c5350045 (#5621), 28909183 (#5673)
- Location: `src/main/java/io/github/carlos_emr/CarlosProperties.java:301-327` (provenance = last successful
  `readFromFile`), `:338-376`; `src/main/java/io/github/carlos_emr/carlos/login/Startup.java:98-104,151-156`;
  `docs/startup-encryption-key.md:12-16,20-35`; `docs/release-notes-2026.08.md:46-56`
- Problem:
  - Contract change. Before: a missing or blank key was appended to `${user.home}/<ctx>.properties`, creating that
    file if needed. Now: it is appended to the last external file read, the file is never created, and
    classpath-only, read-only or unwritable configuration refuses to start. This is intentional and is documented
    (it fails closed).
  - Residual ambiguity 1: `loadedPropertiesFile` is overwritten on every successful read. Startup reads the
    home-directory file after `-Dcarlos_override_properties`, so whenever a legacy home file exists, the key is
    appended to that home file, not to the override the operator selected.
  - Residual ambiguity 2: the success log line does not say which file received the key (`"Secret Key initialized
    in persisted configuration..."`).
  - Docs: the release notes ("persists generated keys to the external configuration that was actually loaded")
    and guide step 4 ("Back up the properties file and key") lead an operator to back up the override.
- Evidence: `readFromFile` ends with `loadedPropertiesFile = propertyFile;` for every file read. `Startup.java:103`
  calls `p.readFromFile(propFileName)` (the user.home path) after the constructor has read the override.
  `getOrCreateEncryptionKey` opens `loadedPropertiesFile.toPath()`. No test covers "override and home file, neither
  with a key".
- Impact: this needs a stale home file to be present, which the guide's step 1 tells operators to remove. If it is
  present, the only copy of a newly generated key sits in a file that operators are told to treat as legacy. If
  that file is lost, MFA secrets, digital signature images, and fax and Teleplan credentials become undecryptable.
  Debian, the devcontainer (where the override and home file are the same file) and carlos-podman (key
  pre-provisioned) are not affected.
- Correction:
  - Log the absolute path that received the key (never the key itself).
  - WARN when a home-directory file shadows `-Dcarlos_override_properties`.
  - Either persist to the explicit override, or document that the last file loaded is the target.
  - Add a test for the override-plus-home-file case.

### S14-3: When the configured override fails to load, the startup refusal blames classpath-only configuration; the new read lock adds a failure mode
- Severity: Low
- Category: bug
- Confidence: Confirmed for the misattributed message. Plausible for lock-unsupported filesystems.
- Commit: c5350045 (#5621), 28909183 (#5673)
- Location: `src/main/java/io/github/carlos_emr/CarlosProperties.java:253-269` (constructor swallows
  `IOException`), `:315-321` (new blocking shared `channel.lock`), `:341-349` (refusal text)
- Problem:
  - If `-Dcarlos_override_properties` cannot be read, the constructor logs `"Error"` and continues on the bundled
    defaults. Causes include permission denied and, new in this release, a failed `FileChannel.lock` (for example
    ENOLCK on NFSv3 without lockd).
  - Provenance is still `/carlos.properties` (classpath), so Startup refuses with: "Configuration source
    /carlos.properties is not an external properties file … supply a writable external properties file with
    -Dcarlos_override_properties=…". The operator already did exactly that.
  - Before this release the override was read without a lock, so a filesystem without lock support loaded it
    normally. Now the override is skipped. If the override path is also the home file, as in the devcontainer
    layout, startup aborts with a raw IOException.
- Evidence: the constructor's `try { readFromFile("/carlos.properties"); … readFromFile(overrideProperties); }
  catch (IOException e) { …error("Error", e); }`. `readFromFile` throws before `loadedPropertiesFile = propertyFile`.
  `getOrCreateEncryptionKey` throws on `loadedPropertiesFile == null` with the message above.
- Impact: startup is refused, which is the safe outcome. On main the same case silently generated a new
  home-directory key. But the diagnosis points the wrong way and the real cause sits in an earlier generic "Error"
  entry. Deployments with configuration on lock-less mounts stop starting.
- Correction:
  - Fail startup naming the configured override and the IOException when it cannot be read.
  - Or record the failed source and use it in the refusal text.
  - Treat an unsupported shared lock (ENOLCK/ENOSYS) as WARN plus an unlocked read, or document the POSIX-lock
    requirement in docs/startup-encryption-key.md.

### S14-4: No test pins the dependency-lock enforcement, and the carlos-emr deb build never runs in PR CI
- Severity: Low
- Category: test-gap
- Confidence: Confirmed
- Commit: be931c3f (#5517). The lock and pin were regenerated in 710fb1ac.
- Location: `scripts/debian-build.test.js:13`; `debian/rules:57-60,150-154`; `.github/workflows/deb-packages.yml:31-44`
- Problem:
  - be931c3f enforces the CARLOS lock in source builds (it drops `-Pskip-dependency-lock`) and adds the DrugRef
    `dependency-lock-maven-plugin:1.1.1:check`.
  - It also loosened the only static test from the exact DrugRef command to `"$$src/pom.xml"[^;]*\bclean package`.
    That pattern still matches if the check goal or `-DdependencyLock.filename` is deleted. Nothing asserts that
    `MVN_FLAGS` lacks `skip-dependency-lock`.
  - `debian/rules` itself runs only in `deb-packages.yml` (release/dispatch). The package-lifecycle harness (T26 in
    `docs/testing/release-2026.08-verification.json`) is manual.
  - The only recorded source build against the DrugRef lock (`docs/ui-tests/deb-install-validation.md:34-44`,
    2026-11-03) predates the 2026-11-05 repin to 93775a04 and lock regeneration in 710fb1ac.
- Evidence: `grep -rn "drugref-dependencies-lock\|dependencyLock" scripts .github` finds no test or CI reference.
  `npm run test:scripts` runs `scripts/*.test.js`, including the loosened assertion.
- Impact: if the lock is stale, the failure appears only at publish time (loud, blocks the release). If a later
  edit removes the integrity checking, no test notices.
- Correction:
  - Assert in `debian-build.test.js` that the DrugRef build line contains the `:check` goal and
    `-DdependencyLock.filename=` resolving to `debian/drugref-dependencies-lock.json`.
  - Assert that `MVN_FLAGS` contains no `skip-dependency-lock`.
  - Optionally add a small PR job, path-filtered on `debian/drugref.pin` and the lock, that runs the DrugRef
    `:check` against the pinned checkout.

### S14-5: The lintian override for maintainer-script-calls-systemctl now uses a wildcard, and its justification is out of date
- Severity: Low
- Category: process
- Confidence: Confirmed
- Commit: be931c3f (#5517)
- Location: `debian/carlos-emr.lintian-overrides:33-37`, `debian/carlos-emr-drugref.lintian-overrides:5-9`;
  `debian/carlos-emr.postinst:354,941`
- Problem: `[postinst:221]` became `[postinst:*]`, which accepts any future top-of-line `systemctl` call in the
  postinst, including a start/stop that would bypass policy-rc.d. That bypass is what the tag exists to catch. The
  comment still says the override covers "only `systemctl reset-failed`, for clearing the application unit's …
  counter", but it now also covers `systemctl reset-failed mariadb.service` (from beta6 #5554).
- Evidence: the flagged calls at head are `:354` (carlos-emr reset-failed) and `:941` (mariadb reset-failed). Both
  are benign. lintian runs `--fail-on error` (`deb-packages.yml:317`) and these tags are warnings, so the overrides
  only change what reviewers see.
- Impact: nothing is hidden today. Future reviewers lose the per-line prompt that the old pin forced.
- Correction:
  - Update the comment to cover the MariaDB unit.
  - Add a packaging test that every line-leading `systemctl` call in both postinsts is
    `is-*`/`reset-failed`/`daemon-reload` (no lifecycle verbs), which is what the override promises.

## Checked and found OK
- No silent temporary key. Every failure path aborts startup: classpath-only source, `open(READ, WRITE)` refused,
  lock or IO error, AES unavailable, short write. The appended key is `force(true)`'d before it is returned and
  used. An invalid existing key is never rotated.
- Races:
  - Static monitor in-JVM, plus an exclusive fcntl lock with re-read inside the lock across JVMs.
  - Java `FileLock` and the postinst's `fcntl.lockf` are the same POSIX record locks.
  - Thread and two-JVM tests assert a single key line and cross-decryption.
- Keys never logged. Messages carry the path and property name only.
- The appended entry's `\n\n` ends a trailing `\` continuation for LF/CR/CRLF endings (traced against `Properties`
  line-reader rules). No file is created (no `CREATE`), so no world-readable stub, and existing owner and mode are
  untouched.
- Upgrades from the betas:
  - Debian keys stay in `/etc` (carlos-ctl regenerates only when blank).
  - Legacy home-directory key files are still read, so standalone installs keep their key.
  - carlos-podman template pre-provisions the key and `AbandonOldChart=true` on a read-only tmpfs.
- Devcontainer recovery procedure checked against the Dockerfile:
  - `/scripts` is on PATH for `docker exec … server stop`.
  - `COPY ./config/shared/volumes/*.properties /root/`.
  - `qbe-reporting-account` appends with `>>`, which works with the documented single-file bind mount.
- 866f2f31 `reload_nginx` behaves the same as the old `reload || restart` and is covered by a state-table test.
- The default-site removal never touches `sites-available/default` or an operator's regular file; tests cover
  symlink, dangling, regular and absent.
- set -e safety of new constructs: `RET=false; db_get … || true`; `if ! python3 - "$PROPERTIES" <<'EOF' … then`;
  the cert function's `if is-active … else start`.
- DrugRef enforcement:
  - The pinned pom (93775a04) declares mariadb-java-client 3.5.11, HikariCP 6.2.1 and hibernate-core 7.0.0.Final,
    all present in the lock with integrity entries (53 artifacts across all scopes).
  - The README.source regeneration recipe matches `debian/rules`.
  - publish-release runs the CARLOS lock check before packaging.
- No new carlos-ctl verbs or flags in any maintainer script. The Depends floor (1.3.1) equals the pin.
- 69974cb3: `fonts-liberation` is present at head (`scripts/deb-docker-validation.sh:210`,
  `docs/ui-tests/deb-install-validation.md:1033`). 450c28e0 is an empty commit.
- `carlos-emr-drugref` depends on the exact `carlos-emr` version, so carlos-emr (and its cutover) is configured
  before DrugRef. The restart is deferred to the trigger.

## Out of scope but notable
- The postinst silently removes any `sites-enabled/default` symlink, whatever it points to (including an
  operator's re-enabled custom site), on every configure that holds the lock. This predates beta6.
- `reload_nginx` (now explicitly) starts an operator-stopped nginx whenever a self-signed certificate is regenerated
  (renew timer, or `init-config` during an upgrade). This contradicts the postinst's "operator-stopped nginx stays
  stopped" policy. The old `reload || restart` did the same.
- The `CarlosProperties` constructor still swallows a failure to read an explicitly configured override and
  continues on the bundled defaults (pre-existing; see S14-3 for the diagnostic part).
- carlos-ctl `prop_get`/`prop_set` match only `key = value`. A key written with a `:` or whitespace separator is
  valid `java.util.Properties` but invisible to `init-config`, which would append a new key that wins, losing the
  original. This is in the carlos-ctl repo.
- `CarlosProperties.saveProperty` is now dead public API that still creates files and bypasses the lock protocol.
- Startup's WEB-INF fallback is unreachable: `p` is never empty after the constructor loads `/carlos.properties`,
  and `/WEB-INF/…` is not a classpath resource.
- `docs/testing/release-2026.08-verification.json` T26 says "pinned carlos-ctl 1.3.0"; the pin is 1.3.1.
