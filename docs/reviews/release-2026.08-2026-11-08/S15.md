## Findings

### S15-1: A commit whose acknowledgement is lost is treated as a confirmed rollback, so the same page can save the prescription again
- Severity: Medium
- Category: data-integrity
- Confidence: Confirmed (traced in CARLOS code and in the Spring 7.0.6 / Hibernate 7.2 sources; not executed)
- Commit: 2b184d9f (#5627/#5631), which extends `persistCorrection`'s logic to every new, renewed and corrected save.
- Location: `src/main/java/io/github/carlos_emr/carlos/prescript/pageUtil/RxWriteScript2Action.java:2084-2111`, `:1920-1927`; tests `src/test/java/io/github/carlos_emr/carlos/prescript/pageUtil/RxWriteScript2ActionCardCorrectionUnitTest.java:590-605`, `:673-692`
- Problem: `persistStashTransaction` treats Spring's `STATUS_ROLLED_BACK` as proof that nothing was saved. In that case it restores card ids and draft revisions, the random-id map and the ReRx list, so the rendered page can submit the save again. It keeps the drafts "consumed" only for `STATUS_UNKNOWN`. With `JpaTransactionManager`, however, a failure of the JDBC `COMMIT` itself is reported as `STATUS_ROLLED_BACK`. This covers a connection dropped or killed during commit, and a database crash or failover after the commit became durable but before the reply. The chain is:
  1. Hibernate (`AbstractLogicalConnectionImplementor.commit`) marks the transaction `FAILED_COMMIT` and throws `org.hibernate.TransactionException`.
  2. With JPA bootstrap, `ExceptionConverterImpl.convertCommitException` wraps it in a `RollbackException`, with the original as its cause.
  3. `JpaTransactionManager.doCommit` hands that cause to `HibernateExceptionTranslator`, which always returns a `DataAccessException`. Its fallback is `JpaSystemException`, so a `TransactionSystemException` is never raised here.
  4. In `processCommit` that is a plain RuntimeException, not a `TransactionException`, so it goes to `doRollbackOnCommitException`.
  5. `JpaTransactionManager.doRollback` only rolls back while `tx.isActive()` is true, and it is false after `FAILED_COMMIT`. Nothing throws, so Spring reports `triggerAfterCompletion(STATUS_ROLLED_BACK)`.
  
  In practice, the only way to reach `STATUS_UNKNOWN` is an exotic non-persistence cause, or a *rollback* failure. A rollback failure is safe, because no commit was ever attempted. The classification is therefore inverted at both edges. Both "unknown outcome" tests use a fake `AbstractPlatformTransactionManager` whose `doCommit` throws `TransactionSystemException`, which the real stack does not produce for this failure.
- Evidence:
  ```java
  } catch (RuntimeException e) {
      if (completion.get() == TransactionSynchronization.STATUS_ROLLED_BACK) {
          // Only a confirmed rollback makes the old rendered version safe to retry...
          previous.forEach(PreviousIdentity::restore);      // revisions restored → replay accepted
          bean.setRandomIdDrugIdPair(previousPairs);
          bean.setReRxDrugIdList(previousReRx);
      }
  ```
  The tests fake the failure like this:
  ```java
  protected void doCommit(...) { throw new TransactionSystemException("Synthetic uncertain commit"); }
  ```
- Impact: This is the genuinely in-doubt case that #5686 and #5631 set out to protect. If the first COMMIT was in fact applied:
  - pressing Save again from the same page is accepted (the revisions match again) and writes a second, active copy of the prescription;
  - for a renewal, the restored ReRx list re-archives the source a second time;
  - the first copy has no ADD, REPRESCRIBE or DISCONTINUE audit entries, because `afterCommit` never ran.
  
  The browser receives `INCOMPLETE_RX_SAVE`. `reportRefusedSave` shows `saveIncomplete` without reloading the profile (see #5753), so the on-page profile still looks unchanged. The failure is rare on a single-host install, more plausible with a remote or replicated database, and clinically serious (a possible duplicate dispense). #5753's suggested fix, to report a "confirmed rollback" as "nothing was saved", would make this case actively misleading if it were implemented as written.
- Correction:
  - Separate failures inside the callback from failures of the commit. Call `status.flush()` as the last statement of the `TransactionTemplate` callback, so constraint and flush errors surface inside the callback and are definite rollbacks.
  - Set a flag once the callback returns. Treat any exception after that point, from the commit itself, as uncertain: keep the revisions consumed, return a distinct code that the page maps to `saveUncertain` and a profile refresh, and write an "outcome unknown" audit.
  - Optionally resolve the doubt by re-reading the new prescription row by id in a fresh transaction.
  - Replace the fake-manager tests with an integration test on a DataSource proxy whose `Connection.commit()` delegates and then throws `SQLException`.

### S15-2: In a multisite install, a prescriber with no active site cannot print a prescription (always 400, while fax works)
- Severity: Medium
- Category: omission
- Confidence: Confirmed
- Commit: 980a1be0 (#5541), which turns #5533's 500 into a 400 but leaves this legitimate request refused.
- Location: `src/main/webapp/WEB-INF/jsp/rx/ViewScript2.jsp:237,248,468-474`; `src/main/java/io/github/carlos_emr/carlos/form/pdfservlet/PrescriptionPdfServlet.java:27-45`; `src/main/java/io/github/carlos_emr/carlos/form/pdfservlet/FrmCustomedPDFServlet.java:1189-1204`
- Problem: With multisites on, `ViewScript2.jsp` always creates `vecAddressName = new Vector()` and fills it from `siteDao.getActiveSitesByProviderNo(...)`. The list is empty when the prescriber has no `providersite` row, or when all their sites are inactive. `onPrint2` nonetheless sets `useSC = true` whenever `vecAddressName != null`, and sends `scAddress=""`, because no select option matches. The new entry-point guard answers every non-fax request with `useSC=true` and an unparsable `scAddress` with `sendError(400, "Invalid satellite clinic address")`. The unit test pins exactly this with `@NullAndEmptySource`. The fax path, for the same page, ignores the empty block and renders the main clinic (`bindFaxHeaderToRecord`).
- Evidence:
  ```jsp
  <% if(vecAddressName != null) { %>
  useSC = true;              // even when the provider has zero active sites
  ```
  The servlet guard:
  ```java
  && Boolean.parseBoolean(request.getParameter("useSC"))
  && !hasSatelliteClinicFields(request.getParameter("scAddress"))) {
      response.sendError(HttpServletResponse.SC_BAD_REQUEST, "Invalid satellite clinic address");
  ```
- Impact: For such prescribers, Print and Reprint open a new tab with a 400 error page whose message ("Invalid satellite clinic address") they cannot act on, so the prescription cannot be printed. Fax still works. This was already broken on main (an AIOOBE and a 500), but #5533 offered "fall back to the primary clinic address" as the expected behaviour, and the PR states that primary-clinic printing is unchanged.
- Correction: Do either or both of the following, and add a test for the multisite/no-site page:
  - In `ViewScript2.jsp`, set `useSC = true` only when an offered block was actually selected (`vecAddress` is non-empty and the value matched).
  - In the servlet, treat a missing or empty `scAddress` as `useSC=false` and print the main clinic header, as fax does. Keep the 400 for a non-empty malformed block.

### S15-5: If the audit executor is saturated, the audit queued in `afterCommit` is silently lost; this now applies to every new prescription
- Severity: Low
- Category: silent-failure
- Confidence: Plausible
- Commit: 2b184d9f (#5627/#5631)
- Location: `src/main/java/io/github/carlos_emr/carlos/prescript/pageUtil/RxWriteScript2Action.java:2115-2132,2224`; `src/main/java/io/github/carlos_emr/carlos/log/LogAction.java:122-128,274-284`
- Problem: New saves now queue their ADD, DRUGREASON, REPRESCRIBE and DISCONTINUE audits in `afterCommit`. `LogAction.addLog` is asynchronous, but on `RejectedExecutionException` (a queue of 1000 is full and all threads are busy) it falls back to `addLogSynchronous`, which calls `OscarLogDao.persist`. Inside `afterCommit` the JPA resources are still bound and the holder still reports an active transaction. The `@Transactional(REQUIRED)` DAO call therefore joins the already-committed transaction, as the Spring `TransactionSynchronization#afterCommit` documentation warns: "use PROPAGATION_REQUIRES_NEW". The identity insert is then delayed and never flushed, and no error is logged. LogAction's own comment says this fallback ensures "no audit event is silently dropped". Before this commit, a new save audited outside any transaction, so the fallback committed normally.
- Evidence: `afterSaveCommit(() -> LogAction.addLog(...LogConst.ADD, LogConst.CON_PRESCRIPTION, scriptId, ...))` leads to `executeAsync`, then (on `RejectedExecutionException`) to `addLogSynchronous(oscarLog)`, then to `getOscarLogDao().persist(oscarLog)`. `AbstractDaoImpl.persist` is just `entityManager.persist(o)`, with no flush.
- Impact: Prescriptions saved while the audit pipeline is backed up, for example during a database slowdown, can lack their audit rows, and nothing reports it. This is rare.
- Correction: In `afterSaveCommit`, run the audit through a `REQUIRES_NEW` `TransactionTemplate`, or make the synchronous fallback start its own transaction. To confirm, add a test that injects a rejecting executor (`LogAction.setExecutorServiceForTesting`) around a real JPA commit and asserts that the `OscarLog` row exists.

## Checked and found OK
- **Transaction coverage.** There is exactly one `PlatformTransactionManager` in the web context (`JpaTransactionManager`), and no open-EntityManager-in-view filter. The save path's writes all go through JPA `AbstractDaoImpl` with `@Transactional(REQUIRED)` and join the REQUIRES_NEW transaction:
  - prescription header (PrescriptionDao);
  - drug rows (DrugDao.persist);
  - drug reasons;
  - partial dates;
  - the ReRx and superseded archives (`RxManagerImpl.archiveDrug`, which is not transactional itself, with its `addLogSynchronous` audit).
  
  No Rx DAO uses REQUIRES_NEW, and no legacy JDBC writes appear in the save path.
- **What the save request writes.** It writes no case-management note, allergy or interaction acknowledgement, or favourite.
- **Rollback restoration.** A rollback restores drugId, script_no, revision, the random-id map and the ReRx list, and clears the `scriptId` attribute. `RxCorrectionSaveRollbackIntegrationTest` proves a real H2 rollback of the drug, prescription and partial-date rows, then a single retry.
- **Duplicate submits and replays.** Duplicate or concurrent submits are serialised on the session bean. Revisions are consumed before any write, so a replay after a committed save is refused with 400 or 409. FormSubmissionGuard is not needed for this path.
- **Security on the changed routes.** `updateSaveAllDrugs` checks `_rx` write globally and per patient (`requirePatient`), is POST-only (405) and refuses a patient mismatch (409). Its AJAX POSTs carry the CSRFGuard header. The renal gate checks `_rx` read plus patient-level access. The PDF pre-check only adds a refusal, after LoginFilter.
- **Satellite validation.** It accepts every block that `RxSatelliteClinicAddress.html` composes: values are HTML-encoded, so they cannot contain `<br>` or `</b>`. Accents, unit numbers, embedded newlines and postal formats are unaffected.
- **Limited-use links.** `preventDefault()` runs before `addLuCode`. The JS-attribute and HTML encoding contexts are correct.
- **Custom notes.** Quantity "0" is display-only. Notes are still saved with quantity null, and their print text has no Qty line.
- **Renal validation.**
  - The CrCl formula is unchanged.
  - An invalid weight, an invalid age or future DOB, or an invalid selected creatinine gives N/A with no highlighted dose. A newer invalid measurement is not silently overridden by an older lab.
  - A missing observation gives N/A with 200, and an infant (age 0) gives N/A with 200.
  - Stale responses are ignored. `divId` and the ATC code are encoded in JS-attribute context and URL-encoded in the request.
- **#5600 privacy.** The HL7 dump, QR chunk contents and raw exception logging are gone. `LogSafe.exceptionTrace` never reads exception messages. The demographic exceptions carry no PHI. The gender log carries only a LogSafe-sanitised demographic number.
- **Uncertain-save classification.** Within this deployment, no 4xx can follow a commit in `updateSaveAllDrugs`. CSRF rejections become 403 and login redirects land off WriteScript, so both are correctly treated as refusals. All five locales define `saveUncertain`.

- Pre-existing: yes (present on origin/main)
- Commit: none (pre-existing). The slice reviewed this call site because it is the per-card caller of the renal function changed by 967d1175 and 0581f152.
- Location:
  - Sink: `src/main/webapp/WEB-INF/jsp/rx/prescribe.jsp:567`, the same line on main and at release head.
  - Source: `src/main/java/io/github/carlos_emr/carlos/prescript/pageUtil/RxWriteScript2Action.java:289` (main `:290`), `rx.setAtcCode(this.getAtcCode())`, where `setAtcCode` is a `@StrutsParameter` (`:3021`).

- Problem: `prescribe.jsp:567` writes the card's ATC code into a JavaScript string literal inside a `<script>` block with a raw `<%= %>` expression; nothing encodes it. The same file encodes the same value correctly for the allergy check (`:774`, `context="javaScriptBlock"`) and for the hidden input (`:284`). The value is not only drugref data:
  - the legacy update path (`rx/WriteScript`, `action=update*`) copies a request parameter into the staged card without validating it;
  - the save persists it to `drugs.ATC`, which is `varchar(20)`;
  - represcribing that drug later, by any user, copies it back onto a new card that this line renders.
  
  The block runs for every staged card while `RENAL_DOSING_DS=yes`, which is the shipped default (`carlos.properties:155`).
- Evidence: `<script type="text/javascript">getRenalDosingInformation('renalDosing_<%=rand%>','<%=rx.getAtcCode()%>');</script>` — the ATC value sits unencoded inside the JS string argument. Compare `:774`, which wraps the same getter in `<carlos:encode ... context="javaScriptBlock"/>`.
- Impact: A persisted ATC value that closes the string and the script element would execute in the prescriber's session when the card renders, i.e. stored XSS in the prescribing workspace. Because the field is persisted and re-rendered on represcribe, one user can plant it and another trigger it. The `varchar(20)` column limits length, and the packaged ModSecurity policy would likely score a naive attempt, so exploitation is constrained but not clearly prevented at this layer.
- Correction: Encode at the sink like the sibling calls: `getRenalDosingInformation('renalDosing_<%=rand%>','<carlos:encode value="<%=rx.getAtcCode()%>" context="javaScriptBlock"/>')`. Consider validating the ATC parameter server-side (ATC codes are a fixed alphanumeric shape).

### S15-P2: REST `/ws/rs/rx/prescribe` is not atomic — a late drug failure leaves a committed header and earlier drugs
- Severity: Medium
- Category: data-integrity
- Confidence: Confirmed
- Pre-existing: yes (present on origin/main). This is the REST twin of the web defect #5627 that the slice (2b184d9f) fixed only for the web path.
- Commit: none (pre-existing)
- Location: `src/main/java/io/github/carlos_emr/carlos/managers/RxManagerImpl.java:457-528` (same line numbers on main); header write `PrescriptionManagerImpl.java:181-203` (`:196` persist, same on main); REST caller `RxWebService.java:486-502` (same on main)
- Problem: `prescribe` writes the prescription header (`createNewPrescription` → `prescriptionDao.persist`) and then, in a loop, adds or updates each drug. There is no enclosing transaction (the method is not `@Transactional`, and neither is `RxWebService.prescribe`). If a drug add/update returns null partway, the method returns null after the header and the earlier drugs are already committed. `updateDrug` also archives the replaced drug only after adding the new one, so a failure can leave both.
- Evidence: `Prescription p = this.prescriptionManager.createNewPrescription(...)` then the `for (Drug d : drugs)` loop calling `updateDrug`/`addDrug`; on `temp == null` the method does `return null;` with no rollback. `RxWebService` turns that null into `resp.setSuccess(false)` with message "Failed to prescribe drugs".
- Impact: A REST client that gets a failure response can nonetheless have created a header plus a partial set of active medications, with no indication which were written. Integrators retrying would duplicate. Lower reach than the web path because fewer deployments use this endpoint.
- Correction: Wrap `prescribe` (or `RxWebService.prescribe`) in a single transaction so a failed drug rolls back the header and the earlier drugs, matching the web fix.
