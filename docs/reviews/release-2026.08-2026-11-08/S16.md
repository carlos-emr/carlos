## Findings
### S16-1: Users who hide "Unresolved Issues" in CPP preferences can no longer save, sign or switch encounter notes
- Severity: High
- Category: regression
- Confidence: Confirmed
- Commit: 68af38f1 (#5601)
- Location:
  - `src/main/webapp/js/newCaseManagementView.js.jsp:1449-1470` (`loadDiv` `refreshed` flag)
  - `:3498-3500` (`onIssueUpdate`)
  - `:3380`, `:3367-3369` (sticky `issueUpdateFailed`)
  - `src/main/webapp/WEB-INF/jsp/casemgmt/newEncounterLayout.jsp:277-279,597-598` (`hideCpp` removes the module)
  - `newCaseManagementView.js.jsp:952-954` ("Preferences may have intentionally removed the module")
- Problem:
  - Every issue refresh ends with `onIssueUpdate`, which calls `loadDiv('unresolvedIssueslist', …, complete)`.
  - The commit changed `loadDiv` to complete with success only when `$(div).update(...)` ran (`complete(refreshed && 2xx)`). Main completed with success on any 2xx.
  - A provider can set Preferences → CPP → Unresolved Issues = Hide (with CPP preferences enabled). `hideCpp('unresolvedIssues')` then removes `#unresolvedIssues`, so `#unresolvedIssueslist` never exists.
  - `$('unresolvedIssueslist')` returns null and `.update` throws (CarlosAjax swallows the throw). `refreshed` stays false and the refresh fails.
  - That failure triggers `alert(updateIssueError)` and sets `issueUpdateFailed = true`. After that, `deferNoteSaveUntilIssues` refuses every Save, Sign & Save, Sign-Save-Exit, New Note, Edit note and filter with the same alert.
  - The next issue refresh resets the flag but fails again, so the chart cannot recover.
  - The refresh runs on: Edit of any note (`:2535`), New Note / `writeNewNote` (`:3626`), every successful CPP save (`:1412`), Assign issue, and noteIssueList issueChange/issueDelete.
- Evidence: a node reproduction runs the real carlos-ajax.js and the real barrier code from both branches. One note-editor issue refresh is run with the panel absent:
  ```
  main    | issues panel hidden | issueUpdateFailed=false | Save blocked=false | alerts=[]
  release | issues panel hidden | issueUpdateFailed=true  | Save blocked=true  | alerts=["An error occurred while updating issues. Most likely your session has expired.", ...]
  release | issues panel shown  | issueUpdateFailed=false | Save blocked=false | alerts=[]
  ```
  The repo's own test (`scripts/echart-cpp-issue-refresh.test.js:204-207`, "panel rendering") pins a throwing panel update as "block saves". No test or browser check covers a hidden panel.
- Impact:
  - For every provider with that preference, the first note edit, new note, CPP edit or issue change leaves the chart unable to save or sign. The alert wrongly says the session has expired.
  - Only the initial server-rendered editor still saves, until the first such action; then the page must be reloaded.
  - After a successful CPP save the same alert appears, so the clinician may re-enter the CPP item and create a duplicate.
  - #5750's workaround (add or remove an issue) does not help here. The same failure also occurs whenever the panel is not in the DOM: a module still loading, or a role denied the legacy `_unresolvedissues` object.
- Correction:
  - In `loadDiv` (or in `onIssueUpdate`), treat an absent target as "nothing to refresh = success". For example, skip the Unresolved Issues reload when `!$('unresolvedIssueslist')`. Keep a real update failure as a failure.
  - Apply the same rule to the note-editor container in `ajaxUpdateIssues`. `updateSucceeded` is false when the `sig` div is absent, for example after the full/quick chart toggle (`viewFullChart` is not deferred).
  - Add a JS test and a browser check with Unresolved Issues hidden.

### S16-2: Patient-isolation doc still says a malformed or zero patient is refused with 403
- Severity: Low
- Category: docs
- Confidence: Confirmed
- Commit: 7115e3ee (#5496), left stale by 93382265 (#5524)

### S16-3: The takeover check (#5647) no longer requires the user to be told the note lock was lost
- Severity: Low
- Category: test-gap
- Confidence: Confirmed
- Commit: b0699e5b (#5647)
- Location: `scripts/concurrency-chart-note-takeover-playwright-checks.js:120-124`; `scripts/concurrency-chart-note-takeover.test.js:101-103`; `src/main/webapp/js/newCaseManagementView.js.jsp:3043-3048` vs `:2928-2931`
- Problem:
  - On main the check required a "lock" alert or message: "the user must also be told the lock was lost".
  - It now also accepts any alert ending in " 409", meaning the generic `savingNoteError + status` ("Failed to save note! 409").
  - That relaxation matches what the Save and Sign & Save path (`saveNoteAjax` onFailure) actually does. That path neither shows `noteLockLostError` ("Your note lock has been lost. Please copy your note text, close this window, and reopen the chart.") nor sets `lostNoteLock`. The ajaxsave path does both.

- Correction: in `saveNoteAjax` onFailure, treat 409 like `ajaxSaveNote` does (set `lostNoteLock` and alert `noteLockLostError`), or show a lock-specific message. Then restore the check's requirement for a lock-specific message.

### S16-4: Routine photo-upload rejections now write WAF audit entries containing the session cookie
- Severity: Low
- Category: privacy
- Confidence: Plausible (WAF config read; no packaged run)
- Commit: 83ab2f3a (#5591)
- Location: `src/main/webapp/WEB-INF/jsp/casemgmt/uploadimage.jsp:86-93`; `debian/assets/modsecurity/main.conf:102-104`
- Problem:
  - Multipart rejections that reach the `input` result were answered 200 before; they now get 400. The old Playwright assertion was `post.status() === 200`.
  - These rejections are things like a disallowed content type (PNG/HEIC) or an empty part.
  - The packaged WAF audits every non-404 4xx with parts ABFHZ. Part B holds the request headers: the Cookie with JSESSIONID, and the Referer `…/casemgmt/ViewUploadimage?demographicNo=<id>`.
  - The action-level errors were already 500 via `errorpage.jsp`, so only the `input` cases are new.
- Impact: a routine user error now leaves session cookies and a PHI-correlating id in `modsec_audit.log`. This is the same class as #5781 (renal dosing), on a different route.
- Correction: address it together with #5781, for example by excluding expected application 400s from the audit status or masking the Cookie/Referer headers. Alternatively answer validation re-renders with 200 or 422 kept out of `SecAuditLogRelevantStatus`.

## Pre-existing issues
### S16-P1: The CPP save and the note Save/Sign path accept a redirected 200 page as success, so CPP text can be lost silently
- Severity: Medium
- Category: silent-failure
- Confidence: Confirmed (code traced; not run)
- Pre-existing: yes (present on origin/main)
- Commit: n/a (main; 68af38f1 only wrapped this success path in try/catch)
- Location:
  - release `src/main/webapp/js/newCaseManagementView.js.jsp:1404-1414` (`updateCPPNote` onSuccess) and `:3034-3036` (`saveNoteAjax` onSuccess)
  - main `:1395-1398` and `:3012-3014`
  - `src/main/java/io/github/carlos_emr/carlos/sec/LoginFilter.java:444-461` (main and release; `INACTIVITY_LIMIT_MINS` defaults to 60 at `:390-392`)
  - `src/main/webapp/share/javascript/carlos-ajax.js:127-136` (only `errorpage` redirects are detected)
- Problem:
  - With the session still alive but more than 60 minutes since the last user-initiated request, LoginFilter answers any request, AJAX included, with a 302 to `/logoutPage`. Background polls keep the session alive without resetting the activity timer. The facility-selection guard also redirects.
  - The XHR follows the redirect and receives 200 HTML. `updateCPPNote` treats any 2xx as saved: it has already hidden the dialog, then replaces the CPP panel with the logout page and runs the issue refresh.
  - `saveNoteAjax` likewise replaces `#notCPP`, which holds the editor and typed text, with that page.
  - In contrast, `ajaxSaveNote` (`:2910-2917`) and autosave (`autosaveAcknowledged`, `:3680`) validate a server acknowledgement for exactly this case.
- Evidence: `onSuccess: function (request) { … if (request.responseText.length > 0) { $(div).update(request.responseText); } ajaxUpdateIssues(…)` has no acknowledgement check. LoginFilter does `httpResponse.sendRedirect(contextPath + "/logoutPage")` without checking `isAjax`.
- Impact:
  - A clinician who returns to a chart after an hour and saves a CPP item sees the dialog close as if it saved. The item is not stored and the typed text is gone; CPP items have no draft.
  - A note Save in the same state wipes the editor. The 5-second autosave draft limits that loss.
  - Related test coverage: #5802.
- Correction: give `updateCPPNote` and `saveNoteAjax` an acknowledgement check like `ajaxSaveNote` (a marker the real response carries, or `responseURL` still at the action). Alternatively make LoginFilter's inactivity branch answer AJAX with the status-code rejection (`UnauthenticatedRejectionResolver`), not a 302.

### S16-P4: `PatientForm.EDITED_DATE_COMPARATOR` throws NullPointerException for forms without dates and can break email chart notes
- Severity: Low
- Category: bug
- Confidence: Plausible (depends on data)
- Pre-existing: yes (present on origin/main)
- Commit: n/a (#5691 fixed only `CREATED_DATE_COMPARATOR`)
- Location:
  - release `src/main/java/io/github/carlos_emr/carlos/encounter/data/EctFormData.java:330-344`; main `:372-387`
  - `src/main/java/io/github/carlos_emr/carlos/email/util/EmailNoteUtil.java:264-265` (main and release)
  - `src/main/java/io/github/carlos_emr/carlos/managers/EmailManager.java:148-153`
- Problem:
  - If one row has a null `edited`, the comparator dereferences the other row's `created` with no null check: `o2.edited.compareTo(o1.created)` / `o2.created.compareTo(o1.created)`.
  - `formCreated` is nullable in every form table and `formEdited` is nullable in formBPMH, as stated in 1b7cbfee's own message.
  - `EmailNoteUtil` sorts the email's form attachments with this comparator in `addEmailNote`. That call runs after `emailSender.send()` and after the SUCCESS status update, and only `EmailSendingException` is caught.
- Evidence: the comparator body, and `Collections.sort(formList, PatientForm.EDITED_DATE_COMPARATOR);`.
- Impact:
  - An email with two or more form attachments, one lacking both dates, raises an NPE after the email was sent. The chart note is not written, the user gets an error page and may resend.
  - If the call is transactional, the SUCCESS status may also roll back. That is unverified.
- Correction: use a null-safe key comparator as #5691 did (`edited ?: created`, nulls last, ID tie-break).

### S16-P5: The nullable `casemgmt_note.archived` and `position` columns are still mapped to primitives with no NULL handling
- Severity: Low

- Confidence: Plausible (requires an explicit NULL in the row)

### S16-P6: The messenger popup link puts the provider's display name into the URL without encoding
- Severity: Low
- Category: bug
- Confidence: Confirmed (code); cosmetic impact
- Pre-existing: yes (present on origin/main)
- Commit: n/a
- Location:
  - `src/main/java/io/github/carlos_emr/carlos/encounter/pageUtil/EctDisplayMsg2Action.java:59` (main and release)
  - consumer `src/main/java/io/github/carlos_emr/carlos/messenger/pageUtil/MsgDisplayDemographicMessages2Action.java:152-153` (main `:153`)
- Problem: `"&userName=" + bean.userName` is concatenated raw. The name comes from the request or from the provider's first and last name and may contain `&`, `#`, `+` or `%`.
