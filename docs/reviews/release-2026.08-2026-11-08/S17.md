### S17-1: #5545 fixed only one of three endpoints that turn their own 400 into a 500
- Severity: Low
- Category: omission
- Confidence: Confirmed
- Commit: 87a23718 (#5545)
- Location: `src/main/java/io/github/carlos_emr/carlos/webserv/rest/ScheduleService.java:511-562` (fetchDays), `:664-700` (fetchProviderAppts), fixed one at `:655-656`
- Problem: #5545 added `catch (WebApplicationException e) { throw e; }` to `fetchProvidersApptsCount`
  only. Two sibling endpoints in the same file have the same nesting:
  - `GET /schedule/fetchDays/{s}/{e}/{providers}`
  - `GET /schedule/fetchProviderAppts/{p}/{s}/{e}`

  In both, the inner `catch` throws a 400 "Path parameter has the wrong format", and the outer
  `catch (Exception e)` then catches it, logs an ERROR with a stack trace, and rethrows a 500
  "Internal server error". This is the same defect class as #5532.
- Evidence: `try { ... try { sDate = IsoDates.parseIso8601Date(sDateStr); ... } catch (Exception e) { throw new WebApplicationException(...BAD_REQUEST...) } ... } catch (Exception e) { logger.error("ScheduleService.listAppointmentsByPeriodProvider error", e); throw new WebApplicationException(...INTERNAL_SERVER_ERROR...) }`. Lines 518-519 and 560-561; lines 682-683 and 697-699.
- Impact: REST clients get a 500 for malformed date input, and the server log records a spurious
  ERROR. Server-log audits count these as unexplained signatures, the way they flagged #5532.
- Correction: add the same `catch (WebApplicationException e) { throw e; }` ahead of the generic catch
  in both methods. Extend the CXF endpoint test to cover them.

### S17-3: Patient alert, custom provider fields and waiting-list note are still silently truncated at 255 characters
- Severity: Medium
- Category: silent-failure
- Confidence: Confirmed
- Commit: 7bac5ad1 (#5650). The gap is older than this commit; #5650 left these fields outside the add/edit alignment.
- Location:
  - Alert inputs: `WEB-INF/jsp/demographic/edit-form-clinical.jsp:1321` (alert textarea, no maxlength)
    and `add-form-clinical.jsp:617` (cust3 textarea).
  - Waiting-list note inputs: `add-form-clinical.jsp:511` and `edit-form-clinical.jsp:1141`.
  - Writes: `demographic/pageUtil/DemographicUpdate2Action.java:512-517`,
    `DemographicAddRecord2Action.java:325-328,420` and `webserv/rest/DemographicService.java:663-681`.
- Problem: `Demographic.validateFieldLengths()` and the shared limits fragment do not cover:
  - `demographiccust.cust3`, the patient alert, `varchar(255)`. It is an 8-row textarea on edit.
  - `cust1`, `cust2` and `cust4` (nurse, resident, midwife), each `varchar(255)`.
  - `waitingList.note`, `varchar(255)`.

  Packaged installs run MariaDB with `sql_mode = ""` (`debian/assets/mariadb/60-carlos-emr.cnf:43`).
  CARLOS connects with `jdbcCompliantTruncation=false` (`carlos.properties:54`), and the connector only
  forces STRICT when that option is true. MariaDB therefore cuts longer values to 255 characters,
  raises only a warning, and the save reports success. The project's own `EmailFieldLengthValidator`
  Javadoc calls this outcome unacceptable for clinical data.

  On strict installs the REST update now fails after the custom-field and waiting-list writes have
  committed, because neither the service nor the manager has a transaction around them.
- Evidence: `cust.setAlert(request.getParameter("alert"));` has no length check. No `maxlength` and no
  JS guard exist on the `alert`, `cust3` or `waiting_list_note` inputs.
- Impact: the end of a long patient safety alert is silently lost. Neither the user nor the admin is
  told at save time.
- Correction:
  - Add `DemographicCust` and waiting-list note limits (255 code points) to the server-side validation
    on add, edit and REST, returning a visible error.
  - Add `alert`, `cust3` and `waiting_list_note` to `demographic-field-length-limits.jspf`.
  - Alternatively, widen `cust3` (alert) to TEXT in a forward migration.

### S17-6: Bulk updates stamp `updatedatetime` with the database clock, and the new +1-second rule keeps a skewed time
- Severity: Low
- Category: silent-failure
- Confidence: Plausible
- Commit: e0759727 (#5561)
- Location:
  - `commn/dao/SiteDaoImpl.java:79` (bulk update)
  - `commn/model/Appointment.java:379-385` (`@PreUpdate`)
  - `utility/OscarTrackingBasicDataSource.java:316-321` (connection time zone)
  - `debian/assets/skel/carlos-emr.env:41-43` (`CARLOS_TZ`)
  - `commn/dao/OscarAppointmentDaoImpl.java:243-253` (`findByUpdateDate`)
- Problem:
  - Renaming a site now runs
    `update appointment set location=?, updatedatetime=greatest(current_timestamp, timestampadd(second,1,updatedatetime))`.
    It touches every historical appointment at that site and uses the MariaDB session clock.
  - Entity writes use the JVM clock. The new `@PreUpdate` then sets `max(now, persisted + 1 s)`, so a
    stored future value stays ahead: every later edit advances from it.
  - The packaged JVM runs in `CARLOS_TZ`, which the env file says should be the clinic zone, not UTC.
    MariaDB keeps the host's SYSTEM zone: the cnf sets no `default-time-zone`.
  - CARLOS appends `connectionTimeZone=<JVM zone>` to the JDBC URL. Connector/J 3.5.11 only sets the
    session `time_zone` when `forceConnectionTimeZoneToSession` is true (`StandardClient.addTimeZoneCommand`).
  - On a UTC cloud host with `CARLOS_TZ=America/Toronto`, a site rename therefore stamps every row at
    that site four to five hours ahead of clinic time. Those rows stay ahead for that long.
  - Sync clients of the SOAP `getAppointmentsUpdatedAfterDate` call (`updateDateTime > cursor ORDER BY
    updateDateTime LIMIT n`) that move their cursor to the newest value seen will jump ahead and skip
    ordinary edits to other appointments made in that window.
- Evidence: SiteDaoImpl.java:79. The connector reads `if (!Boolean.TRUE.equals(conf.forceConnectionTimeZoneToSession())) return;` and the option defaults to null. No `default-time-zone` is set anywhere under `debian/`.
- Impact: needs a split time-zone host, a multisite rename and a cursor-based sync client. Effect:
  silent sync gaps and "last updated" times in the future. Edit conflict detection itself still works,
  because versions keep increasing.
- Correction: bump `updatedatetime` with an application-supplied timestamp bound as a parameter (the
  JVM clock) instead of `current_timestamp`. Alternatively, force the session time zone with
  `forceConnectionTimeZoneToSession=true` (or the `timezone` option), and document that the MariaDB and
  JVM zones must match.
- What would confirm it: on a packaged UTC host with `CARLOS_TZ=America/Toronto`, compare
  `SELECT @@session.time_zone, NOW()` over the application's connection with the JVM clock, then rename
  a site and read `appointment.updatedatetime`.

### S17-7: The web merge still uses the patient lock that 8e70d7a8 found can deadlock disjoint merges
- Severity: Low
- Category: bug
- Confidence: Plausible
- Commit: a24c5666 (#5609); the gap was left by 8e70d7a8 (#5655)
- Location:
  - `demographic/pageUtil/DemographicMergeRecord2Action.java:154-160`
  - `commn/dao/DemographicDaoImpl.java:1786-1791` (`findForUpdate`) and `:1795-1802` (`lockForMerge`)
  - `commn/model/Demographic.java:1571-1577` (eager `demographic_merged` collection) and `:1685`
    (eager provider)
  - `util/persistence/OscarMySQL5Dialect.java:67`
- Problem: the web merge path (`admin/MergeRecords`, the normal UI) locks every participant with
  `demographicDao.findForUpdate(id)`. That is `em.find(Demographic.class, id, PESSIMISTIC_WRITE)` on an
  entity with an eager `@ElementCollection` over `demographic_merged` and an eager provider join.
  Because `supportsAliasLocks()` returns false, the lock clause covers every joined table.

  A day later, 8e70d7a8 added `lockForMerge`, a scalar `SELECT ... FOR UPDATE` on the primary key, with
  the comment "A hydrated PESSIMISTIC_WRITE also locks the eager demographic_merged join. Its empty index
  gaps can deadlock two otherwise disjoint merge parents." It switched only the REST/manager path. The
  web path inserts into `demographic_merged` while holding those gap locks.
  `DemographicMergeMariaDbIntegrationTest` exercises only `DemographicManager`. The web action has
  mocked unit tests only.
- Evidence: `if (demographicDao.findForUpdate(id) == null) { return false; }` (web) against
  `if (!demographicDao.lockForMerge(id))` (DemographicManagerImpl.java:744).
- Impact: two administrators merging different duplicate sets at the same time can hit an InnoDB
  deadlock or lock-wait timeout. The transaction rolls back cleanly and the user sees the generic
  error page, so no data is corrupted. The lock also blocks the patient's MRP provider row.
- Correction: use `demographicDao.lockForMerge(id)` in `mergeRecords`, and add a web-action case to
  the MariaDB contention test.

### S17-P4: SOAP "updated after" paging silently skips appointments that share the boundary second
- Severity: Medium
- Category: data-integrity
- Confidence: Confirmed
- Commit: n/a. e0759727 makes large ties more likely.
- Location: `commn/dao/OscarAppointmentDaoImpl.java` release `:243-253,894-905` / main `:213-223,864-875`; `commn/dao/AppointmentArchiveDaoImpl.java:65-75` (both); `webserv/ScheduleWs.java:158-166`
- Problem: the queries are `x.updateDateTime > ?1 order by x.updateDateTime` with
  `setLimit(itemsToReturn)`, on a DATETIME(0) column, with no tie-breaker.
  - A client that pages by passing the last `updateDateTime` it received loses every unreturned row
    from that same second.
  - If more rows share one second than `itemsToReturn`, the client can never page past them.
  - Same-second runs are routine: recurring-series creation, day-sheet acknowledgment, and since
    e0759727 every appointment of a renamed site gets one shared value.
- Evidence: `"select x from Appointment x where x.updateDateTime>?1 order by x.updateDateTime"` and `setLimit(query, itemsToReturn)`.
- Impact: schedule-sync integrations (reminders, portals) silently miss appointment changes.
- Correction: order by `(updateDateTime, id)` and accept an `(updatedAfter, afterId)` cursor, or
  document an inclusive bound with deduplication by id on the client.
