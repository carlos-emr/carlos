## Findings

### S18-1: HRM "Earlier Version n of N" labels count the other way from lab versions on the same picker, and their order is not reliably chronological
- Severity: Low
- Category: bug
- Confidence: Confirmed
- Commit: 1d363415 (#5564, fixes #3954)
- Location: `src/main/webapp/WEB-INF/jsp/documentManager/attachDocument.jsp:713-726`, `src/main/webapp/WEB-INF/jsp/eform/attachEform.jsp:245-256`, `src/main/java/io/github/carlos_emr/carlos/hospitalReportManager/HRMUtil.java:232-271`, `src/main/java/io/github/carlos_emr/carlos/hospitalReportManager/dao/HRMDocumentToDemographicDao.java:42`
- Problem: The attachment pickers now group HRM versions and label each earlier version with `earlierVersionOf` = "Earlier Version {position} of {count+1}". `position` is the index in `duplicateLabIds`. `HRMUtil.filterDuplicates` builds that list while iterating `findByDemographicNo` (`order by h.reportDate DESC`), so the first entry is normally the most recent earlier version. When the report dates tie, the order is arbitrary, and a replaced "newest" is appended at the end.

  The same picker numbers lab versions the opposite way: `totalVersions - versionLoop.index`, so "1 of N" is the oldest. An HRM "Earlier Version 1 of 3" is therefore usually the second-newest report, while a lab "Earlier Version 1 of 3" is the original. HRM version rows also show no date and no name in their visible label; the lab version rows do show a date.
- Evidence: attachDocument.jsp:713-715 `<c:forEach items="${hrmVersionIds}" ... varStatus="hrmVersionLoop"> <fmt:message key="...earlierVersionOf" ...><fmt:param value="${hrmVersionLoop.count}"/>`. Labs at :641/:651 use `${totalVersions - versionLoop.index}`. HRMDocumentToDemographicDao:42 has `order by h.reportDate DESC`. HRMUtil:257-271: the previous display entry is appended when a newer duplicate is found later.
- Impact: A clinician choosing which earlier HRM report to attach to a referral or eForm can pick the wrong version if they trust the label. Preview is available, and the default (top-level) item is still the newest, so the risk is limited, but the new UI is misleading.
- Correction: Order `duplicateLabIds` by the same newness rule (`HRMResultsData.isNewer`, then time received) and number versions oldest = 1, as labs do. Alternatively, drop the "n of N" ordinal and show each version's report date and time received in the label.

### S18-P1: Unlinking a mismatched HL7 lab leaves its readings, and its other versions, on the wrong patient's chart
- Severity: High
- Category: data-integrity
- Confidence: Confirmed (code path). The "older version shown as current" effect is Plausible.

It sets `patientLabRouting.demographic_no = UNMATCHED` only for the one requested segment (`findByLabNoAndLabType(labNo, "HL7")`, :83) and never touches `measurements` rows (`lab_no` extension) or the other versions' routing. ### S18-P6: Any per-row failure silently truncates the Inbox document list
- Severity: Low
- Category: silent-failure
- Confidence: Confirmed for the catch-all mechanism. The specific bad-data trigger (a routing or ctl_document row without a document) is Plausible.
- Commit: none (pre-existing; #5689 removed one NPE trigger but kept the catch-all)
