## Findings

### S19-1: A persistent inbound fax outage now leaves one WARN per JVM lifetime, so ERROR-level monitoring and the packaged log audit no longer see it
- Severity: Low
- Category: silent-failure
- Confidence: Confirmed
- Commit: 61429a7f (#5612)
- Location:
  - `src/main/java/io/github/carlos_emr/carlos/fax/core/FaxImporter.java:438-446`
  - `src/main/java/io/github/carlos_emr/carlos/fax/core/FaxPollBackoff.java:53-62`
  - `docs/fax-provider-configuration-and-ux.md:136-139`
  - `docs/ui-tests/deb-install-validation.md:1852-1858`
- Problem:
  - **Before:** on main, every failed inbound listing or credential decryption logged an ERROR, every poll (60 s).
  - **Now:** `recordPollFailure` logs only when `pollBackoff.failed()` returns true. That is the first failure of a streak, and the log is at WARN. The hourly capped retries that keep failing log nothing at all.
  - **Status badge:** the scheduler status JSON (`FaxManagerImpl.getFaxSchedularStatus`) still reports a running scheduler with an empty `lastError`.
  - **Only remaining signal:** the alert on Configure Fax, which also resets on restart.
  - **Stale validation doc:** the packaged-install validation guide still names the per-minute `FaxImporter.java:406` "Fax provider error for account ..." ERROR as the sign that the `fax-configure` fixture was not restored, and calls the backoff "missing". That ERROR no longer exists, and `scripts/deb-server-log-audit.sh` reduces only ERROR, FATAL and SEVERE events.
- Evidence: `if (pollBackoff.failed(faxConfig.getId())) { … log.warn("Inbound fax polling failed for account {} …") }`, where `failed()` ends `return previous == null;`. Main had `catch (FaxProviderException e) { log.error("Fax provider error for account {} …") }` on every poll. `FaxImporterPollTest` pins exactly one failure log line across 11 failed polls.
- Impact:
  - **Who misses it:** sites that alert on ERROR lines (journal or logwatch filters), and the deb log audit.
  - **What they miss:** that inbound faxes stopped reaching CARLOS days ago. Faxes stay unread at SRFax, so they are delayed, not lost. The only way to find out is to open Configure Fax.
  - **Why it is a change:** removing the per-minute noise was intended (#4437), but the log went from 60 ERRORs an hour to none ever.
- Correction:
  - Log the first failure of a streak at ERROR, once.
  - Log a WARN with the consecutive count (no provider text) at each capped hourly retry that still fails.
  - Optionally expose a polling-failure count in `getFaxSchedularStatus`.
  - Update `deb-install-validation.md:1852-1858` and app-findings-log finding 180 to the new log shape.

### S19-2: Resolving a failed email now persists, and erases the stored failure reason without recording who resolved it
- Severity: Low
- Category: data-integrity
- Confidence: Confirmed
- Commit: abdba03e (#5649)
- Location:
  - `src/main/java/io/github/carlos_emr/carlos/email/admin/ManageEmails2Action.java:228`
  - `src/main/java/io/github/carlos_emr/carlos/managers/EmailManager.java:272-276`
  - `src/main/java/io/github/carlos_emr/carlos/commn/dao/EmailLogDaoImpl.java:168-189`
  - `src/main/webapp/WEB-INF/jsp/admin/emailStatusResults.jspf:42-43`
- Problem:
  - `setResolved` passes `errorMessage = null`. The DAO's RESOLVED update writes `e.errorMessage = :msg` as NULL, never touches `timestamp`, and nothing calls `LogAction`.
  - On main, Resolve was never dispatched (#5641), so in practice the failure text survived. From this release, every Resolve erases it permanently.
  - **Visible effect:** the result card's error popover disappears. The row keeps its original send time, and nothing records who resolved it or when.
  - **Inconsistency:** the fax analogue (`ManageFaxes2Action.SetCompleted`, `:362`) keeps the job's `statusString`.
- Evidence:
  - The action calls `emailManager.updateEmailStatus(loggedInInfo, id, EmailStatus.RESOLVED, null)`.
  - The DAO runs `UPDATE EmailLog e SET e.status = :status, e.errorMessage = :msg WHERE e.id = :id AND e.status = :failed`.
  - `EmailLogDaoIntegrationTest` asserts `stored.getErrorMessage()).isNull()` after a resolve.
- Impact: after Resolve, nobody can tell why a patient email failed (for example a rejected address), or who closed it. The diagnostic and audit loss is small but permanent.
- Correction: keep `errorMessage` on RESOLVED (do not bind null). Add an audit entry, for example `LogAction.addLog(loggedInInfo, "ManageEmails2Action.setResolved", "Email", "emailLogId=" + id, …)`, or resolvedBy/resolvedAt columns.

### S19-3: CARLOS exports eForms that its own ZIP importer now refuses (form HTML over 16 MiB)
- Severity: Low
- Category: breaking-change
- Confidence: Confirmed. The asymmetry is traced in code; templates this large are uncommon.
- Commit: 90c1e797 (#5500)
- Location:
  - Import: `src/main/java/io/github/carlos_emr/carlos/eform/EFormExportZip.java:72, 313, 453-457`
  - Export, which writes the HTML without a limit: `EFormExportZip.java:186-193`
  - `src/main/java/io/github/carlos_emr/carlos/eform/upload/HtmlUpload2Action.java:81-83`
  - `database/mysql/migration/common/V1.0.59.27__preserve_oscar19_text_capacity.sql:193-194`
  - `src/main/webapp/WEB-INF/classes/struts.xml:67`
- Problem:
  - **What CARLOS accepts and stores:** `eform.form_html` is LONGTEXT (widened to keep OSCAR 19 capacity). `HtmlUpload2Action` reads and saves any uploaded HTML up to the 50 MB multipart cap. `exportForms` writes the HTML with no limit.
  - **What it imports:** the new importer rejects any retained HTML entry over 16 MiB with "ZIP import text byte limit exceeded".
  - **Result:** an eForm CARLOS accepts, stores and exports cannot be imported back. A typical case is self-contained HTML with embedded base64 page images, moved between clinics or restored after deletion. Through Manage eForms the failure is the generic error page (#5757).
- Evidence:
  - Import: `if (entryBytes > MAX_IMPORT_TEXT_ENTRY_BYTES || …) throw new IOException("ZIP import text byte limit exceeded");`
  - Export: `byte[] bytes = html.getBytes("UTF-8"); … outputToInput(zos, is);`, with no cap.
  - `docs/eform-zip-import-limits.md` says large packages "must import successfully".
- Impact: rare. An admin who exports a large template gets an unexplained failure when importing it again.
- Correction: do one of the following, and document the limit in `eform-zip-import-limits.md`.
  - Raise the HTML budget to at least what upload and the editor can store (the 50 MB multipart cap). That is still well below the 256 MiB stream ceiling.
  - Enforce the same 16 MiB ceiling, with a clear message, at upload, editor save and export.

## Checked and found OK
- **Fax backoff state:**
  - The delay is `min(60, 2^(n-1))` minutes; the counter saturates; accounts are never disabled.
  - Success clears the state (`recovered`), and removed or disabled accounts are pruned on every poll.
  - Every `FaxPollBackoff` method is synchronized, and `snapshot()` returns an immutable copy. Admin page rendering never waits on a network poll.
- **Fax poll loop:**
  - Only setup and listing failures back off; a per-document `RuntimeException` doesn't, and pending local imports still run during backoff.
  - The SRFax unread-pull and mark-read policy is unchanged; faxes stay unread at SRFax during backoff.
  - `ensureSuccess` makes bad credentials throw, so they do trigger the backoff.
- **Fax logs and UI:** the WARN lines carry the account id, provider type, HTTP status and exception class, never provider text or PHI. The UI says "at or after", which is accurate: the effective retry is the first scheduler tick after `nextRetry`, about one tick later than the doc's 1, 2, 4 … minutes.
- **Email error page:** no PHI in the log (class, reference, `LogSafe.exceptionTrace`) or on the page (fixed bundle text + reference). The output is encoded with `carlos:forHtmlContent`. A `SecurityException` restores the draft and goes to the 403 page. Retry reuses the same draft key.
- **Email resolve:** idempotent (an already-RESOLVED row answers 200). The FAILED-only conditional update keeps the transport outcome authoritative. `findFresh` bypasses a stale persistence context. `StringUtils.isInteger` rejects out-of-range ids, so a bad id gets 400, not 500. The CSRF token travels on the jQuery POST.
- **ZIP import containment:** `validateZipEntryPath` runs for every entry, including skipped ones, before any read. Staging and publication use `validateGeneratedChildPath`/`validateExistingPath`.
- **ZIP import budgets:** the byte budget wraps `read(byte[], int, int)`, which `closeEntry`, `skip` and single-byte `read` all funnel through. Exact limits are accepted. Entry count includes directories and metadata. There is no ratio limit, by design. Nested archives are never expanded.
- **ZIP import cleanup:** the stream is closed by try-with-resources, the staging directory is deleted in `finally`, and the properties temp file is deleted in `finally`. Publication happens only after all budget checks.
- **ZIP export:** the name-normalization rewrite is output-equivalent, and the bulk copy is equivalent with the stream left open.
- **RTL fix scope:** genuinely unknown keys still reach the server and raise the "could not be filled in automatically" banner. A missing value falls back to the DOM field or a user prompt, not a silent blank. A failed composite handler sets the "Template fields could not be loaded" status. The log-audit allowlist matches only the exact synthetic `renderer_missing_ap_<13 digits>` key.
- **Template editor:** the only caller is the editor's multipart POST form, and its admin-shell AJAX path keeps the form's method. GET and HEAD are refused by the filter (`Allow: POST`) and by the action before binding is used or the privilege is checked. A tokenless POST is refused by CSRFGuard (403, Playwright-covered).
- **Tests:** they exercise real behaviour, not just mocks: `FaxImporterPollTest`/`FaxPollBackoffUnitTest`, `EmailLogDaoIntegrationTest` (real SQL), `EFormExportZipLimitsUnitTest`/`ImportZipInputStreamUnitTest` (boundaries, cleanup, ownership), `rtl-template-autofill.test.js` (real `APCache.js` and `editControl2.js` code) and `HtmlEdit2ActionUnitTest`. The #5613 commit is test- and doc-only.

## Declined to judge
- **Struts multipart `maxStringLength`:** its default might affect large editor saves. Not configured in CARLOS, and I could not check the Struts 7 default without the jar. Pre-existing and not changed by #5651.
- **SRFax empty-inbox status:** if `Get_Fax_Inbox` ever answered "Failed" for an empty inbox, idle accounts would back off. There is no evidence of this; production would already have shown per-minute ERRORs on main.
- **HTTP 200 for the email preparation error page:** looks deliberate. A 5xx would be rewritten by `ResponseSanitizationFilter` and lose the recovery page. The draft-expired page uses 410.
