### S21-1: Audit rows that stored entity `toString()` silently lost their content, and some now identify nothing
- Severity: Low
- Category: regression
- Confidence: Confirmed
- Commit: d9f0a955 (#5512)
- Location (release; caller lines on main in brackets):
  - `src/main/java/io/github/carlos_emr/carlos/commn/model/AbstractModel.java:42-49`
  - `managers/DemographicManagerImpl.java:530-531, 605-606, 668-669` (main 509, 585, 648)
  - `managers/PatientConsentManagerImpl.java:267` (persist is at :269; main 267)
  - `webserv/rest/DiseaseRegistryService.java:151` (main 151)
  - `managers/ScheduleManagerImpl.java:221` (main 217)
  - `integration/fhir/manager/OscarFhirResourceManager.java:182,232,251`
  - `managers/RxManagerImpl.java:158`
  - `prescript/pageUtil/RxDeleteRx2Action.java:404,443`
- Problem:
  - These calls write `entity.toString()` (or `"" + entity`) into the persisted audit table (`log.data`, shown by
    Administration log report `admin/web/LogReport2Action.java:210`). Before the commit, that text was the
    reflective field dump. Now the base `toString()` stores only `Type[id=N]`.
  - Where the call runs before persistence, the stored row now has no identifying content at all:
    - `DemographicManager.addDemographic ext` (and `updateDemographic ext` for a newly added extension) is logged
      before `updateExtension()` saves the extension. Every such row now reads `id=null(DemographicExt[id=null])`:
      no id, no key name.
    - `PatientConsentManager.addConsentType` logs `ConsentType[id=null]` two lines before `persist`.
  - Other rows lost detail:
    - `Dxresearch.add` loses the coding system and code.
    - `AppointmentManager.addAppointment` (no demographic/content columns) loses the patient, provider and time.
    - The commit also hard-codes "Retrieved prescription" and "Prescription discontinued" for two Rx rows. Those
      keep their contentId and demographic columns, so they are acceptable.
  - Issue #5486's "Behaviour" note says: "confirm that no code uses these toString() results functionally (... or
    in persisted strings). If any does, give that call site an explicit method." The audit document
    (`docs/security-object-diagnostics.md:48-53`) lists only the CheckBoxBean, prescription and FHIR audit
    callers, and says nothing was "persisted as functional application data". The release notes say nothing.
- Evidence:
  ```java
  // DemographicManagerImpl.java:603-607 (addDemographic) – ext.getId() is still null here
  for (DemographicExt ext : demographic.getExtras()) {
      LogAction.addLogSynchronous(loggedInInfo, "DemographicManager.addDemographic ext",
              "id=" + ext.getId() + "(" + ext.toString() + ")");   // now "id=null(DemographicExt[id=null])"
      updateExtension(loggedInInfo, ext);                          // persists afterwards
  // PatientConsentManagerImpl.java:267-269
  LogAction.addLog(..., "PatientConsentManager.addConsentType", consentType.getType(), consentType.toString()); // "ConsentType[id=null]"
  consentTypeDao.persist(consentType);
  ```
- Impact: Privacy officers and admins reviewing the audit trail can no longer see which demographic extension
  field was added, changed or deleted, which consent type was created, or which diagnosis code was registered.
  The `addDemographic ext` rows are now pure noise. Nobody notices until an investigation needs them. Dropping
  the PHI values is consistent with policy, but the non-PHI identifiers (extension key, entity id) were dropped
  too.
- Correction:
  - Give each call site explicit, non-PHI audit text. Log the extension rows after the save, with the id and
    `LogSafe.sanitize(ext.getKey())`.
  - Move the `addConsentType` audit after `persist` and record the id.
  - For `Dxresearch.add` record the coding system and id. For `addAppointment` record `demographicNo`,
    `providerNo` and the id, or use the `addLog` overload that fills the demographic column.
  - Note the audit-text change in the release notes and in the audit document.

### S21-2: The "blocking scan of src/main" skips 64 application Java files and all JSP tag files
- Severity: Low
- Category: test-gap
- Confidence: Confirmed
- Commit: d9f0a955 (#5512)
- Location:
  - `.github/workflows/semgrep.yml:106-112`
  - `.semgrep/reflective-diagnostics-carlos.yml:11`
  - `.semgrepignore:12`
  - `docs/security-object-diagnostics.md:98-102`
- Problem:
  - `semgrep scan --error --max-target-bytes 0 --config .semgrep/reflective-diagnostics-carlos.yml src/main` walks
    a directory target, so it honours the repository `.semgrepignore`. That file excludes
    `src/main/java/io/github/carlos_emr/carlos/ar2005/`: 64 Java files compiled into the WAR and still edited
    (97ffd9c3, c739112a, 7b751dda).
  - The rule's `paths.include` is `['**/*.java','**/*.jsp','**/*.jspf']`, so JSP tag files are never checked.
    `WEB-INF/tags/cdsSourceFields.tag` contains scriptlets.
  - The doc states the step "scans `src/main`". Neither location contains a reflective call today (I grepped the
    whole tree), so this is a forward-looking hole, not a live leak.
  - The gate is also purely lexical over reflective APIs. Equivalent all-field dumps (hand-written or
    IDE-generated `toString()`, Java records) are invisible to it; see S21-P3.
- Evidence: `.semgrepignore:12: src/main/java/io/github/carlos_emr/carlos/ar2005/`;
  rule line 11: `include: ['**/*.java', '**/*.jsp', '**/*.jspf']`.
- Impact: A reflective `toString()` added in `ar2005` or in a `.tag` file passes CI, although the doc promises
  it is blocked.
- Correction:
  - Run the lexical ban with `git grep -nE '<regex>' -- 'src/main/**'` (it ignores `.semgrepignore`), or exempt
    this rule from the ignore file.
  - Add `**/*.tag`, `**/*.tagx` and `**/*.jspx` to `paths.include`.
  - Align the doc text with what is actually scanned.

### S21-P4: `AbstractModel.equals` throws instead of returning false
- Severity: Low
- Category: bug
- Confidence: Confirmed (code). No production caller found that triggers it.
- Commit: n/a
- Location: `src/main/java/io/github/carlos_emr/carlos/commn/model/AbstractModel.java:61-72` (main :62-73).
  This is the file #5512 edited.
- Problem:
  - `equals(null)` throws NPE (`o.getClass()`).
  - An unsaved receiver compared with a same-class object logs a WARN with a stack trace, then throws NPE on
    `getId().equals(...)`.
  - So `Objects.equals(entity, null)`, and `List.contains`/`indexOf`/`remove` with an unsaved entity, throw.
  - #5512 rewrote `BaseObject`'s equality, but not this one (349+ entities).
- Evidence: `if (getClass() != o.getClass()) return (false); ... return (getId().equals(abstractModel.getId()));`
- Impact: Latent crash risk. I checked the obvious callers (`ConfigureFax2Action`, `BillingCorrectionService` —
  BillingONItem overrides `equals` — and `ConsultationAttach`) and none passes null or an unsaved receiver.
- Correction: Make `equals` null-safe and reflexive (`this == o` first; null → false; unsaved → reference
  identity), consistent with `BaseObject`.
- Pre-existing: yes (present on origin/main)
