### S22-1: #5595 leaves two other `_dxresearch` routes (quick-list items, code search) answering HTTP 500 for a missing grant
- Severity: Low
- Category: omission
- Confidence: Confirmed
- Commit: 13547aee (#5595)
- Location: `src/main/java/io/github/carlos_emr/carlos/dxresearch/pageUtil/dxResearchLoadQuickListItems2Action.java:60`, `src/main/java/io/github/carlos_emr/carlos/dxresearch/pageUtil/dxResearchCodeSearch2Action.java:79` (same lines on main); `src/main/webapp/WEB-INF/classes/struts-clinical.xml:36-39`
- Problem: #5595 changed only `dxResearchLoadQuickList2Action` from `RuntimeException` to `SecurityException`. In the same package, the quick-list items route (posted from `dxResearchSelectQuickList.jsp:80` and `dxResearchNewQuickList.jsp:74`) and the code-search popup (`dxResearch.jsp:161`) still throw `new RuntimeException("missing required sec object (_dxresearch)")`. The `clinical` package maps that to `error`, which is HTTP 500 plus an ERROR log with stack trace. The commit's own claim, "return 403 when quick-list read access is denied", is therefore met for one of the two quick-list read routes.

Neither route is in the `authz-read-role-matrix` pins, so the "no 500" assertion does not see them.
- Impact: a login without `_dxresearch` that reaches these routes (bookmark, stale popup, direct request) gets the generic "unexpected error" page and the server logs a stack trace. Data stays protected.

### S22-2: Negative `limit`/`offset` on `GET /demographics` and `/pharmacies/` changed from 200 to 400; only JavaDoc says so
- Severity: Low
- Category: breaking-change
- Confidence: Confirmed
- Commit: bac72ac0 (#5596)
- Location: `src/main/java/io/github/carlos_emr/carlos/webserv/rest/DemographicService.java:256-259`, `src/main/java/io/github/carlos_emr/carlos/webserv/rest/PharmacyService.java:100-104`; `docs/release-notes-2026.08.md` (no entry)
- Problem: on main, `/demographics` treated `limit<=0` as the default 500-row page (`DemographicDaoImpl.getActiveDemographics`: `if (aLimit <= 0) aLimit = MAX_SELECT_SIZE;`). Both endpoints ignored a negative `offset` (`if (offset > 0) setFirstResult`). All three now answer 400, on the session (`/ws/rs`) and OAuth (`/ws/services`) surfaces. Oversized limits (500 → 400) and a negative pharmacy `limit` (Hibernate `IllegalArgumentException` → 500) are genuine fixes. The rest is a new refusal of values clients could legitimately have been sending, for example `limit=-1` meaning "everything", which used to return the first 500 patients. #5746 lists only "400 for a negative offset" as a missing release note; the negative `limit` on `/demographics` is not listed anywhere.
- Evidence: main `DemographicDaoImpl` lines 246-249 (default for `<=0`); release `if ((offset != null && offset < 0) || (limit != null && (limit < 0 || limit > DemographicDao.MAX_SEARCH_RESULT_SIZE))) throw new BadRequestException(...)`. The tests pin `"0,-1"` and `"-1,10"` → 400.
- Impact: an integration paging with `limit=-1` or `offset=-1` now fails with an empty-body 400 instead of receiving patients or pharmacies. There are no in-tree page consumers; the integrations affected are external.
- Correction: add the change (negative offset on both lists, negative limit on `/demographics`, oversized limits now 400) to the release notes or integrator notice, and extend #5746 accordingly.

### S22-3: Dashboard Assign Tickler now refuses and erases 24-hour and lower-case times that the server accepts and the old picker read correctly
- Severity: Low
- Category: regression
- Confidence: Confirmed
- Commit: 383db897 (#5610)
- Location: `src/main/webapp/web/dashboard/display/drilldownDisplayController.js:62-80` (`parseTicklerValue`), `:114-118` (`rejectInvalidText` clears the field), `:54-57` (message); server `src/main/java/io/github/carlos_emr/carlos/dashboard/admin/TicklerRequest.java:78,90`
- Problem: the client accepts only `/^(0?[1-9]|1[0-2]):([0-5]\d) (AM|PM)$/` and sets `input.value = ''` on blur, Enter or any outside press for anything else. The server is unchanged: it accepts `hh:mm a` (case-insensitive AM/PM) or `HH:mm`, and its own error text says "Use hh:mm AM/PM or 24-hour HH:mm (for example 10:30 AM or 14:30)". The client message says only "Use hh:mm AM/PM". The old flatpickr parser misread some inputs, and those really were reinterpretations that the fix rightly rejects ("2030-02-30" → 2030-03-02, "13:75 PM" → 14:15, "2:30 Pm" → 02:30). But it read "14:30", "2:30 pm" and "10:30 am" correctly.
- Evidence: node run of the release parser gives `"14:30" REJECTED`, `"10:30 am" REJECTED`, `"10:30AM" REJECTED`. The old parser (runtime `tokenRegex.K="(AM|PM|am|pm)"`) gives `"14:30" -> 14:30`, `"2:30 pm" -> 14:30`, `"10:30 am" -> 10:30`. Java with the server patterns gives `14:30 -> 14:30`, `2:30 pm -> 14:30`, `10:30 am -> 10:30`. `scripts/dashboard-tickler-pickers.test.js` pins the rejections of `14:30` and `10:30 am` deliberately.
- Impact: a clinician typing a time as they always did sees it erased and must retype it in 12-hour upper-case form. Picker clicks are unaffected, and no wrong time is stored. The new validation text is also hard-coded English in JS, not in the bundles.
- Correction: accept `HH:mm` and case-insensitive AM/PM in `parseTicklerValue`, normalizing to `h:i K` on commit (still rejecting impossible values), or make the client and server guidance agree. Prefer keeping the typed text with the error rather than clearing it.

### S22-P1: `GET /ws/rs/demographics` (and `/ws/services/demographics`) returns full master records of patients the caller is locked out of
- Severity: Medium
- Category: security
- Confidence: Confirmed
- Commit: n/a (code touched by bac72ac0 #5596)
- Pre-existing: yes (present on origin/main)
- Location: release `src/main/java/io/github/carlos_emr/carlos/webserv/rest/DemographicService.java:214-224,254-277` (main `:215-224,252-272`); release `src/main/java/io/github/carlos_emr/carlos/managers/DemographicManagerImpl.java:761-774` (main `:722-735`); `src/main/java/io/github/carlos_emr/carlos/webserv/rest/conversion/DemographicConverter.java:141-205`
- Problem: the single-record endpoints use the record-level check `requireDemographicPrivilege(action, demographicNo)`, which evaluates the patient-specific `_demographic$<n>` lock. The list uses only the object-level overload: its comment reads "Object-level privilege check — no patient-specific restriction". `DemographicManagerImpl.getActiveDemographics` also checks only the object-level `_demographic` read. Every active patient is then converted with `DemographicConverter.getAsTransferObject`: HIN/version, SIN, email, phones, address, DOB, chart no., names and roster data. `SecurityInfoManager.hasDemographicReadPrivileges(..., Collection)` exists for exactly this batch case and is not used.
- Evidence: `getAllDemographics` → `requireDemographicPrivilege("r")` → `hasPrivilege(loggedInInfo, "_demographic", action, null)`. Compare `getDemographicData` → `requireDemographicPrivilege("r", id)`. The converter sets `t.setHin(...)`, `t.setSin(...)`, `t.setEmail(...)` and so on, with no per-patient filtering.
- Impact: any signed-in user with general `_demographic` read who has been explicitly locked out of a patient can page `/ws/rs/demographics?offset=…&limit=500` and read that patient's full demographic record. The Master Record page refuses the same read. This belongs to the #4223 patient-lock bypass family but is not listed there; #4223 lists only the UI patient search.
- Correction: filter or redact each row with the record-level read check (`hasDemographicReadPrivileges` or a per-row `hasPrivilege(..., "r", demographicNo)`). Decide whether `total` counts restricted rows, and add a locked-patient case to the REST endpoint tests.

### S22-P2: Tickler Edit month and year quick picks overflow month ends (Jan 31 + "1m" → Mar 3)
- Severity: Low
- Category: bug
- Confidence: Confirmed
- Commit: n/a (`addQuickPick` touched by dee8195d #5699)
- Pre-existing: yes (present on origin/main)
- Location: release `src/main/webapp/WEB-INF/jsp/tickler/ticklerEdit.jsp:343-354` (`addTime`; main `:339-350`); the same pattern is in `src/main/webapp/WEB-INF/jsp/tickler/ticklerAdd.jsp:336-340`
- Problem: `currentDate.setMonth(currentDate.getMonth() + num)` lets JavaScript roll an invalid day into the next month. The "Nm" and "Ny" quick picks (`num*12` months) therefore land days late at month ends and on Feb 29.
- Evidence: node, America/Toronto: 2027-01-31 +1m → 2027-03-03; 2028-01-31 +1m → 2028-03-02; 2026-08-31 +1m → 2026-10-01; 2026-10-31 +4m → 2027-03-03; 2028-02-29 +12m → 2029-03-01.
- Impact: a follow-up tickler set "1 month" from Jan 31 is due Mar 3, not Feb 28. The date is visible in the box before saving, so a careful user can correct it, but quick picks exist to avoid checking.
- Correction: clamp to the last day of the target month (for example, compute the target month, then `Math.min(day, daysInMonth)`) in both `ticklerEdit.jsp` and `ticklerAdd.jsp`.

### S22-P3: Send and Archive archives the original message before the reply is sent, so a refused reply leaves it archived with no reply
- Severity: Low
- Category: silent-failure
- Confidence: Confirmed
- Commit: n/a (flow "verified" by 7b65c40e #5522)
- Pre-existing: yes (present on origin/main)
- Location: `src/main/webapp/WEB-INF/jsp/messenger/CreateMessage.jsp:378-412` (same on main); `src/main/java/io/github/carlos_emr/carlos/messenger/pageUtil/MsgCreateMessage2Action.java:177,186,195,213,226` (refusal paths)
- Problem: `XMLHttpRequestSendnArch()` first POSTs `btnDelete=archive` to `messenger/DisplayMessages` and only then submits the reply form. When the server then refuses the reply, `redisplay` keeps the draft but does not undo the archive. Refusal reasons: attachments released, PDFs prepared for another patient, PDFs too large, no valid recipients after deduplication, send failure. `archiveMessageId` is carried only for redisplay; nothing archives server-side after a successful send.
- Evidence: `oRequest.onload = ... document.forms[0].submit();` follows `oRequest.send('btnDelete=archive&messageNo=' + ...)`. The `redisplay(...)` paths contain no archive restoration. The new browser check covers only a refused plain Send followed by a successful Send and Archive.
- Impact: the user sees the refusal for the reply but not that the message being answered has already left the inbox. If they close the window, the message sits in the archive unanswered, which matters for clinical messages.
- Correction: archive server-side in `MsgCreateMessage2Action` after `sendMessage2` succeeds, using the already-authorized `archiveMessageId`. Alternatively, run the archive XHR only after a successful send response.

## Checked and found OK
- **#5624 root cause and guard.** `RestJaxbContextUnitTest.shouldBuildOneContext_forEveryRegisteredSessionService` reads every `jaxrServer` service bean from the shipped `spring_ws.xml`. It builds the production `jaxb` bean (`singleJaxbContext=true`, `extraClass`) under MOXy and Glassfish and asserts one shared context (CXF falls back to per-class contexts silently). Any newly added un-JAXB-able type in a statically declared request/response type fails the build. Not covered: `Response`-typed entities and the OAuth-only `OAuthStatusService`; I found no XML-producing `Response` methods that carry entities.
- **Content negotiation.** CXF 4.1.9 fixes the response type at operation selection (`intersectSortMediaTypes(...).get(0)`). XML-first resources therefore answer XML for `*/*`/no `Accept`, as before #5347. JSON-first resources still answer JSON, and the Jackson provider still uses the JAXB-aware `jacksonObjectMapper`.
- **Error responses.** REST exception mappers return `text/plain` or empty bodies (403/409), the same for XML and JSON callers. `ResponseSanitizationFilter` leaves 4xx bodies alone unless a stack trace is present.
- **Runtimes on the class path.** Glassfish `jaxb-runtime` is the packaged runtime, MOXy is test scope only, and the Jackson JAX-RS and JAXB modules are present.
- **ProviderTransfer XML exposure.** XML exposes the same fields as JSON; `/providers` and `/provider/{id}` both apply `visible()`.
- **#5596.** Null and zero behaviour is unchanged on both endpoints, the boundary values are tested, and the JavaDoc matches the DAO behaviour.
- **#5539.** The rollback still happens on `attachmentsRefused`, the parent form keeps fields and selection, the message is a translated bundle key in all five locales, the refusal page is encoded, and an iframe still fires `onload` on a 400.
- **#5610.** Leap years, impossible dates, year 0, "today", ISO-Z strings and junk are rejected. Dates validate correctly in a midnight-DST zone (America/Santiago). The server still refuses spring-forward gaps with a clear message. The document `pointerdown` listeners are removed on destroy (flatpickr 4.6.13 fires `onDestroy` first), and pickers are destroyed before the modal is reused or fails.
- **#5514.** Old and new display rules are equivalent for every combination of min/max/sex/threshold/hidden. Only a null patient became quiet; malformed configuration still logs ERROR (tested).
- **#5522.** `submissionerror` is defined in scope, and redisplay always restores the draft (fields encoded). The Send and Archive XHR goes through CSRFGuard's hijacked XHR.
- **#5523.** No JS runs without a trigger element. Native buttons/links get no duplicate key handler. `tabindex="-1"` and inline `display:none` opt-outs are kept. The `chooseDate` key exists in all bundles.
- **#5699.** The billing reader matches the old 3×20 loop and the order-failure semantics. The overscroll rule moved everywhere #3966 listed (`appointmentstyle.css` was already `:root`-scoped). Both Rx paste paths are trimmed.
- **GET/HEAD and CSRF.** No new mutator routes. `EditTickler2Action` and the billing actions remain POST-only, and no new forms were added.

## Out of scope but notable
- **Other paged REST endpoints.** These still pass raw paging values to DAOs without the #5596 validation (Plausible 500s for negative or oversized values): `TicklerWebService.getMyTicklers`/`search`, `MessagingService.getMyUnreadMessages`, `LabService.getHl7LabsByDemographicNo` and `InboxService`.
- **Zero limit.** `limit=0` means an empty page on `/pharmacies/` but the default 500-row page on `/demographics`. The old pharmacy JavaDoc promised "the entire result set"; the release documents the empty page rather than unifying the two.
- **Orphan flowsheet customizations.** `FlowSheetCustom2Action.save()` can persist a customization for a flowsheet name that has no template (when `count` is absent or 0) before the editor now answers 404.
