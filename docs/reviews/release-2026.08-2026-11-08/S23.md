## Findings
### S23-1: The JDK-equivalents audit still lists DownloadInInterceptor as a migrated stream-copy site
- Severity: Low
- Category: docs
- Confidence: Confirmed
- Commit: fe88bc1e (#5497)
- Location: `docs/jdk-equivalents-audit.md:12`; `src/main/java/io/github/carlos_emr/carlos/integration/ebs/client/ng/DownloadInInterceptor.java:11-49`
- Problem:
  - The audit table lists DownloadInInterceptor among the "Byte-stream copy with discarded return count" sites. It says the site was migrated from `IOUtils.copy` to `transferTo` and is covered by `JdkStreamCompatibilityUnitTest`.
  - Release commit 4b302882 (#5710, "preserve XML contracts and stream ownership") later rewrote the interceptor. It no longer reads, copies or replaces the SOAP message stream; it logs only a fixed event and the HTTP status.
  - The row therefore describes code that no longer exists.
- Evidence:
  - Doc line 12: `| Byte-stream copy with discarded return count | DocumentUpload2Action, ..., IHAPOIHandler, DownloadInInterceptor | ...`.
  - `git show 4b302882 -- .../DownloadInInterceptor.java` deletes `is.transferTo(cos);`.
  - The new Javadoc reads: "It never reads, copies or replaces a message stream, nor enumerates attachments".
- Impact: No runtime effect. A maintainer auditing EBS/MCEDT stream ownership (the defect #5710 fixed) would be told the interceptor still copies, and so consumes, the response stream.
- Correction: Remove DownloadInInterceptor from that row, or note that #5710 removed the copy.

No other finding. I checked every replaced call in both commits, and each one behaves the same as before for every input it can receive. The details are in the next two sections.

## Checked and found OK
- **Base64:** all 15 replaced encoders were the commons non-chunked, standard-alphabet, padded overloads.
  - No `encodeBase64(…, true)`, URL-safe or chunked overload was touched.
  - Null-input behaviour matches at every reachable site: NPE in both, or guarded (ClientImage).
  - No decoder was migrated. The lenient commons `decodeBase64` is kept at every site that reads the new encodings (SearchConfig, ClientImage, EmailLog, LabDisplayHelper, MsgCommxml, UtilMisc, Doc2PDF), so stored values with line breaks or URL-safe characters still decode.
  - No commons encoder or `DigestUtils` call remains in `src/main`.
- **Hex and digests:** `HexFormat.of()` produces lowercase hex, the same as codec. String overloads hash UTF-8 bytes. The stream overloads do not close the stream and propagate IOException. `NoSuchAlgorithmException` is wrapped in IllegalArgumentException, as in codec.
- **Untouched areas:** URLEncoder/URLDecoder, FileUtils, FilenameUtils, `closeQuietly`, MultiReadHttpServletRequest's bounded `copyLarge` and MEDITECHHandler's InputStream→Writer copy are not touched. I confirmed the audit doc is right about each.
- **No risky JDK string or collection calls:** the slice adds no `String.isBlank` or `strip` without a null guard, no `split` or `replaceAll`, and no `List.of`, `Set.of`, `Map.of` or `copyOf` in production code.
- **`Stream.toList()`:** used once, in the private `billingIdsCsv`. `String.join` consumes the result immediately, so its being unmodifiable cannot matter.
- **CARLOS "null"-text semantics:** `noNull`, `filled`, `empty` and `isNullOrEmpty` are unchanged. `isNumeric` still means `Double.valueOf` after `filled`; `isInteger`, `maxLenString`, `containsIgnoreCase`, `splitToStringArray` and `lineBreaks` are also unchanged. The new Javadoc is accurate, including when `splitToStringArray` throws NPE. Adding `filled`/`noNull` semantics to the remaining JSP callers changed nothing.
- **Leftovers:** no import of the CXF or Spring `StringUtils` remains in `src/main`. No `collections4` KeyValue, MultiValueMap, LinkedMap or OrderedMap remains outside MeasurementFlowSheet's documented `ListOrderedMap`. No `MILLIS_PER_*` remains except in a comment.
- **Issue acceptance criteria:** #5484's are met (CXF import gone, unused helpers removed, null-element and "null"-text tests added, Javadoc added). #5483's "do not migrate" list is respected.
- **Test quality:** the new tests are not vacuous; each asserts against commons-codec, commons-io or collections4 directly. `Locale.setDefault` in StringUtilsUnitTest is safe because Surefire uses forked JVMs with no in-JVM parallel execution.

## Declined to judge
- **`DocumentUpload2Action:397`:** `Files.newInputStream(…).transferTo(Files.newOutputStream(…))` now takes the JDK's FileChannel→FileChannel transfer path (sendfile/copy_file_range) instead of a read/write loop. The bytes are the same by specification. I can't rule out a filesystem-specific JDK quirk, for example with an NFS-mounted document directory, but I found no evidence of one, so I am not reporting it.
- **Commit timing on streamed responses:** the default buffer is now 16 KiB instead of 8 KiB. This could only change when a Tomcat response is committed if a read fails mid-stream, and every touched site behaves the same after such a failure.
- **Tickler Playwright script changes:** these are test-harness only, and four later commits rewrote the script again.

## Out of scope but notable
- **`util.DateUtils` day differences miscount across DST changes.** `getDifDays`, `getNumberOfDaysBetweenTwoDates` and `calculateDayDifference` divide elapsed milliseconds by a fixed 86,400,000, so their callers' calendar-day counts are off by one whenever the span crosses a DST change. This is pre-existing and the slice faithfully preserved it.
  - Checked on JDK 21 in America/Toronto: `calculateDayDifference(2026-03-01, 2026-03-09)` = 7.
  - On 2026-11-01, `getDifDays(23:30, 00:00)` = 1, so a same-day check reports a different day.
  - Affected callers include `AdmissionForDisplay` days-in-program, `ReferralSummaryDisplay` days-in-queue, BC `ServiceCodeValidationLogic` same-day checks, `BillingONCHeader1DaoImpl` bill age and the `Cds4ReportUIBean` day counts.
  - The audit doc's justification for these sites ("elapsed durations, not calendar-day arithmetic", `docs/jdk-equivalents-audit.md:17`) is therefore not accurate for these helpers.
