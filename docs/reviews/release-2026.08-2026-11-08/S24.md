### S24-1: The cleanup edited six dynamically dispatched `.jspf` pages that CI never compiles
- Severity: Low
- Category: test-gap
- Confidence: Confirmed
- Commit: 80c022cd (#5681)
- Location: `pom.xml:2495` (`<exclude>**/*.jspf</exclude>` in the jspc profile); `src/main/webapp/WEB-INF/web.xml:683-684` (`*.jspf` mapped to the JSP servlet); dispatchers: `struts-provider.xml:56` (faxStatusResults.jspf), `EFormViewRoutes.java:74` (eform_floating_toolbar.jspf), `HealthTracker.jsp:53`, `TemplateFlowSheet.jsp:34`, `appointmentprovideradminday.jsp:2420,2433` (`<jsp:include page="….jspf">`)
- Problem: a `.jspf` reached by a Struts result, RequestDispatcher or `<jsp:include>` is its own translation unit, compiled only on first request in production. jspc excludes all `.jspf`, so "all 995 JSPs compile" (PR validation) and the checker docstring's backstop ("Jasper must still compile every page after any cleanup") do not cover these units. The commit removed 16 imports and 7 taglib declarations from six of them (HealthTrackerPage.jspf, TemplateFlowSheetPage.jspf incl. `javax.swing.Spring`/`Encode`/`demographic.data.*`, appointmentPregnancy.jspf ×6 (four `java.util` types, `ProviderPreference`, `AppointmentProviderAdminDayUIBean`), appointmentFormsLinks.jspf, faxStatusResults.jspf `c`/`e`, eform_floating_toolbar.jspf `c`).
- Evidence: I verified each by hand — none of the removed simple names, no class of `io.github.carlos_emr.carlos.demographic.data`, and no `<c:`/`<e:`/`<rewrite:` use occurs in those files (or `share/templates/patient.jspf`, the only static include inside them). So nothing is broken today; the gap is that a compile error or missing import here only shows up as an HTTP 500 at runtime.
- Impact: a later cleanup or edit of these pages can break the fax-status panel, eForm toolbar, flowsheets or the schedule's form links with CI green.
- Correction: compile the dynamically dispatched `.jspf` units in jspc (include them explicitly, or a small JspC run over the 8 dispatched fragments: the 6 above + `admin/emailStatusResults.jspf`, `includes/spinner.jspf`).

### S24-2: Neither jspc nor the new audit detects a tag prefix used without a declaration (the silent failure direction)
- Severity: Low
- Category: test-gap
- Confidence: Confirmed
- Commit: 80c022cd (#5681)
- Location: `scripts/check-jsp-directives.py:200-224` (`inspect` yields only unused/unresolvable findings); no `jsp-config` in `web.xml`
- Problem: the audit only proves directives are *not dead*. With Jasper's default `errorOnUndeclaredNamespace=false`, a `<prefix:tag>` whose taglib is missing is emitted as literal template text and still compiles, so a wrong taglib removal passes both jspc and the audit. Example: deleting `admin/securityupdate.jsp:35` (`security` taglib) leaves `<security:oscarSec … reverse="true">` (line 42) as text and its scriptlets run unconditionally (every user is redirected away); in the non-reverse form (e.g. `admin/admin.jsp:724-731` Messenger links) the guarded content is shown to everyone. EL `prefix:fn(` misses are caught by jspc; tags are not.
- Evidence: my scan of every compiled `.jsp` unit at head finds no undeclared prefix except 7 pre-existing PMmodule pages using Struts-1 `html:` (see "Out of scope"), so the check is cheap to add.
- Impact: the next directive sweep (e.g. #5477's remaining `e` declaration, TLD retirement in #5478) has no guard against the failure mode that is silent and can be an authorization bypass in the UI.
- Correction: add a "prefix used but not declared in its unit" rule to `check-jsp-directives.py` (same unit model), or set `<error-on-undeclared-namespace>true</error-on-undeclared-namespace>` in a `jsp-property-group` after fixing the 7 PMmodule pages.

### S24-P1: Reflected XSS: raw request parameters in EL in four touched, reachable JSPs
- Severity: High
- Category: security
- Confidence: Confirmed

- Commit: none (pages edited by 80c022cd)

  - `WEB-INF/jsp/form/formselect.jsp:53,54` `value="${param.savedAddSelection}"`, `value="${param.savedDeleteSelection}"`. Route `form/setupSelect` (FrmSetupSelect2Action always returns `continue`).
  - `WEB-INF/jsp/oscarMDS/Page.jsp:102,105` `onClick="submitForward('${ searchProviderNo }', '${ param.status }')"` (and `submitFile`). `searchProviderNo` is the raw request parameter (`DmsInboxManage2Action.java:316,646`); route `documentManager/inboxManage?method=prepareForContentPage`. The same page URI-encodes these values elsewhere (:334-383).
  - `WEB-INF/jsp/demographic/manageHealthCareTeam.jsp:392,453` `class="${ param.view }View"` (outside the `view eq 'detached'` blocks at :362-386). Route `demographic/ViewManageHealthCareTeam` (`_demographic` w), also `<jsp:include>`d by the demographic edit page.
- Problem: JSP EL does not escape. Each sink puts a raw query parameter into an HTML attribute or a JS string inside an attribute. There is no request-sanitizing filter (web.xml filter list), CSRFGuard does not cover GET, and HttpMethodGuardFilter treats these routes as reads. - Correction: use `${carlos:forHtmlAttribute(...)}` for the attribute sinks and `${carlos:forJavaScriptAttribute(...)}` for the onClick arguments (or validate `newNoteIdx` as an integer and `view` against `detached`). Two unreachable (unreferenced) pages carry the same pattern and can be fixed or deleted: `casemgmt/search.jsp:122`, `tickler/ticklerAddWidget.jsp:67`.

### S24-P2: Quebec HIN auto-fill drops accented letters because add.jsp is read as ISO-8859-1
- Severity: Low
- Category: data-integrity
- Confidence: Confirmed
- Pre-existing: yes (present on origin/main)
- Commit: none (page edited by 80c022cd)
- Location: `WEB-INF/jsp/demographic/add.jsp:463-476` (`removeAccents`), `:478-501` (`autoFillHin`, calls at :489-490); trigger `add-form-personal.jsp:837` (`onfocus="autoFillHin()"`); main = release lines
- Problem: add.jsp has no `pageEncoding`/`contentType` charset (only `<meta charset="UTF-8">` at :87), so Jasper decodes the UTF-8 regex literals `[àáâãäå]`, `[èéêë]`, `ç`, … as ISO-8859-1. The response is UTF-8 (ResponseDefaultsFilter), so the browser receives `[Ã ¡¢£¤¥]` etc. The accented letters are then deleted by the final `\W` replace instead of folded. The project already documents this Jasper default as seen live (`admin/updateDrugref.jsp:150-154`).
- Evidence: simulation of the served function: "Côté, Émile" → `CT` (intended `COTE`); "Bélanger, Josée" → `BLJ` (`BELJ`); "Tremblay, Ève" → `TRE` (`TREE`). `js/check_hin.js:54` skips validation for non-ON provinces, so the wrong RAMQ prefix is saved without warning.
- Impact: new QC patients with an accented surname or first initial get a malformed auto-filled health number unless staff notice.
- Correction: add `<%@ page pageEncoding="UTF-8" %>` (preferred for all CARLOS JSPs), or write the regexes with `\u00e0`-style escapes / `normalize('NFD').replace(/[\u0300-\u036f]/g,'')`.

### S24-P5: Key-pair creation runs on GET, and it writes to `getOutputStream()` then keeps rendering the page
- Severity: Low
- Category: security
- Confidence: Confirmed (code-traced; the server-log symptom was not reproduced)
- Pre-existing: yes (present on origin/main)
- Commit: none (page edited by 80c022cd)
- Location: `WEB-INF/jsp/admin/keygen/createKey.jsp:71-123` (main = release); gate `admin/gate/ViewKeygenCreateKey2Action.java` (no method check); `HttpMethodGuardFilter.java:92-99,174-187` (route not treated as a write); `Owasp.CsrfGuard.properties:97` (`ProtectedMethods=POST,PUT,DELETE,PATCH`)
- Problem: (a) any request with `name` creates and persists a key pair (`KeyPairGen.java:84,98`), including a cross-site GET to `admin/ViewKeygenCreateKey?name=…`, which neither CSRFGuard nor the method guard covers. (b) On success the page streams the key through `response.getOutputStream()` (:108) and closes it, then continues writing the HTML into the JspWriter. At page release Jasper flushes it via `response.getWriter()`, which throws `IllegalStateException` (getOutputStream already called).
- Impact: forged key pairs can be created for arbitrary service names (and "already created" then blocks the real one). Each successful creation also ends in a server-side exception. The success path is untested (#5707).
- Correction: move creation into a POST-only action that returns `NONE` after the download (CLAUDE.md direct-response rule), or reject GET when `name` is present and `return` right after the stream is written.

### S24-P6: Clinical Reports "CSV" export starts with ten blank lines and an unquoted filename
- Severity: Low

- Confidence: Confirmed
- Pre-existing: yes (present on origin/main)
- Commit: none (page edited by 80c022cd)
