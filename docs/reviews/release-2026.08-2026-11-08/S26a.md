- Category: silent-failure
- Confidence: Confirmed

  - `scripts/ci/lifecycle_baselines.py:6,25-29` (`REQUIRED_TAGS = {'2026.08.0-beta6','2026.08.0-beta5'}`)
  - `scripts/ci/package_lifecycle.py:96` (the package set must be exactly beta6/beta5 plus target)
  - `docs/testing/release-2026.08-lifecycle-baselines.json:3-4`
  - `scripts/coverage/release-coverage-floors.json:3` (`base`)
  - `scripts/ci/run-package-lifecycle-cell.py:158-180` (CLI floor `1.3.1`)
  - `scripts/ci/release-scope-audit.py:71-104`
  - `docs/testing/release-2026.08-verification.md:22`
- Problem:
  - Every main-relative gate is pinned to beta6/beta5 by constants: the main-only-migration inventory, the published-migration byte-identity check, the main and historical package-upgrade lifecycle cells, the wire-compatibility baseline and the coverage floors base.
  - Nothing compares `currentMain` with `origin/main` or the newest published 2026.08 tag.
  - Tag `2026.08.0-beta7` (d40d2939, = origin/main) was published at 2026-11-08T04:15Z. That is before #5800 merged (20:39Z).
  - beta7 ships `database/mysql/migration/common/V1.0.59.33__audit_imported_billing_filenames.sql` and `Depends: carlos-ctl (>= 1.3.2)`. release/2026.08 has neither.
- Evidence:
  - The scope audit at the release head returns `mainOnlyMigrations: []`, `unresolvedMainOnlyMigrations: 0`.
  - `compare_shared(root, e53e6cb5, HEAD, minimum=82)` returns `ready: True`.
  - The same call with the real published main (`d40d2939`, minimum=83) raises `Shared migration inventory is smaller than its reviewed baseline`.
  - So the "Release Verification Tooling" job is green only because its baseline is stale.
- Impact:
  - A beta7 install has V1.0.59.33 applied. A build from release/2026.08 without the beta7 back-merge rejects it: `FlywaySchemaValidator.java:213` and `FlywayRunner.java:178` use `ignoreMigrationPatterns(new String[0])`, so an applied migration the build does not ship is a hard validate failure. postinst db-migrate or boot fails on upgrade.
  - The qualification tooling built to catch this reports zero main-only migrations and certifies upgrades from beta6/beta5 packages with CLI 1.3.1.
  - The second guard is also blind (S26a-P1).
- Correction:
  - Back-merge beta7 into release/2026.08 (docs/release-process.md).
  - Re-pin `currentMain`, the lifecycle manifest and `REQUIRED_TAGS`, `validate_config`'s package set, the floors base and the CLI floor to beta7.
  - Add a freshness guard: fail `release-scope-audit.py`, and therefore the CI job (fetch tags), when origin/main or any published 2026.08 tag is not covered by the baselines.

### S26a-2: The plan's `packaged-full` lane can never pass, because `error-sanitization` now skips without a fault token, and unwrapped runs silently lose its refusal probes
- Severity: Medium
- Category: bug
- Confidence: Confirmed
- Commit: 9004536d (#5800)
- Location:
  - `scripts/error-sanitization-playwright-checks.js:105-109`
  - `docs/testing/release-2026.08-verification.json:3138-3150` (`packaged-full` command: no wrapper, no environment)
  - `scripts/ci/run-installed-error-sanitization.py:136-139`
  - `scripts/ci/release_verification.py:506,640`
  - `scripts/run-playwright-suite.js:564-565`
- Problem:
  - The check now throws `SkipCheck` unless `ERROR_SANITIZATION_FAULT_TOKEN` is set. Only `run-installed-error-sanitization.py` sets it.
  - That wrapper accepts only `node scripts/error-sanitization-playwright-checks.js` or `node scripts/run-playwright-suite.js` as its command, and it writes no receipt.
  - `verify-release-evidence.py run --check packaged-full` executes the plan command verbatim, and `verify()` requires the receipt command to equal it. So it cannot be wrapped, and `error-sanitization` is SKIP there. Under `--strict-release` a SKIP is FAIL.
- Evidence:
  - `packaged-full` has no `selection`. Applying `browser_results`' selection logic gives ON 962 checks and BC 752 checks, and both sets contain `error-sanitization`.
  - Before 9004536d, the satellite-address and schedule-date controlled-400 probes ran unconditionally.
- Impact:
  - The 6 required `packaged-full` executions stay FAIL even after every known product pin is fixed. `releaseReady` cannot become true through the documented procedure, which invites working around the plan.
  - Ordinary unwrapped suite runs report the whole check as SKIP and no longer exercise the #5532/#5533/#5575 refusals.
- Correction:
  - Keep the refusal probes unconditional and make only the fault-route block depend on the token.
  - Either add a receipt-producing plan check that runs the suite under the wrapper, or deselect `error-sanitization` from `packaged-full` in favour of a dedicated wrapped check.

### S26a-3: The fault wrapper replaces the product's HTTP 500 error page for the whole wrapped suite, so installed qualification of 500 handling observes the fixture
- Severity: Medium
- Category: test-gap
- Confidence: Confirmed (the mechanism). Plausible (that a specific check's verdict changes).
- Commit: 9004536d (#5800)
- Location:
  - `scripts/ci/run-installed-error-sanitization.py:95-101,159-160` (global `<error-page><error-code>500</error-code>` mapped to the fixture servlet, held for the wrapped command for up to 36,000 s)
  - `scripts/deb-docker-validation.sh:534` (every suite run is wrapped)
  - `scripts/ci/run-package-lifecycle-cell.py:113-115` (the whole smoke tier is wrapped)
  - `src/main/webapp/WEB-INF/web.xml:729-731` (the product's location-only `errorpage.jsp`)
  - `scripts/fixtures/ErrorSanitizationFaultServlet.java:25-30`
  - `ResponseSanitizationFilter.java:804-815`
  - `scripts/lib/playwright-harness.js:1294-1296`
- Problem:
  - Tomcat prefers an error-code mapping to the default error page. For the entire wrapped suite, every non-/ws 500 (`sendError(500)` or an uncaught exception) is dispatched to the fixture, which emits `java.lang.IllegalStateException: FAKE-private-error-5794`. ResponseSanitizationFilter then always substitutes its own "An error occurred / HTTP Status: 500 / Reference ID" page.
  - `errorpage.jsp` and its `ErrorPageLogger.logIfPresent` ERROR/WARN lines (`errorpage.jsp:58`) are never exercised for a 500 during installed qualification. The server-log audit and PHI log scan see the sanitizer's signature instead.
  - The harness's text detector `assertNotErrorPage` (`/CARLOS has encountered an unexpected error|HTTP Status 500|…/`) does not match the sanitized "HTTP Status: 500" page.
  - 43 check files use `assertNotErrorPage` without `assertStrictPage`, `wireStrictPage` or `runWorkflow`. 8 of those never inspect an HTTP status at all.
- Impact: The main installed evidence (deb-docker-validation suites, lifecycle smoke) qualifies a modified deployment. Regressions in the product's 500 rendering and logging cannot be observed, and 500s reached by text-guarded checks are not recognised as error pages.
- Correction:
  - Install the numeric-500 mapping only while `error-sanitization` itself runs, i.e. wrap `--only error-sanitization` separately.
  - Alternatively, use an exception-type mapping for a fixture-only exception so product 500s keep `errorpage.jsp`.
  - Teach `assertNotErrorPage` to recognise the sanitized page (see S26a-P7).

## Checked and found OK
- `verify()` fails closed on missing, duplicate, stale (source or plan), cancelled and nonzero receipts. It also refuses wrong commands or runtimes, changed or added input files, recomputed-counter mismatches, routed cases that did not pass in their destination, a missing source-bound build and `external` checks.
- `junit_evidence` counts flaky and rerun failures as failures, refuses counter drift (apart from the one documented Surefire collision) and binds display-name containers to their source.
- `run-python-release-tests.py` and `node_results` count skips, TODOs, cancellations, expected failures, subtest failures and import errors as not ready, and reject empty discovery.
- `command_evidence` requires exactly the contract's boolean assertions, with hashed inputs. `process_group` raises on timeout or interrupt, so a timeout is a failure, never a pass.
- `check-coverage-floors.py` compares in the right direction; unmapped files and floors outside the comparison fail.
- `verify-mariadb-dao-reports.py` fails on any skip or failure in all three modes. The CI MariaDB settings match the packaged invariants (`60-carlos-emr.cnf:43-44`).
- The CI browser fixture contract matches script-regressions.yml (SHA c4997404…, 17 commands, every source hash matches).
- Workflow security in this slice:
  - No `pull_request_target`, apart from dco-check, which never checks out PR code and passes the comment body via env.
  - No `${{ github.event.* }}` or `head_ref` inside `run:`.
  - Permissions are `contents: read` (plus `packages: read`).
  - Actions are SHA-pinned.
  - No cross-workflow artifact downloads, and no secrets beyond GITHUB_TOKEN.
  - The WAF steps use bash with pipefail and `tee`.
- Triggers:
  - script-regressions and release-verification run on PRs to every branch and on pushes to release.
  - WAF and Debian Python run on PRs and pushes, path-filtered.
  - maven-project runs on PRs only; cds-native on PRs only, path-filtered.
