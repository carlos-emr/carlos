## Findings
### S26b-1: The `--strict-release` release lanes cannot pass: 20 manifest checks never write a structured result, and several more always SKIP on a standard install
- Severity: Medium
- Category: breaking-change
- Confidence: Confirmed. For the always-SKIP entries, whether any single install could satisfy them is Plausible.
- Commit: 8e70d7a8 (#5655) added strict mode; 7c688417 (#5700) and 9004536d (#5800) added the packaged lanes and made deb `suite` always strict.
- Location: `scripts/run-playwright-suite.js:464-465`, `:564-566`; `docs/testing/release-2026.08-verification.json:3138` (`packaged-full`); `scripts/deb-docker-validation.sh:508`; `scripts/ci/release_verification.py:396-401` (consumer)
- Problem:
  - **The strict PASS rule.** In strict mode a check that exits 0 counts as PASS only if it wrote a RESULT_JSON record whose outcome is PASS. Only `runCheck`/`runWorkflow`/`runLegacyCheck` write that record.
  - **20 manifest entries never write it.** I checked that no structured runner is reachable through their requires. Each still exits 0 on success and `process.exit(1)` on failure:
    - core: add-login-account, allergy-rx-alert, consultation-nullable-fields, consultation-signature-submit, demographic-add, echart-new-patient-notes, edoc-schedule-navigation, eform-admin-crud, flowsheet-admin, flu-billing-report, patient-list-by-appointment-export, prescription-signature, report-demographic-navigation, rx-fax-record-binding, rx-fax-reprint-represcribe, rx-fax-signature-stamp, rx-preview-pharmacy, tickler-note-dialog;
    - standalone: chart-draw, dependency-tables.
  - **Every strict lane fails them unconditionally.** All 20 are non-manual and unprofiled. 19 have province `all`; `flu-billing-report` is ON only. So they fall into:
    - `packaged-full` (strict, no tier filter; the verifier expects every non-manual default-profile check for the province);
    - deb `suite --tier core`, which is now always strict.
  - **Other entries in the same selection always SKIP on a standard demo install,** and strict mode turns a SKIP into FAIL:
    - `o19-migrated-smoke` (extended, not manual) needs an `carlos-ctl import-o19` database and its credentials (`o19-migrated-smoke-playwright-checks.js:698`). The runbook forbids pointing it at a normal database.
    - `pathnet-status` and `legacy-lab-display-pathnet` are marked provinces `all` but SKIP unless the legacy BC PathNet tables exist and `PATHNET_LABS=yes`. See `pathnet-status-playwright-checks.js:20,25` and `legacy-lab-display-playwright-checks.js:32,70`.
  - No document or ledger lists any of these checks as known strict-mode blockers.
- Evidence:
  - The runner rule:
    ```
    raw = options.strictRelease && (!record || record.outcome !== 'PASS' || record.cleanupFailed)
      ? { outcome: 'FAIL', detail: 'strict release: successful exit lacks a consistent clean structured PASS' }
    ```
  - Reproduced with the real runner and a record-less child that exits 0:
    - without `--strict-release`: `PASS legacy-pass ... EXIT 0`;
    - with `--strict-release`: `FAIL legacy-pass -- strict release: successful exit lacks a consistent clean structured PASS ... EXIT 1`.
  - `packaged-full` command: `node scripts/run-playwright-suite.js --strict-release --province {profile} --residue-audit --junit {run}/browser.xml`.
- Impact:
  - The documented qualification lane (`verify-release-evidence.py run --check packaged-full`, iterations 1–3 per province) can never report ready, even with a defect-free application. Every attempt fails with 20+ unrelated "FAIL" rows.
  - The failure is loud, not silent. But it will be misread as product regressions, and it pushes operators toward dropping `--strict-release`, which would bring back the skip-as-pass behaviour of #5795.
- Correction:
  - Convert the 20 scripts to `runCheck`/`runLegacyCheck`. Make `playwright-suite-manifest.test.js` fail when a manifest script cannot reach a structured runner.
  - Move environment-bound checks out of the default selection: mark `o19-migrated-smoke` manual or give it its own profile, and set `pathnet-status` / `legacy-lab-display-pathnet` to provinces `["BC"]` plus a PathNet profile. Alternatively, list them in the verification matrix as separately qualified lanes.

### S26b-2: Two new #5800 checks report every finding under the first finding's step label, so a single expected-failure pin would hide the others
- Severity: Low
- Category: silent-failure
- Confidence: Confirmed. The masking is latent: neither check is pinned yet.
- Commit: 9004536d (#5800)
- Location: `scripts/tickler-mrp-routing-playwright-checks.js:180-182,231`; `scripts/lab-recall-delegate-delivery-playwright-checks.js:165,249`; `scripts/run-playwright-suite.js:391`
- Problem:
  - **What the checks do.** Both checks collect several independent semantic failures and then throw `markFailedStep(new AggregateError(findings,…), findings[0].failedStep)`.
  - **Why that defeats the runner.** The runner classifies a run as `known-fail` whenever the failing step equals the pinned step. So pinning the first finding would report the run as a non-failing known-fail even when other, different findings also failed, including new regressions.
  - **Which findings would be hidden.** In tickler-mrp-routing the first runtime finding is the literal, pinnable label "unsaved MRP composer survives patient selection" (#5824). Pinning it would hide the missing/inactive-MRP fallback findings (#5825) and any future finding.
  - **This breaks two stated contracts:**
    - the runner's "a known defect cannot hide a new one";
    - the convention in `waf-clinical-text-corpus` (`finishRows`: "several failed rows … must not hide behind one pin"), which reports `N route rows failed`.
- Evidence: `if(findings.length)throw h.markFailedStep(new AggregateError(findings,…),findings[0].failedStep);`. The runner's rule is `if (raw.failedStep === expected.step && !raw.cleanupFailed) return known-fail`.
- Impact:
  - Today there is no effect: both checks fail loudly. `tickler-mrp-routing-inventory.md` notes four known failing comparisons and that no pin was added.
  - Pinning is the project's usual way to unblock release (#5793). The first pin added would silently mask unrelated defects in the MRP-routing and lab-recall paths.
- Correction: follow `finishRows`. Use the finding's own label only when exactly one finding exists; otherwise use a synthetic label such as `${findings.length} findings` that no pin can match.

### S26b-3: Packaged `suite` qualifies a modified deployment: the whole run is wrapped in the #5794 fault adapter, which rewrites the installed web.xml
- Severity: Low
- Category: test-gap
- Confidence: Confirmed
- Commit: 9004536d (#5800)
- Location: `scripts/deb-docker-validation.sh:534`; consumer `scripts/ci/run-installed-error-sanitization.py:89-103,151-171`; shipped `src/main/webapp/WEB-INF/web.xml:729-731`
- Problem:
  - **What `suite` now runs.** `cmd_suite` runs the entire requested suite (any tier) inside `run-installed-error-sanitization.py`. For the whole run, the adapter adds `<error-page><error-code>500</error-code><location>/__test-error-<token>.jsp</location>` and a test servlet to the installed `web.xml`, restarts CARLOS, and only afterwards restores the file and restarts again.
  - **Every application 500 is rendered by the fixture.** Specific error codes take precedence over the shipped default `<error-page><location>/WEB-INF/jsp/error/errorpage.jsp</location>`. So every application 500 seen by every other check is rendered by the fixture servlet (tainted body plus an `X-Carlos-Test-Error-Dispatch` header) and then replaced by the sanitizer's `<title>Error 500</title>` page, not the shipped errorpage.jsp.
  - **The adapter's error message is misleading.** It raises "Installed front-door error check failed" whenever any check in the wrapped suite fails.
- Evidence:
  - `in_container ". /root/suite-env.sh; CARLOS_DISPOSABLE_HOST=true python3 scripts/ci/run-installed-error-sanitization.py -- node scripts/run-playwright-suite.js $quoted --junit …"`.
  - Adapter: `if result.returncode: raise RuntimeError('Installed front-door error check failed')`.
- Impact:
  - Qualification evidence for 500 paths comes from a configuration that is never shipped. errorpage.jsp's 500 rendering, which production users see, is never exercised in packaged runs.
  - Checks whose negative assertions rely on `isApplicationErrorPage()` (`<title>Error Page</title>`) see a different body for 500s. I found no current check whose pass depends on that, so the residual risk is coverage, not a false pass.
- Correction:
  - Run the adapter only around `--only error-sanitization`, as a separate step before or after the main suite, the way `run-package-lifecycle-cell.py` does for explicit selections.
  - Have the adapter's error name the failed command generically (for example, "wrapped command failed").
