## Findings

### S26c-1: The SQL-safety hook now lets quote-sandwich SQL through ("never allowlistable") whenever the predicate is not a bare column
- Severity: Medium
- Category: regression
- Confidence: Confirmed
- Commit: d86b63cc (#5616)
- Location: `.claude/hooks/validate-sql-safety.py:760` and `:798` (new gate), `:620-670` (`has_sql_context`), `:729`, `:744-747` (quote sandwich, `always_unsafe=True`), docstring `:26-27`
- Problem: The new `if not has_sql_context(statement): continue` runs before the `always_unsafe` handling, for every pattern including the quote sandwich. A statement now counts only if it has one of:
  - a sink;
  - a query-named variable (the generic `sb`, `buf` and `conditions` are deliberately excluded);
  - a literal matching the narrow `sql_structure` regex.

  Predicates whose left side is an expression fail all three: `lower(col) = '`, `DATE(x) = '`, `CAST(…) = '`, `CASE WHEN … = '`, `concat()`/`IFNULL()`, and a leading `' OR col = '`. So does an IN-list item built in a generic builder (`sb.append("'" + t + "'")`). For these the always-unsafe quote sandwich is now skipped, although main blocked all of them. The 110 fixtures contain no such case, so CI stays green.
- Evidence: exit codes of the main and release hooks on Write payloads:

  | Code | main | release |
  |---|---|---|
  | `String nameFilter = "lower(d.last_name) = '" + lastName + "'";` | 2 | 0 |
  | `String cond = "DATE(a.appointment_date) = '" + day + "'";` | 2 | 0 |
  | `filters.add("lower(last_name) = '" + name + "'");` | 2 | 0 |
  | `conditions.add("CAST(dob AS DATE) = '" + dob + "'");` | 2 | 0 |
  | `"CASE WHEN status = '" + s + "' THEN 1 END"` | 2 | 0 |
  | `"' OR last_name = '" + name + "'"` | 2 | 0 |

  On a real file, I sent a no-op Edit of `src/main/java/io/github/carlos_emr/carlos/commn/dao/PatientLabRoutingDaoImpl.java:296` (`sb.append("'" + t + "'");`, which is consumed at `:299` as `x.labType in (" + sb.toString() + ")"`):
  - main: blocked (`CRITICAL: Value embedded between SQL quotes (injection)`);
  - release: allowed (exit 0).
- Impact: Claude Code edits can now add quote-embedded SQL injection without the hook objecting, which breaks the hook's documented invariant. CodeQL and Semgrep still catch tainted flows in CI, but values that do not look tainted (method parameters) pass every local gate. There is no production runtime effect.
- Correction:
  - Apply the context gate to always-unsafe patterns only when the literal is a logger or exception message (`is_message_literal`). Alternatively, count as SQL context any literal ending in `<expr> <comparison op> '` or `IN ('`, and a bare `'` appended to a builder.
  - Add expected-2 fixtures for the cases above.

### S26c-2: The review-attribution fix was not applied to the HTML/link document editor (AddEditHtml2Action)
- Severity: Medium
- Category: omission
- Confidence: Confirmed
- Commit: 8e70d7a8 (#5655)
- Location: `src/main/java/io/github/carlos_emr/carlos/documentManager/actions/AddEditHtml2Action.java:142-147`, `:169-177` (identical on main). The fix was applied only at `AddEditDocument2Action.java:653-657` and `:720-735`.
- Problem: 8e70d7a8 made AddEditDocument2Action ignore the posted `reviewerId`, `reviewDateTime` and `extraReviewerId` ("A review attests to the authenticated actor, never a hidden form field"). `docs/testing/release-2026.08-verification.md:61-62` says document reviews now take the actor from the session. The sibling routes `documentManager/addEditHtml` and `documentManager/addLink` (struts-document.xml:109-116) still trust the posted values. They fall back to the session user only when no reviewer is posted, then `EDocUtil.editDocumentSQL(currentDoc, this.getReviewDoc())` writes the reviewer and the time (its `doReview` branch). The edit branch accepts any document id, not only HTML documents.
- Evidence: `String reviewerId = filled(this.getReviewerId()) ? this.getReviewerId() : ""; … if (!filled(reviewerId) && this.getReviewDoc()) { reviewerId = (String) request.getSession().getAttribute("user"); … }` → `EDocUtil.editDocumentSQL(currentDoc, this.getReviewDoc());`. A POST of `mode=<docId>&reviewDoc=true&reviewerId=<other provider>&reviewDateTime=2020/01/01 00:00:00` records that provider and that time as the reviewer. No REVIEWED audit row is written on this path.
- Impact: Any user with `_edoc w` can attribute a document review to another clinician, backdated, through this endpoint. Ordinary use of the page is unaffected: addedithtmldocument.jsp:426-431 shows "Reviewed" only on unreviewed documents and posts an empty reviewerId.
- Correction:
  - When `reviewDoc` is true, take the reviewer from LoggedInInfo and the time from the server, and ignore the posted reviewer fields.
  - Write the REVIEWED audit.
  - Add the forged-field regression test (the same shape as `shouldAttributeReviewToSessionActor_whenPostedReviewerIsForged`).

### S26c-3: REST unmerge, which now works, still "succeeds" and writes audit rows for links that are already removed
- Severity: Low
- Category: data-integrity
- Confidence: Confirmed
- Commit: 8e70d7a8 (#5655)
- Location: `src/main/java/io/github/carlos_emr/carlos/commn/dao/DemographicMergedDaoImpl.java:83-88`; `src/main/java/io/github/carlos_emr/carlos/managers/DemographicManagerImpl.java:716-734`
- Problem: After the parameter swap, `findByParentAndChildIds` matches real rows, so `DELETE /ws/rs/demographics/merge` works for the first time. On main, correctly ordered ids always produced IllegalArgumentException, which reached the client as HTTP 500. However, the query has no `deleted = 0` filter, which causes three problems:
  - Unmerging a pair that was already unmerged finds the deleted row, returns 204 and writes a new `DemographicManager.unmergeDemographics` audit row.
  - A pair merged twice gets one audit row per historical row.
  - Unlike the admin `DemographicMerged.UnMerge` (`demographic/data/DemographicMerged.java:126-153`), the REST path neither stamps lastUpdateUser/lastUpdateDate nor removes the `_eChart$<child>` row. Only the legacy Index2.jsp:115 reads that row.
- Evidence: `createQuery("d", "d.demographicNo = ?1 AND d.mergedTo = ?2")` has no deleted predicate. The manager does `for (dm : findByParentAndChildIds(...)) { dm.setDeleted(1); merge(dm); LogAction.addLogStrict(..., "id=" + dm.getId()); }`.
- Impact: REST clients cannot tell "unmerged now" from "was not merged", and the audit log records unmerges that changed nothing. No clinical data changes.
- Correction:
  - Select only active links (`deleted = 0`).
  - Return 404 or 409 when no active link exists.
  - Stamp lastUpdateUser and lastUpdateDate.
  - Decide whether REST unmerge should clean up the `_eChart$<child>` row the way the admin path does.

### S26c-4: The deadlock-avoiding scalar lock covers only the REST merge; the admin Merge Records page still takes the lock the commit calls deadlock-prone
- Severity: Low
- Category: omission
- Confidence: Plausible
- Commit: 8e70d7a8 (#5655). The admin locking came from a24c5666 (#5609), committed one day earlier on this release.
- Location: `src/main/java/io/github/carlos_emr/carlos/commn/dao/DemographicDaoImpl.java:1793-1802`; `src/main/java/io/github/carlos_emr/carlos/demographic/pageUtil/DemographicMergeRecord2Action.java:156-161`
- Problem: lockForMerge exists because "A hydrated PESSIMISTIC_WRITE also locks the eager demographic_merged join. Its empty index gaps can deadlock two otherwise disjoint merge parents." Only DemographicManagerImpl (REST, which no UI calls) uses it. The admin merge page, which is the real merge UI, still locks with `demographicDao.findForUpdate(id)` (`DemographicDaoImpl.java:1786-1790`, `find(..., PESSIMISTIC_WRITE)`).
- Evidence: `if (demographicDao.findForUpdate(id) == null) { return false; }` runs inside a TransactionTemplate. DemographicMergeMariaDbIntegrationTest drives only DemographicManagerImpl, so this path has no native contention test.
- Impact: Two concurrent admin merges of disjoint patients could deadlock. InnoDB would roll one back and the error would escape `TransactionTemplate.execute` to the error page. This is rare, and nothing is left half-merged.
- Correction: Use `lockForMerge` in `mergeRecords`, keeping the same sorted order. To confirm the risk, run the existing contention test against `mergeRecords`.

### S26c-5: An additional review of a document whose first review was cleared leaves it unreviewed; a vanished document fails without a message
- Severity: Low
- Category: bug
- Confidence: Confirmed (a race is needed to trigger it)
- Commit: 8e70d7a8 (#5655)
- Location: `src/main/java/io/github/carlos_emr/carlos/documentManager/actions/AddEditDocument2Action.java:623-629`, `:720-735`, `:753-758`
- Problem: The client still decides whether a click is a first or an additional review: `extraReviewDoc` is set in editDocument.jsp:254-264 from the reviewer that was loaded with the page.
  - If the stored review was cleared after the page loaded (any metadata "Update" clears it, through the `doReview=false` branch of EDocUtil.editDocumentSQL), the extra path copies the now-blank stored reviewer (`newDoc.setReviewerId(storedReview.getReviewer())`, which is null, plus an empty time). The document stays unreviewed and the clinician's review exists only as a DocumentExtraReviewer row. Main instead restored the stale hidden reviewer, which was also wrong.
  - If the document is deleted between the access check and the lookup, the action throws IllegalStateException. The generic `catch (Exception)` turns it into `failEdit` with an empty error table, so the user sees no message.
- Evidence: see the cited lines; `catch (Exception e) { request.setAttribute("docerrors", errors); … return "failEdit"; }` runs with `errors` empty.
- Impact: The clinician believes the document is reviewed, while lists and the inbox show it as unreviewed.
- Correction:
  - Decide the mode on the server from the stored reviewer: blank means a first review by the actor, present means an additional review (see S26c-P1).
  - Add an error key for the missing-document case.

## Pre-existing issues

### S26c-P1: Review attestation follows client flags: "Reviewed" with a replacement file keeps the old reviewer on new content, and concurrent first reviews overwrite each other
- Severity: Medium
- Category: data-integrity
- Confidence: Confirmed
- Pre-existing: yes (present on origin/main)
- Location (release / main): `src/main/java/io/github/carlos_emr/carlos/documentManager/actions/AddEditDocument2Action.java`
  - content update: `:631-648` / main `:625-641`;
  - file write: `:680-716` / main `:673-709`;
  - additional review keeps the first reviewer: `:720-737` / main `:713-727`.

  JSP: `editDocument.jsp`: `reviewed()` at `:254-264` calls `form.submit()` on the same multipart form that holds `docFile` (`:439`); the Reviewed button is at `:471`.
- Problem:
  - **Replacement file plus "Reviewed"**: when a file is selected and the user clicks "Reviewed" on an already-reviewed document, the action uploads the replacement content and then calls `editDocumentSQL(newDoc, true)` with the stored first reviewer and time. The first clinician's attestation now covers content they never saw. Main did the same through the hidden reviewer and time fields; 8e70d7a8 reimplemented it from the database. `form.submit()` also skips the page's `onsubmit` confirmation.
  - **Concurrent first reviews**: two clinicians who both opened an unreviewed document both post `reviewDoc=true`. The second save overwrites the first reviewer, and the first review leaves no DocumentExtraReviewer row.
- Evidence: release `:732-735`: `newDoc.setReviewerId(storedReview.getReviewer()); newDoc.setReviewDateTime(... storedReview.getReviewdatetime() ...)` runs after `writeValidatedUpload(...)` (`:696`). Main `:723-724`: `this.setReviewDoc(true); newDoc.setReviewDateTime(this.getReviewDateTime());`.
- Impact: The "Reviewed by Dr A [date]" shown on a replaced clinical document is misleading, and a review can silently disappear.
- Correction:
  - Decide first versus additional review from the stored state, inside the save transaction.
  - When content is replaced, clear the previous attestation (as "Update" does) and record only the actor's review.

### S26c-P2: AddEditHtml2Action add and edit paths lack the patient and stored-document write checks that AddEditDocument2Action enforces
- Severity: Medium
- Category: security
- Confidence: Confirmed
- Pre-existing: yes (present on origin/main; the file is unchanged on release, so line numbers are the same)
- Location: `src/main/java/io/github/carlos_emr/carlos/documentManager/actions/AddEditHtml2Action.java`:
  - only the global `_edoc w` check: `:75-78`;
  - add with request `function`/`functionId`: `:151-168`;
  - edit of any document id: `:169-177`.

  For comparison: `AddEditDocument2Action.java:359` (requirePatientDocumentWriteAccess) and `:608` (requireStoredDocumentWriteAccess), the same lines on main and release. The `ViewDocumentWrite2Action.java:57-59` gate checks only when the form is rendered.
- Problem: A direct POST to `documentManager/addEditHtml` or `addLink` can:
  - add an HTML or link document to any patient (`function=demographic&functionId=N`), without `isAllowedAccessToPatientRecord` or a per-patient `_edoc` check;
  - change the description, type, html/docxml, responsible, public flag and review fields of any stored document by id, including documents of patients the user is locked out of (`_demographic$N`/`_eChart$N`).
- Evidence: the only security check is `securityInfoManager.hasPrivilege(..., "_edoc", "w", null)`; neither `IncomingDocumentCapacityResponse.require*` method is called.
- Impact: Circle-of-care authorization bypass for document metadata and review state, available to any `_edoc w` user.
- Correction: Call `requirePatientDocumentWriteAccess` on add and `requireStoredDocumentWriteAccess(…, mode)` on edit, before any write, as AddEditDocument2Action does. Also consider restricting the edit branch to HTML/link documents.

### S26c-P4: The SQL hook (both versions) misses method-call operands in quote sandwiches, keyword-less predicates and append-chained quotes
- Severity: Low
- Category: security
- Confidence: Confirmed
- Pre-existing: yes (present on origin/main)
- Location: `.claude/hooks/validate-sql-safety.py:701` and `:710` (concat/append patterns use `[^"\']*`, so an embedded `'` ends the literal), `:729` (the quote sandwich needs a bare `\w+` operand). Main: `:581`, `:590`, `:609`.
- Problem: All of these exit 0 on both main and release:
  - `String sql = "SELECT * FROM demographic WHERE last_name = '" + request.getParameter("name") + "'";` with the sink in a later statement;
  - the same with `form.lastName`;
  - `String filter = " AND d.demographic_no = " + demoNo;`
  - `sql.append(" AND last_name = '").append(name).append("'");`
  - a text block filled with `.formatted(name)`. `String.format("… '%s'", name)` is caught by both versions.

  The release now catches the inline-sink form (`stmt.executeQuery("…'" + request.getParameter("n") + "'")`: main 0, release 2).
- Evidence: results of the comparison scripts I ran in the scratch work-S26c folder (compare3.py, compare4.py).
- Impact: The classic request-parameter injection passes the AI-edit guard when it is assigned to a variable first. CI CodeQL and Semgrep remain the backstop.
- Correction: Allow dotted and call operands in the quote-sandwich pattern, stop treating `'` as a literal terminator in the concat patterns, and treat `.append("…'")` followed by a non-literal append as a sandwich. Add fixtures for each case.

### S26c-P5: The SQL hook blocks every edit to 89 core source files because it rescans pre-existing dynamic SQL in the whole file
- Severity: Low
- Category: process
- Confidence: Confirmed
- Pre-existing: yes (present on origin/main, where 272 files were affected; release reduces this to 89)
- Location: `.claude/hooks/validate-sql-safety.py:543-567` (whole post-edit file reconstructed) and `main()` (exit 2 on any issue)
- Problem: For Edit and MultiEdit the hook rescans the entire file, so a file that already contains flagged dynamic SQL (much of it built from whitelisted fragments) blocks every edit, including comment-only edits. - Correction: Block only on issues whose span overlaps the edited text (diff the pre-edit and post-edit issue sets), and report pre-existing issues as warnings.

### S26c-P6: `.claude/settings.json` does not implement the guardrails CLAUDE.md documents as enforced
- Severity: Low
- Category: process
- Confidence: Confirmed for the content of the lists; Plausible for how `Write(...)` and `Edit(...)` rules interact
- Pre-existing: yes (present on origin/main; unchanged since alpha10)
- Location:
  - `.claude/settings.json`: `:101` `Bash(git commit *)`, `:106` `Bash(git push origin *)`, `:54-59` Write/Edit allows for migrations, `:120-122` `gh api` writes only in the ask tier, `:125-136` deny list (23 entries).
  - CLAUDE.md: `:1272`, `:1276-1283`, `:1307-1327`.
- Problem: CLAUDE.md says force-with-lease, force pushes with the flag after the remote, `--amend`, `--no-verify`, rebase, `push origin --delete`, remote add/set-url, `gh workflow` and `gh api` write methods are blocked, with "layered defense" across flag orders. The deny list has none of these.
  - Because `Bash(git push origin *)` and `Bash(git commit *)` are allowed, `git push origin main --force`, `git push origin --delete x`, `git commit --amend` and `git commit --no-verify` all run without a prompt.
  - File protection uses only `Write(...)` denies and has no `Edit(...)` deny.
  - `Edit(database/mysql/migration/*/V1.0.*__*.sql)` explicitly allows editing existing Flyway migrations, including published ones, which CLAUDE.md forbids, while `Write(database/**)` denies creating new ones.
- Evidence: the allow, ask and deny lists as listed above.
- Impact: The safety model described to maintainers is weaker in practice. Server-side branch protection still guards the protected branches.
- Correction: Add the documented deny patterns (both flag orders, `=` variants, `--delete`, `--amend`, `--no-verify`, `gh api -X POST`/`--method`), add `Edit(...)` denies for `.git/**`, `.github/**` and `database/**` (or remove the Edit allows for existing migrations), or correct CLAUDE.md.
