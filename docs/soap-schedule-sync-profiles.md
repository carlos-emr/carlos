# SOAP schedule synchronization

The published WSDLs and operation signatures remain the default contract. These profiles apply only to `getAppointmentsUpdatedAfterDate`, `getAppointmentArchivesUpdatedAfterDate` and `getAppointmentsByProgramProviderDemographicDate` on ScheduleWs. Check the published WSDL for exact parameter names; the original exclusive timestamp and existing program/provider/patient filters retain their meaning.

## Default timestamp profile

Omitting `X-Carlos-Schedule-Sync-Profile`, or selecting `legacy-timestamp`, keeps the published request: an exclusive timestamp and a page size (maximum 5,000). Zero retains the existing empty-list behavior. Rows have deterministic update-time/record-ID ordering. **An unmodified client needs no change, and a request is never refused because of where its page boundary falls.**

The contract such a client relies on is the one the operations have always had: the query is strictly *after* the supplied timestamp (`updatedatetime > bound`), and the client's next bound is the newest `updateDateTime` it received. The column stores whole seconds, so several rows often share one. If a page ended inside such a group, the next request would start after the whole second and the remaining rows of the group would never be delivered.

The server therefore completes the group that the last row of the page belongs to:

- The response holds the requested rows plus the remaining rows that share the last row's update timestamp. It can be **longer than the requested page size**, by at most the rest of that one group. A client must not treat "more rows than I asked for" as an error, and should keep paging until it receives an empty page (a client that stops at a page shorter or longer than its page size simply resumes from its bound on its next run).
- The response never exceeds the 5,000-row hard limit.
- If even 5,000 rows cannot hold the whole group (for example, more than 5,000 appointments written in the same second by a bulk operation), the server returns exactly the requested rows, as 2026.08.0-beta6 did, and logs a warning containing only row counts. A timestamp-only client then moves past that second without the rest of the group, as it always did. Nothing short of the cursor profile below can page through a group of that size; clients that may meet one should adopt it.
- Consent filtering is applied before the group is completed: only rows the caller may see count toward the page or extend it.

A client that follows the contract above cannot stall or loop: every non-empty page ends at a timestamp later than the bound that produced it. Each call owns one repeatable-read transaction, so the requested rows and the completion of their group are read from the same snapshot.

## Explicit timestamp/ID profile

Send `X-Carlos-Schedule-Sync-Profile: timestamp-id` and a positive page size up to 5,000. On the first request omit `X-Carlos-Schedule-Cursor`. Read `X-Carlos-Schedule-Next-Cursor` and `X-Carlos-Schedule-Has-More` from the HTTP response. When more is true, send that next cursor as `X-Carlos-Schedule-Cursor` on the next request. Keep the original exclusive timestamp, actor, operation, filters and GMT selection unchanged. Page size may change. The cursor contains the last returned row's timestamp/ID, never a consent-blocked row's position. On an empty terminal page the previous cursor is retained; on an initially empty page there is no next cursor.

Both profiles acknowledge `X-Carlos-Schedule-Sync-Profile`, `Cache-Control: no-store` and `X-Carlos-Schedule-Reconciliation: required`. Unknown, blank or repeated profile/cursor headers, a cursor without the cursor profile, and a cursor reused with another actor, operation, original bound or filters produce Client faults before data access; a request that sends none of these headers cannot receive any of those faults. A cursor-profile page never exceeds the requested size. Cursor metadata is validated against returned rows. Storage/policy failures fault the entire call with a fixed server message; no successful partial page is returned. Cursor encoding is canonical base64url and context-bound, not a signed authorization credential. Every request still applies the operation's existing authority and consent policy.

Each call owns a repeatable-read transaction. Native queries use `(updatedatetime, primary key)` seek positions with raw batches of at most 500. Consent filtering continues across blocked batches until a full permitted page plus one permitted lookahead row, or the request snapshot's end. An unrestricted update privilege retains its existing consent-bypass behavior. Archive and program/provider/patient operations retain their existing policy, rather than inheriting a new consent rule from another operation.

## Reconciliation and extension compatibility

Timestamp/ID continuation is complete for a stable set of records, including arbitrarily large tied groups. It is not a change-data-capture log. A transaction can commit a row behind an already issued cursor; existing rows can also move behind it, and patient access can change. `Has-More: false` means the current request snapshot was exhausted. Clients must apply idempotent record updates, replay from an earlier trusted bound periodically and perform a full reconciliation when their lateness/access assumptions no longer hold. A fixed overlap cannot guarantee arbitrary late-commit capture. Preserve the terminal cursor for continuation, and retain a separate reconciliation checkpoint; never advance that checkpoint merely because a page is empty.

Custom ScheduleManager/appointment DAO implementations must implement the new seek/page extension methods to use safe paging. Their default implementations fail explicitly when unsupported; they do not silently fall back to timestamp-only queries. Existing method descriptors remain available. Native acceptance uses production DAO queries and Spring transaction annotations on generated, Ontario and BC schemas. `ScheduleLegacySyncEndpointTest` (real SOAP, real manager) and `ScheduleLegacySyncIntegrationTest` (production queries and transaction annotations) drive a timestamp-only client across groups that straddle page boundaries for all three operations and require every row exactly once without a fault; `AppointmentUpdatePagesUnitTest` covers the hard-limit boundary and the truncating fallback. It separately proves a late commit is recovered by replay, rather than claiming impossible lossless streaming across independent request snapshots. Audit persistence has separate transaction tests; these paging fixtures replace only the audit sink.
