# BC billing and Dx Research spreadsheet exports

Issue #5438 moves eight BC CSV exports to Apache Commons CSV and Dx Research XLSX to a direct table writer. The #5472 dependency cleanup supplies the shared JDK OOXML implementation; POI remains a test-only workbook reader. That writer (`SpreadsheetExport`) streams without buffering and flushes the caller's stream only after the complete package; if a row or the stream fails part-way it abandons the archive (no central directory, no flush), so a direct-response caller whose response is still uncommitted can return HTTP 500 instead of a truncated workbook. A literal `_` before `xHHHH` is always written `_x005F_`, whether or not a closing `_` follows, so readers never decode report text as an OOXML escape. PDF generation and the three shared remittance subreports remain on Jasper. The pre-change files are in `src/test/resources/export-baseline`, committed separately before the replacement.

All CSV files retain `<REP_TYPE>.csv`, UTF-8 without BOM, LF records and the `application/csv` content type (now with an explicit UTF-8 charset). All fields are quoted. They have one header, no run timestamp, report/page titles, blank layout columns, repeated page headings or page-number footers. Each source record occupies one CSV record (invoice/rejection exports may append an explicitly labelled warning record when malformed C12 claim identifiers were excluded); embedded newlines remain quoted cell content. The shared `SpreadsheetCsv` policy prefixes formula-like text with a tab, including leading tab/CR/LF and disguised formula markers; plain negative numbers stay numeric. This guard tab is intentional cell content.

Money is plain decimal CAD with two places and no currency symbol or thousands separators. Dates use `dd-MMM-yy` with Canadian English month names. Missing or legacy `00000000` report dates are empty. Malformed nonempty accounting dates and amounts retain their source text (with the same spreadsheet formula guard), so legacy rows do not abort the download. Out-of-range amounts retain their original notation. An invoice whose billed amount is unavailable or cannot be represented as a finite balance has an empty calculated Balance; A/R retains that row rather than treating its unknown balance as settled. Malformed S00 payment amounts also leave the calculated balance empty and retain the claim, without assuming a zero payment. Payment/refund summaries exclude missing or malformed amounts and individual adjustment components from their known subtotals, retain valid payments, refunds and adjustment components (including adjustments on zero payments), and report the count of unparsed amount fields. Any affected total is labelled “known amounts only”; the warning counts fields, not claims. In payment detail, an unparseable adjustment total shows the seven components separated by ` | `; fractional-cent payment input is labelled `Unparsed Teleplan amount` to avoid presenting it as decimal dollars. Patient DOB, HIN and phone strings are preserved as supplied. Host locale does not select any output format.

Files are completed in private temporary files before download headers or response streams are accessed. Generation/query failures return HTTP 500 with no attachment or partial file; missing/invalid download parameters return HTTP 400. Billing and report privilege checks remain in the action entry points. Export failure logs contain fixed messages and exception class names, never patient rows or exception messages. Both CSV and PDF accounting readers propagate query failures. The remittance PDFs (`pdf_rep_msprem`, `pdf_rep_mspremsum` and its `msppremsum.practsum` and `msppremsum.s23` subreports) use the same implied-cents decoder through `TeleplanAmount.known`, which never throws from a template expression: one stored field that is not a Teleplan amount (`12.5`, `+123`, a stray letter) no longer refuses the whole PDF with HTTP 500. The report prints every row. Such a field is shown as `Unparsed Teleplan amount: <source text>`, the CSV wording: in the cell itself where the cell is wide enough (remittance summary header and practitioner rows), otherwise as a `?` in the amount cell and a line under the row that names the column (remittance detail and adjustment rows), so the source text is never printed alone where it could be read as dollars. Totals add known amounts only; the practitioner total, the remittance summary and the adjustment totals print `Known amounts only. Unparsed amount fields excluded: N`. A blank or missing Teleplan amount is a real zero (it is what a held S04 line stores) and is neither flagged nor counted. Rows without a malformed field keep their previous layout. Valid empty PDFs remain supported.

Payment/refund detail and summary PDFs retain unreadable private-payment amounts explicitly and exclude them from known-only totals, matching CSV. Detail rows label unavailable amounts as Unknown; both PDFs print the number of unparsed amount fields excluded. Malformed adjustment detail remains visible and is excluded when it is not a single decimal. Query failures still refuse the entire download.

A blank Teleplan paid amount on a payment row is zero, not an unparsed field: every held (S04) remittance line is stored that way, so such rows are left out of the Payments and refunds detail and summary (PDF and CSV) unless they carry an adjustment, exactly like an explicit zero, and they do not count towards the unparsed-field notice.

Rejected Teleplan detail amounts retain their source text with an `Unparsed Teleplan amount:` prefix. This also applies to numeric-looking invalid wire values such as `12.3`, `1e3` and `+123`, so later CSV/PDF formatting cannot reinterpret them as decimal dollars or include them in totals.

Private-payment amounts and adjustments use plain decimal text, with surrounding whitespace accepted. Scientific notation remains visible as source text and is excluded from known totals, so exponent strings cannot expand into huge arithmetic allocations. Summary rows with unparsed fields remain present even when their known payment subtotal is zero and no adjustment code is present. Unknown private balances refuse settlement rather than being classified as balanced.
