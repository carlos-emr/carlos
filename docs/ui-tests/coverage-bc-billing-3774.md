# BC supplementary billing associations (#3774 / #3784)

Coverage found an inverted validation branch: valid edits and every delete redirected before persistence, while invalid edits reached the DAO. Six focused assertions fail on the original release. The fix writes only validated POST edits/deletes, rejects unknown modes and malformed delete identifiers, redirects after successful persistence, and renders action errors without writing on validation failure. The form now has the name its fee-code picker expects.

Review follow-up hardened two further points. Mutations now require `_admin.billing`/`_admin` write rights, matching the `<security:oscarSec>` gate on `billingSVCTrayAssoc.jsp`: a successful mutation redirects instead of rendering that JSP, so a plain `_billing` writer could otherwise POST the action directly and change shared billing configuration the page refuses to show them. Reading the list still needs only `_billing` write, as before. The page also renders validation errors through a single `<carlos:encode>` loop; the raw scriptlet loop and the `<s:actionerror/>` tag that previously both rendered them were removed, so submitted service codes cannot reach the browser unencoded or twice. Because those bundle messages are legacy HTML fragments, the action strips their trailing `<br/>` before handing them to the encoder, and the two Polish values this page renders were moved from `&#X...;` entities to the `\uXXXX` escapes the rest of that bundle uses; `SaveAssoc2Action` and `BillingCreateBilling2Action` share these keys and still render them as markup, so the tag stripping stays in this action rather than in the bundles.

The focused Java suite includes invalid primary/secondary codes, successful save/delete, GET rejection, unknown mode, invalid delete identifier, read-only view, missing billing-admin rights and error exposure to the JSP, plus the mutation-action discovery contract. The browser workflow opens Administration through the schedule, creates three owned fee codes, rejects an invalid association, creates/reopens/updates/deletes an owned association, verifies database values and cleans up its rows. It requires a BC schema and billing region; an Ontario deployment reports SKIP, not PASS.

Local Java tests pass with the VM stopped. All three browser steps passed on the Ubuntu 26.04 VM using installed validation14 DEBs and a freshly migrated/seeded BC schema: visible invalid-input rejection, create/reopen, then update/delete with exact database assertions and owned-fixture cleanup. The original ON configuration was restored after testing. No migration or schema is added by the fix.
