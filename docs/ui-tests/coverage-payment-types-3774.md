# Ontario payment-type CRUD (#3774 / #3786)

Live installed-DEB testing confirmed 403 responses because the payment JSPs set CSRF-TOKEN explicitly and CSRFGuard's XHR wrapper appends a second value. Waiting for bootstrap did not help; a diagnostic counted two header segments without recording token values. The fix waits for bootstrap, sends the token as a protected form parameter, leaves the automatic XHR header to CSRFGuard, reports token failures without submitting, and makes AJAX error text readable. Delete becomes asynchronous instead of blocking the browser.

The owned-fixture Playwright workflow exercises empty validation, create, edit, reopen and delete with database assertions and literal quote/ampersand values within the 25-character schema. Node tests execute the production JavaScript and cover delayed and rejected token bootstrap, duplicate activation while a request is pending, failure-message precedence and save-result handling. They also cover a click that lands before `DOMContentLoaded`, when `csrf-token.jspf` has not yet published `window.csrfTokenReady`: the helper waits for the event rather than reading a still-empty input and reporting a bootstrap failure that has not happened.

The 27 payment-script cases also execute the JSP delete callback with null/malformed responses, numeric and string application errors, explicit success, and a transport failure. They check that rejection reasons are shown without redirecting and that request completion permits retry.

The [validation15 installed-DEB report](https://github.com/carlos-emr/carlos/pull/3789#issuecomment-5742899511) records all four payment workflow steps passing, including the empty-input database invariant. That run predates the early-click bootstrap fix; its regression coverage is the Node test described above. The later review reran the local script checks, not the installed-DEB workflow. Original 403 evidence is retained.
