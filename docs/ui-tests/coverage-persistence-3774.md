# Release persistence and screening report coverage (#3774)

This group tests the release emailConfig mapping and backports the column-widening SQL already on develop, using release version V1.0.23.1. Review exposed #3794: the deployed VARCHAR(1000) disagreed with the model's TEXT mapping. The SQL is byte-identical to develop V1.0.26, but the new version sorts below develop V1.0.24/V1.0.25 so those future features remain eligible for migration; a real Flyway ordering regression verifies that upgrade sequence. Both branch/province version sets were checked for collisions; no SMS or archive changes are imported. It adds reload-based checks for active-only selection, conjunctive sender/type/provider matching, deactivation, absent results, quoted sender input, enum conversion, and a 15KB synthetic JSON value. Security DAO tests cover provider ordering and rejection of non-allowlisted sort expressions.

Mammogram/Pap report scenarios exercise the production report code with fixed dates and controlled history/measurement inputs: no information, future records, due-date boundary, due, overdue, refusal, ineligibility, pending MAM results, report totals, follow-up action and billing metadata. They characterize the release's rules; they do not assert that historical screening intervals are current clinical guidance. Spring initializes the legacy static DAO dependencies, so these are integration-tagged rather than misleadingly classified as isolated unit tests.

Local validation: 48 JUnit cases passed, including the existing Security DAO scenarios. Transactions roll back owned rows. A disposable mutant removing active filters from EmailConfigDaoImpl was rejected by these tests. This is H2/JPA coverage, not evidence of a fresh MariaDB migration or live email transport.

Existing ConsultRequestDao and ProviderDataDao integration tests already exercise the implementations flagged by filename matching in the issue. Their measured baseline and remaining branch limits are recorded in the audit PR; this group does not duplicate those tests just to add implementation filenames.

Schema validation: the new migration unit regression proves that a 15KB synthetic JSON value fails before widening, then round-trips after the migration, preserving existing and NULL values. `scripts/email-config-schema-checks.js` runs against migrated MariaDB using the existing MYSQL_* configuration; it checks successful V1.0.23.1 history, the actual TEXT column, exact short/long UTF-8 JSON and NULL round trips, and rollback cleanup. It rejected the installed legacy BC schema before the fix. The exact migration applied and Flyway validated on that isolated schema; final installed-DEB round-trip validation is pending.
