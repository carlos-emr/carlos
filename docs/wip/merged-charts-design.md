# Merged charts (Merge Records): design for CDS export, with the owner's decisions

Read-only design made at `f3f0538654` (`/home/user/build/wt-integ`, PR #5706). Citations are `File.java:lines` at that commit; recheck them on your branch. Terms: **group** (the charts CARLOS shows as one), **head**, **member** (a merged-away chart).

## Owner decisions (2026-11-14, binding)

1. A chart linked by Merge Records exports as **one chart**: the head's file holds every record of every chart merged into it, in every category and through chains (beyond what CARLOS's head chart itself displays). A merged-away chart is not exported on its own.
2. Every member must pass **the same access checks as if it were exported alone**. If any member is refused, **the whole group is held** (new held reason `CDS_EXPORT_MERGED_CHART_ACCESS`; the held row names the head and which member was refused). A malformed group from older data (a cycle or a fork) is still exported, with a fixed head rule, never held.
3. **Import: everything into the head.** The receiving CARLOS imports every record of the file onto the head chart (which is what it already does with one file). The two merge carriers are kept **as source only**; members are not rebuilt as separate charts and merge rows are not restored natively.
4. If merge rows are ever restored natively, `lastUpdateUser` is the importing provider, with the sender's value kept in the protected source fields (moot under decision 3; record it in the docs).
5. A received file whose merged-chart carrier fails validation (embedded document or ranges do not match their digests, ids malformed) is **refused for review**: nothing of that patient is written, the run reports `CDS_MERGED_CHART_CARRIER_INVALID`, and the rest of the run continues.
6. A deleted history merge row that names a chart outside the file is carried as data (marked outside the file); nothing is held for it.

Standing rules also apply: no ordinary chart held for data shape; no caps; exact values in CARLOS carriers; never log PHI or chart numbers outside `LogSafe` operational use.

## 1. CARLOS's merge model (facts the code must respect)

- `demographic_merged` (`V1__baseline_schema.sql:2632-2644`): `id`, `demographic_no` (merged-away chart, no FK), `merged_to` (FK to demographic), `deleted int(1) NOT NULL DEFAULT 0`, `lastUpdateUser varchar(6)`, `lastUpdateDate DATE`. Entity `commn/model/DemographicMerged.java:42-112`.
- `secObjPrivilege` (`V1__baseline_schema.sql:10986-10993`), PK (`roleUserGroup`, `objectName`), plus `privilege`, `priority`, `provider_no`.
- Merge Records page `DemographicMergeRecord2Action.java:91-174` → `demographic/data/DemographicMerged.Merge` (86-124): refuses self-merge and cycles; inserts the link (`lastUpdateUser` = provider, `lastUpdateDate` = today, `deleted` 0) and, only if absent, the privilege row (`_all`, `_eChart$<member>`, `|or|`, priority 0, `provider_no` '0'); two strict log rows. `UnMerge` (126-159): sets `deleted = 1` on every row of that `demographic_no`, deletes the privilege row, writes a recycle-bin row.
- REST/manager path (`DemographicMergeService.java:98-129` → `DemographicManagerImpl.java:726-802`): inserts link rows only (no privilege row); unmerge sets `deleted = 1` on the active row only and leaves the privilege row. So privilege rows and active links are independent facts: carry both as captured, never derive one from the other.
- Chains exist (A→B→C). `findHead` (`DemographicMerged.java:196-212`) follows active outgoing rows with a visited set and in practice takes the greatest `id`; `getHead` returns the start chart when there is no head. Search replaces a merged-away hit by its head and hides merged-away charts; new appointments and incoming labs go to the head.
- Cycles: refused for new merges, may exist in old data. `findHead` returns null (each chart becomes its own head), labs stay unrouted, `getTail` recurses without a visited set (master record page `StackOverflowError`). A fork (two active outgoing rows) breaks `getHeadRecord`.
- The `|or|` privilege row does nothing for reading for any real role in this build (`SecurityInfoManagerImpl.java:148-153, 204-224, 262-277`; `OscarRoleObjectPrivilege.checkRights("or","or")` is inert). Carry it exactly; never use it as an authorization input.

## 2. What the head chart shows, and member checks

- CARLOS shows member records at the head one hop deep only, for allergies, medications, preventions, documents (filtered by program), inbox document results, consultation requests and HL7 labs (`AllergyMergedDemographicDaoImpl:58`, `DrugMergedDemographicDaoImpl:49`, `PreventionMergedDemographicDaoImpl:84`, `DocumentMergeDemographicDAOImpl:45`, `DocumentResultsMergedDemographicDaoImpl:76`, `ConsultationRequestMergedDemographicDaoImpl:60`, `CommonLabResultData:366-380`). Notes/CPP, measurements, appointments, ticklers, eForms, forms, HRM, messages, disease registry, contacts and pharmacies are not merged at the head. Decision 1 exports all of them anyway.
- Checks per member (decision 2): every check the export already applies to a chart on its own, run for the member: the opening pass `CdsExportAccessService.decidePatient` (946-1004) with `requireReads` (1226-1283; `_demographic` r at role and `$m`, `isAllowedAccessToPatientRecord(m)`, each selected category's object, `_lab_sensitive`, `_dxresearch`, `_eform`), `_rx`, case management (`_eChart` r, `canReadChart`), the `_con`/`_form` record questions; capture-time per-note program/role checks; the closing pass (1015-1045) and the cohort passes before packaging, publication and download. Effective provider and operator both.

## 3. Cohort and job scope

- Today: roster `DemographicDaoImpl.java:107-123` (no merge filter), explicit `127-141`; there is no "all patients" mode. `CdsExportMergeScopeValidator.requireUnmerged` (43-102) holds any captured active link, called from 11 sites (Laboratory:210, 955; Enrolment:126; Report:214; Appointment:242; Clinical:466; NewCategory:137; Immunization:202; Care:133; Demographic:146; History:248) → `MERGED_PATIENT_SCOPE` via `CdsExportClinicalPackageService.heldCode` (1527-1552). Each attempt re-selects (`CdsExportLedgerService.resetAttemptEvidence` 452-456, 1655-1667; `CdsExportClinicalJobService.execute` 127-136).
- **Group rule** (new shared contract `cds/contract/CdsMergedChartContract`): a row is active when `deleted = 0` and its `demographic_no` names an existing chart; `parent(c)` = `merged_to` of c's active outgoing row with the greatest `id` (CARLOS's effective choice); `head(c)` follows `parent` to a chart with none; if the walk repeats, the head is the smallest chart number in the cycle; `group(h)` = every chart whose head is h. Shape flags recorded, never held: `CHAIN`, `FORK` (non-parent active rows travel as links), `CYCLE`, `SELF_LINK`, `DANGLING`.
- **Selection** (`CdsExportSelectionService.capture` 80-148, in its snapshot): a new `CdsExportMergeGroupPlanner` reads active rows touching the selected charts in batches (a new CDS read on `DemographicMergedDao`, ≤ 500 ids per statement), expands each selected chart to its head and the head's whole tree, and writes a staged member `COHORT_GROUPS` sorted by head (head, head's `provider_no`, sorted members, sorted selected charts in the group, frozen active row ids, shape).
- **Cohort**: `CdsExportCohortManifestDto` protocol 2 binds the selection inventory and the group plan; `CdsExportCohortService` verifies heads ascending, members disjoint, every selected chart in exactly one group; its cursor yields one scope per group (`head()`, `members()`, `selected()`, `member(int)` with the same generation/thread checks); `expectedPatients` = number of groups; `readRetained` reads both protocols. A merged-away chart in a roster brings its head's group even if the head's physician is not in the roster; listing head and member gives one file; the file goes in the head's physician folder. `requireSelectedPatient` (1065-1071) accepts a chart in a sealed group that contains a selected chart.
- A merge or unmerge after selection within one attempt: groups stay frozen; the capture carries rows as they are then; ReadMe note `MERGE_CHANGED_AFTER_SELECTION`; a member unmerged after selection stays in this file with its link carried as deleted; a chart merged in after selection is not disclosed (its row is carried as naming a chart outside the file). The next attempt regroups.
- ReadMe (encrypted), job level: `Charts selected`, `Patient files (charts linked by Merge Records are one file)`, one `Selected chart in another patient file: <m> -> <h>` line per such chart, `Merged chart records: written` or `not exported (NO_CDS_ELEMENT_NEW_CATEGORY_NOT_SELECTED)`. Per patient file: one `Merged chart: <m>` line per member with record counts per section, `Merge links: n (active, deleted, outside this file)`, shape and change notes. `CdsExportSupportingFilesValidator` verifies them; the event CSV gains `MERGED_CHART` lines. Held groups appear with the head's number; ReadMe adds `Held patient selected as: <m>`.

## 4. Capture, sealing and resume

- Today everything is keyed by one `demographic_no` (`CdsExportPatientTableReadSupport` plans 1185-1378; `DEMOGRAPHIC_MERGES` reads `demographic_no = :patient OR merged_to = :patient`, deleted rows included; `captureSnapshot` 599-688; `measure` requires one demographic row 579-580; `CdsExportNativeCaptureDto` one patient; `CdsExportChartFingerprints.capture` 68-97; checkpoint entries keyed by patient; adoption requires `candidate.patient() == capture.patient()`; one authorization session per patient; one `patientKey` per document).
- **Recommended: capture each member and bind it to the head's package** (do not change every plan to read by the closure).
  - New `CdsExportNativeCaptureService.captureGroup`: authorize every member's categories and read scopes; inside one read-only repeatable-read transaction run the existing measure/write loop per member (head first, then members ascending), each with its own `SOURCE_VALUES`/`SOURCE_INDEX`; re-read the group's active rows in the same snapshot; re-authorize each member, write each member's `SOURCE_MANIFEST` with its read-back proof, then a `GROUP_MANIFEST` (head, ordered members with manifest id, SHA-256, capture fingerprint, frozen-plan digest, current-rows digest, differences). A lost snapshot restarts the whole group.
  - New source `merge_privileges`: the `secObjPrivilege` row (`'_all'`, `'_eChart$'+patient`) under the column collation as CARLOS looks it up, exact bytes, captured under Demographics for every chart through new `SecObjPrivilegeDao` CDS read methods (catalogue alias, `source-schema/merge_privileges.json`, a ruling note, `CdsExportSourceSchemaValidator` scope list).
  - Replace `requireUnmerged` with `requireGroupScope` at the 11 sites (shape and key validity only). Keep `MERGED_PATIENT_SCOPE` in the enum so older held records read, but never raise it.
  - One authorization session per member (Control keeps a map keyed by patient, `beginGroup`/`endGroup`); `verifiedCaptures(patient)` stays per member.
  - Fingerprint: `CdsExportChartFingerprints.group` hashes the head plus the ordered members' capture fingerprints; a single-chart group keeps today's fingerprint exactly.
  - Checkpoint protocol 2: chart entries keyed by head gain `members` (patient, `sourceManifestSha256`); adoption needs the same parameters and group fingerprint; a chart is reusable only if every member is. A merge, unmerge, privilege change or head flip between attempts changes the group fingerprint, so the chart is rebuilt; a kept chart whose head is now a member is never a candidate.

## 5. XML assembly

1. For each member in order, run the existing `payloads.freeze` and `CdsExportPatientDocumentService.compose` with the member's own `patientKey`, inventory, receipts, coverage and finished-XML validation, into a private intermediate document, with two additions: an Appointments ordinal base (so `CARLOS.Appointment.Source.v1` names positions in the final file; `CdsExportAppointmentSourceMapper.java:134`, `Occurrence` 159-179, the NewCategory pass) and an occurrence map (category, offset, length, SHA-256) from the composer's counting output (183-212).
2. New `CdsExportMergedChartComposer` writes the patient file with the same header and root (150-165): for each category in order, copy the head's occurrences then each member's by verified byte range; each copy's digest must equal that member's `EMITTED` disposition. Members' Demographics and `CARLOS.NativeDemographic.v1` records are not copied (they go into the member carrier).
3. The NewCategory section ends with one `CARLOS.MergedChart.v1` record per member, then one `CARLOS.MergeLinks.v1`.
4. Then `CdsExportXmlValidator` with the head's sender id; references checked against the union of attachments (paths are hashed with each member's key, so they cannot collide); `authorizeCapturedSources` per member.

Carriers (names in `CdsNativeExtensionContract`; rules in `CdsMergedChartContract`):
- `CARLOS.MergedChart.v1`, one per member; CategoryName and DataElement name `CARLOS.MergedChart.v1`; CategoryDescription "Chart merged into this patient's chart in CARLOS (Merge Records)"; tokenSafe JSON: `version: 1`, `chart: "C34"`, `head: "C12"`, `positions` (per section, first 1-based position and count, NewCategory included), `document` (the member's exact standalone CDS file with only its Demographics and, if written, its `CARLOS.NativeDemographic.v1`, schema-validated before writing), `documentSha256`.
- `CARLOS.MergeLinks.v1`, one per file whenever any chart in it has a merge row or privilege row: `charts`; `links` (every `demographic_merged` row naming a chart in the file, active or deleted, exact text, SQL NULL as null, in `id` order; a chart outside the file named by its sender id with `outside: true`); `privileges` (chart, `roleUserGroup`, `objectName`, `privilege`, `priority`, `provider_no`); shape flags and change notes.
- Field accounting: link and privilege fields `MAPPED` under rule `EXACT_MERGE_LINK`; each member's Demographics occurrence `MAPPED` to its carrier.
- When NewCategory is not selected: no carriers; all members' records still in the file; ReadMe line `NO_CDS_ELEMENT_NEW_CATEGORY_NOT_SELECTED`; each member's Demographics recorded as `OPERATIONAL`.
- A non-CARLOS receiver sees one patient (the head's Demographics), every member's records in every section, opaque CARLOS records. Data summaries of member records print the member's CARLOS number; add "merged into CARLOS patient <h>".
- Document: a record entered in two charts (a duplicate allergy) is exported twice (as the head displays it); a record linked to two charts (HRM, message, document) is exported once per chart.

## 6. Import (decision 3: everything into the head)

- The importer already imports every record of one file onto one patient, so the records of members land on the head's chart with no planning change.
- New `CdsMergedChartReader` (model: `CdsAppointmentResidualReader`) validates the two carriers from the sealed parse before any write: the head id equals the file's id; member ids unique, of the form `C<positive integer>`, different from the head; ranges inside each section and non-overlapping, the head owning every other position; each embedded document's SHA-256, schema validity and id match. Invalid → refuse the patient for review with `CDS_MERGED_CHART_CARRIER_INVALID` (decision 5), nothing written for it, the run continues.
- Valid carriers are kept as source only (as other `CARLOS.*` carriers the importer does not restore), with the import report noting "N merged charts from the sending CARLOS imported into this chart".
- Re-export from the receiving CARLOS: the chart is a single chart; the retained `CARLOS.MergedChart.v1` / `CARLOS.MergeLinks.v1` records describe the sender's structure and positions that no longer hold. Do not re-emit them as current carriers; document the rule (they stay in the import's retained source).
- No ledger, receipt or abandon contract changes are needed.
